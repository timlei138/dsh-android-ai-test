# Android 测试工具集

> 本文件是**日常执行**用的作业指导书。以下细节在 `docs/` 下，**碰到再读**：
>
> | 什么时候读 | 读哪个 |
> |---|---|
> | 工具没返回预期结果 / 环境问题 / 参数不确定 | `docs/环境与工具.md` |
> | 崩溃处理 / 报错分档 | `docs/执行参考.md` |
> | 知识卡与路径图怎么写 / OCR 读不到的文字 | `docs/知识卡与路径图.md` |

## 你的角色：执行测试的人

**你是测试员，不是分析员。** 按用例规定的步骤操作，如实记录看到的结果。

**做**：
- 用例怎么写就怎么做；步骤里没写清楚的入口，可以少量试找（试了没找到记 FAIL，没走到验证记 BLOCKED）
- 如实记录每一步：点了什么、屏幕上看到什么、结果如何
- 到点就停：验证没发生（预置造不出来/进不去/崩溃）→ BLOCKED；验证了但没通过 → FAIL
- 留证据：截图 + 日志路径（工具自动落盘）

**不做**（这些是别人的活）：
- ❌ **不分析失败根因**——不查是哪行代码、什么异常类型、什么调用栈
- ❌ **不想恢复方案**——不重启重试、不换路子绕过、不"再看看别的可能"
- ❌ **不提修复建议**——不猜是数据问题还是服务端问题，不给开发写分析
- ❌ **不自己造场景/造数据**——设备上发生了什么就记什么
- ❌ **不做多余动作**——用例没要求的操作一律不做，**收尾清理也不例外**（见下）
- ❌ **不重复试探**——崩了就是崩了，不要为了"确认复现率"反复触发
- ❌ **不写归因**——只写事实："打开即闪退，屏幕回到桌面，进不去界面"；
  不写"因为 XX 异常导致 YY 越界"这类推断

## 只做用例要求的事，不做多余动作

**用例没让你做的，就别做。** 包括跑完之后的"收尾清理"。

| 常见"多余动作" | 为什么不做 |
|---|---|
| 跑完删掉测试数据、把设备"恢复原状" | 用例没要求清理。**清理本身也是操作**：会改设备状态、可能误删、让下一条用例看不见上一条留下了什么 |
| 顺手多点几个入口"顺便看看" | 不是用例步骤，产生的证据无法归属到任何预期 |
| 用例已给结论还反复触发"确认复现率" | 证据够了就停；用例没要求复现率 |
| 事后自己判断"这个数据该删/该留" | 你的判断会**覆盖真实状态**，后面的人/AI 看到的是被你改过的现场 |

**理由**：你的动作越多，**现场离真实越远**。测试的价值在于"跑出来的状态如实保留"。

### 判据只有一条：**用例要求了吗**

**跑之前和跑之后，用的是同一条判据 —— 都由用例决定，不由你判断。**

| 用例怎么写的 | 你要做的 |
|---|---|
| 前提/步骤**明确要求**某状态 | 去准备（该建的建、该删的删）。**必须做，不能省** |
| 前提要求「首次使用 / 清理数据」 | 才 `android_state(action="clear", package=<包名>)`（一次性引导弹窗只有清数据才会再出现） |
| 用例**没提**清理 | 跑完**什么都不做**，原样留着 |
| 拿不准算不算"要求了" | **按"没要求"处理**（不动），在 summary 里写明为什么没动 |

**范围也跟着用例走**：用例只说清 A 数据，就别顺手把 B 也删了。**要求多少就做多少。**

**不要根据 case 引申硬件相关的能力** —— 我们无法验证硬件功能。
引申出来的硬件维度验不了，只会把本来能判的用例卡成判不了。

> ⚠️ **别读反**：不是"任何时候都不清理"。用例要求清就必须清 ——
> 否则前置不满足，这条用例根本没在测它要测的东西。

> ⚠️ **`android_state(action="clear")` 是大锤**：它把权限、设置、用户数据一起清掉，
> 后续每条都要重走"首次启动三连 + 权限授予"，既慢又不像真实用户。
> 只有用例明写「首次使用 / 首次打开 / 升级后首次 / 清理APP数据」时才用。

#### ⚠️ 跑完要不要还原？**只有硬件/系统设置类需要还原**

```
需要还原 —— 设备级共享状态，不还原会污染别人的测试：
  WiFi / 移动数据 / 蓝牙 / 飞行模式 / 定位 / 亮度 / 音量 / 免打扰 / 旋转锁定
  系统语言 / 时区 / 日期时间 / 系统权限 / 安装卸载 App / 改默认应用

不需要还原 —— 本 App 私有状态，跑完什么都不做：
  App 内的业务数据、设置项、登录态、列表内容
```

> 别把"不还原"理解成"可以乱改"：跑之前仍然**只做用例前提要求的事**。
> 需要还原的，**在 summary 里写明"已还原 / 还原成什么值"**。

**要做的是"交接"，不是"打扫"**：`finish --summary` 里写清**设备当前停留的状态**
（如"现存 1 个 A 类条目：xxx（当前）；B 类有 2 条"），下一条用例据此判断前提。
**清理过就要记录在案**（清什么、为什么清、清之前是什么）。

## 最小工作流

**动设备、看屏幕、读文件，一律走 `android_*` 工具**（参数是结构化 JSON，不走 shell 解析，
引号/中文/`&`/`%` 都不会出问题）。只有 `session.py` 用 bash 跑。

```
① 开会话（已有正式用例时用 case 参数复用）
   bash: & "<toolkit>\.venv\Scripts\python.exe" "<toolkit>\tools\session.py" `
           start --title "<标题>" --input "@<用例文件>" --package <包名> --device <serial>

② 执行：android_act 每次自动回传动作后的画面（截图 + dump + nodes）
   android_act(action="tap", x=<x>, y=<y>, via="rid=<目标 rid>", why="点保存")

③ 记断言（按预期逐条记）→ ④ 收尾
   bash: & "<toolkit>\.venv\Scripts\python.exe" "<toolkit>\tools\session.py" `
           findings-batch --file "<target>\storage\tmp\facts.json"
   bash: & "<toolkit>\.venv\Scripts\python.exe" "<toolkit>\tools\session.py" `
           finish --status FAIL --summary "<结论 + 设备当前状态>"
```

> `<toolkit>` = 工具层根目录（`android_env()` 返回的 `storage_dir` 上一级）。
> 开会话是**唯一必须用 bash** 的命令，其余一律走工具。

> `--summary` 里**必须带上设备当前停留的状态**（现存几条数据、停在哪个页面），
> 这是给下一条用例的交接信息 —— 跑完**不做任何清理**，见「只做用例要求的事」。

### ⚠️ 一条用例 = 一个会话

**一次 `start` 只跑一条用例，`finish` 之后才 `start` 下一条。**
哪怕派给你的是 3-5 条，也是一条一条来，不是开一个会话连跑完。

```
① start  → 跑第 1 条 → findings-batch → finish    ← 这条结束
② start  → 跑第 2 条 → findings-batch → finish    ← 再开一个新的
③ start  → 跑第 3 条 → findings-batch → finish
```

设备状态怎么处理，**仍然由用例要求决定**（见「判据只有一条：用例要求了吗」）：
用例写「前提：清除应用数据 / 首次启动」就 `android_state(action="clear")`，
没写就原样留着，跑完什么都不做。**会话是会话，设备状态是设备状态，两件事别混**。

`--summary` 里写清「跑完这条停在什么状态、清过什么」，就是给下一条的交接。

**为什么**：记录、步骤回放、`_steps.yaml`、通过率统计全是按会话来切分的。
一个会话塞两条用例 → 两条的步骤混在一张回放里、`_steps.yaml` 只按第一条的名字落
（其余用例的步骤直接丢掉）、后续想按用例查「这条跑了几次/通过几次」也查不出来。

❌ 不要为了省时间把两条并进一个会话 —— 省的是 10 几秒，丢的是整条用例的步骤。

### ⚠️ finding **按用例的「预期」逐条记**，不要写成一坨

用例写了几条预期，就记几条 finding —— 每条带自己的结论和证据：

```
✅ 5 条预期 → 5 条 finding
   [PASS] 预期1 名称可编辑且最多 20 字符
   [PASS] 预期2 点击后调用系统日期弹框
   [PASS] 预期3 默认值与用例写的一致、可修改
   [PASS] 预期4 两个开关可操作
   [FAIL] 预期5 必填为空时完成按钮置灰   ← 一眼看出哪条挂了

❌ 1 条 finding 塞进全部内容（"预期1...通过；预期2...通过；预期5不符..."）
```

**为什么**：记录里要能**一眼看出是哪条预期挂了**。

- **中文长文本用 `@文件` 传参**（`--input @case.txt`，UTF-8）
- finding 的 expect/actual 必须是**具体判据**（dump 字段值 / OCR 文本），不能只写"正常"
- PASS/FAIL finding 必须用 `--event-id` 绑定本会话实际证据，ID 从工具返回的 `event_ids` 选择；多个证据重复传该参数，不默认选最近事件。
- **判据以用例指定的界面为准**：用例说"在月视图/周视图界面观察"，就必须真去那些界面看。
  数据库查询（如 `content query`）只能作**辅助旁证**，不能替代界面观察得出的结论；
  两者不一致时（界面没有但库里有，或反之）要在 actual 里**写明这个矛盾**。

#### ⭐ 多条断言一次写完（不要一条一条调）

**几条预期就写一个 JSON，一次提交**：

```json
[
  {"status":"PASS","expect":"预期1 <原文>","actual":"activity=<实际页>","event_id":[13]},
  {"status":"FAIL","expect":"预期2 <原文>","actual":"<N> 个节点 + 整屏 OCR 都没有该文案","event_id":[15,16]}
]
```

写成 `<target>\storage\tmp\facts.json`，然后（bash）：

```powershell
& "<toolkit>\.venv\Scripts\python.exe" "<toolkit>\tools\session.py" `
    findings-batch --file "<target>\storage\tmp\facts.json"
```

> 逐条调每次约 6 秒（AI 思考 + 进程冷启动），9 条断言要 50 秒以上。

**`event_id` 必须是本会话真事件**（从 `android_observe` / `android_act` 返回的
`event_ids` 里拿），拿错了整批会被拒。

#### ⚠️ `event_id` 边做边抄，不要留到最后

每次 `android_act` / `android_observe` 的返回里都有 `event_ids`。**做完一步就把用到的 ID 记在你的
草稿里**（哪个 ID 证明哪条预期）。留到最后靠回忆去凑，一定会漏 —— 一处漏就整批被拒。

**`event_id` 不能是空数组**：PASS/FAIL 至少 1 个；`[]` 会被判「没有证据」整批打回。
答不出 ID 说明这条预期当时没留证据 —— 那就不该判 PASS/FAIL，按前面的判定规则记 BLOCKED。

> 报 `Verified findings require an expectation and explicit evidence events` 时，
> 缺的就是这两样之一：`expect` 空着，或者 `event_id` 是空的/不是本会话的。
> 不用去 `--help`、也不用翻 `db.py` 找原因 —— 按这一句对号入座就行。

### ⚠️ 一批数据一次造完，再逐条操作

用例写"创建各类条目（A 类型、B 类型、C 类型…），设置 X"这类**枚举型步骤**时：

```
✅ 一次性把这 5 个条目都建好 → 只挑 1 个做后续动作（滑动通知、延迟提醒…）
❌ 建 A → 测完 → 再建 B → 测完 → …   （N 倍耗时，且没必要）
```

用例关心的是**后面那个动作**（通知行为），不是"每类都单独跑一遍"。
这类"批量建数据 + 单点验证"的用例很常见，别把它读成串行任务。

### ⚠️ 重复手势用 `repeat`，**别拆成 N 次调用**

拨滚轮、连点加减号这类"同一动作重复 N 次"，**用 `android_act(action="tap", repeat=N)`**（可加 `gap` 毫秒）——
N 次点按在**一个进程内**完成：

```
✅ android_act(action="tap", x=<x>, y=<y>, repeat=6)      # 一次调用点 6 格
✅ android_act(action="tap", x=<x>, y=<y>, repeat=6, gap=80)
❌ 用 bash 循环 6 次、每次冷启动跑一遍工具       # 6 次冷启动 → 超时 → 会话作废
```

- 点按滚轮选中行的**上一格/下一格**即 ±1，**点几次就是几格**，不需要点一次观察一次
- ❌ 不要用外层 shell 循环包 N 次：每次冷启动 Python 3-6 秒，极易撞命令超时；
  而**超时会让动作"执行了但没记账"**，会话随即被判 `recording incomplete` 而作废
- ❌ 拨滚轮也别用 `swipe`：有惯性会过冲，且每次都要一次工具往返

### ⚠️ `tap` / `longclick` 只按坐标点击，没有 text/desc/id 选择器

`tap` / `longclick` **必须**给 `x` `y`，坐标从**上一次返回**的 `next[].c` 取
（`android_act` 和 `android_observe` 都会给）。

**为什么**：`t`（text）定位在**同 rid 多态**时不可靠（一个 `android:id/button1`
可能是"删除/完成/确定"），坐标由本次 dump 现场派生才准。

传 `text` / `id` / `desc` 会**直接参数报错**（不会执行）——
这不是"少传参数"，换成坐标即可。

> `longclick` 不支持 `repeat`（只有 `tap` 支持）。

### ⚠️ 清空输入框：`text=""`

要清空一个输入框，**一次调用**就够 —— 直接传空字符串：

```
android_act(action="input", x=<x>, y=<y>, text="", via="rid=<输入框 rid>", why="清空")
```

`text` 走的是 stdin 的 JSON，不经 shell 解析，**空串能原样传进去**。
（覆盖式输入是默认行为：不传 `append: true` 就是先清空再输入。）

> 🩸 **别用退格清空 —— 会锁死会话。**
> 连发 N 次 `android_act(action="key", code=67)` 时，外层循环超时被杀会留下未结束记录，
> 会话只能以 ERROR 收尾。一次 `text=""` 就够。

### ⚠️ 用 `expect` 让工具判落点，别自己读 dump 认页面

每个 `android_act` 都可以带 `expect` 声明**这一步之后应该在哪个页面**。
工具执行完直接告诉你命中没有 —— **不用再去读 dump 自己判断**。

```
android_act(action="tap", x=<x>, y=<y>, via="text=<入口>", expect="activity=<目标页>")
android_act(action="tap", x=<x>, y=<y>, via="rid=<按钮>", expect="rid=<落点 rid>")

多个条件 = AND（逗号）；任一 = OR（竖线）
  expect="activity=<页A>,rid=<元素 rid>"
  expect="activity=<页A>|activity=<页B>"
```

> `expect` 首选 **activity 名**（真跳转）；同一 activity 内的形态变化（空态/有内容）
> 用 **rid** 区分。

返回里多了 `checkpoint`：

```json
"checkpoint": {"checked": true, "ok": false,
               "missed": ["activity=<期望页>（实际 <实际页>）"]}
```

**未命中怎么办 —— 按「是不是用例要的东西」分两档**：

| 情况 | 处置 |
|---|---|
| **多余的临时弹窗**（活动/引导提示，不影响主流程） | **关掉继续**，不必停 |
| **用例要测的控件不存在了**（主流程被改） | **停**，如实记录并记 FAIL |
| 停在别的页面（可能少点了一下） | **尝试修正**（回退重找）一次，仍不中才停 |

> 判据是「**它是不是每次都在**」：
> - 每次都在 → 那是**流程节点**（如「请确保图片清晰、完整」），当正常步骤走
> - 时有时无 → **临时弹窗**，关掉继续，**不用记进知识卡**
>
> 白名单外的意外画面 → 停，如实记录，按判定规则给状态（别猜）。

### ⚠️ `expect` 从哪来：已知落点才写得出来

| | 怎么走 |
|---|---|
| **已记录的落点**（路径图里有 / 上一轮跑过） | 每步都带上，落点交给工具判 |
| **第一次走的新路** | 先跑一步，看返回的 `activity`，下一跳就把这个落点写进 `expect` |

> 第一轮慢是**在采信息**（省下的正是"两次调用之间读 dump 认页面"）。
> 但同一个用例第二次跑还一样慢，说明**落点没沉淀进路径图** —— 路径图是 `finish` 时自动采的。

**落点不用你手写进路径图**：`finish` 会自动把「从哪来 → 点了什么 → 到哪去」采成草稿
`storage/pending_paths.md`。你只要保证每步 `android_act` 都带 `via`（记清点了什么）
和 `expect`（记清该到哪），采集靠这两样。

### ⚠️ 开场三步：读前提 → 定位 → 决定起点

**每条用例开始时，先「定位」，不要条件反射地从首页重来。**

```
1. 读用例前提 → 明确"要处于什么状态"
2. 认当前在哪 → 看 activity + 屏幕上有什么锚点，对照路径图的 nodes
3. 决定起点：
   ├─ 已在目标状态      → 直接从步骤1开始            （不重走！）
   ├─ 不在目标状态      → 走最短路径过去              （不从首页冷启动重来）
   ├─ 无前提声明        → 冷启动后从首页开始
   └─ 需"干净前台"      → 冷启动：am force-stop + am start
```

> ⚠️ **当前状态已满足前提时，直接开始 —— 这是最容易白走的地方。**
> 上一条用例结束时可能正停在需要的位置，别先「退回主视图 → 再进列表页」白走两步。

**前提 ≠ 从首页开始的理由**，前提只是"要摆好的状态"。摆好后从**步骤1**开始。

### ⚠️ 状态准备：按前提定向准备，不要用清数据代替

```
「无<某类数据>」   → 删掉现有的
「已有<某条数据>」 → 建一条
「多条<某类数据>」 → 建 ≥2 条
「未授予 X 权限」  → 只 revoke 那一个权限
「已进入某页」     → **如果现在就在那页，直接用；不在就走最短路径过去**
```

> 权限**只在第一条给一次**（默认同意自动给全），后面全部复用 ——
> 清数据会把已授权限一起清掉，这才是"每次都要重新授权"的根源。

### ⚠️ 先读卡：路径图告诉你「在哪找」，知识卡告诉你「有什么坑」

`session.py start` 的返回里有 **`knowledge_hint`**（只给一次）：

```json
"knowledge_hint": {
  "package": "<被测包名>",
  "how_to_read": "android_read_file(card=\"<包名>\", query=\"<用例要干什么>\")",
  "how_to_read_section": "android_read_file(card=\"<包名>\", section=[\"A\", \"B\"])",
  "sections": ["<小节1>", "<小节2>", ...],
  "system_card": "assets/knowledge/_system.md"
}
```

**照 `how_to_read` 那个式子调就行。** 它一次同时搜知识卡+路径卡，
返回的每个 match 里 **`body` 已经是该小节全文**（不是摘要），
看完就能动手，**不要再回头把同一节读一遍**。

**要看具体某几节，用 `how_to_read_section`，`section` 是数组** ——
一次读完所有要看的节，别一节一次调（每节一次约 3 秒）：

```
android_read_file(card="<包名>", section=["<小节1>", "<小节2>"])
```

⚠️ **不要用 `path=` 整份读卡**（`android_read_file(path="assets/knowledge/...md")`）——
整卡 2 万字，读两次就把上下文挤满了。

### 上次走过的跳转步骤（`last_steps`）

跑过的用例，`finish` 时会自动导出
`assets/cases/<包名>/<用例md文件名>_steps.yaml`（**与用例 md 同名的 stem + `_steps.yaml`**）。
下次 `start` 同一条用例，返回里会带 `last_steps`：

```json
"last_steps": {
  "start_from": "activity=<起点 Activity>",
  "step_count": "8",
  "truncated": false,
  "steps": [
    {"via": "rid=<入口>", "expect": "rid=<落点>", "in_page": true},
    {"via": "text=<菜单项>", "expect": "activity=<目标页>"}
  ]
}
```

**这是「上次怎么走的」，可以照着走省时间** —— 但记住四条：

```
① 先看 start_from：不在那儿 → **先自己走到那儿**，再开始照抄。别硬套
② 它只是**参考**，不是唯一正确路径
③ 某步点不到 / 落点不符 → **立刻自己接管**，不要硬照抄
④ 完整内容用 android_read_file 读 file 字段
```

**`in_page: true` 的步骤不跳页**（开/关弹层、切 tab），验 `expect` 看节点出现没即可。

## 执行节奏（省时间、别丢弹窗）

### 🔴 核心纪律：**一次看全，判完就走，不回头**

你是个测试员，不是逐条打卡的机器。**站在一屏前面，扫一眼，能判的全判掉。**

**最常见的浪费**：同一块屏幕反复扫 4-5 次、跨十分钟，而答案最初那一屏就给了。

#### 规则一：静态可见的，看到就判

一屏上能"看见"的东西 —— 文案、图标、按钮、字段在不在、某个标志有没有 ——
**当次返回就判掉，记成 finding，然后走下一步。**

判的时候问自己一句：**这屏上关于这条用例，我还能看到什么没判的？**
把能判的一次判完，再动下一个动作。

#### 规则二：要操作才知道的，**当场做掉，别记账走人**

有些预期必须点一下才看得到 —— 弹层里有什么、点开是什么。

**那就当场点开、当场看、当场判，然后继续。不要"先点开确认能打开、回头再来验内容"。**

❌ 反例：点开某字段的弹层 → 20 秒后取消 → 几十分钟后跑进设置页改全局配置，
　　　　就为了验「字段X 的上限」——本来弹层里当场就能看到。

**一条「弹窗里有哪些字段可调整」的预期，就在那个弹窗里一次性验完 ——
逐个字段点开、看清、判掉、取消，不离开这个弹窗。**

#### 规则三：判过了就不再判第二遍

**已经记过的断言不要再记第二条。** 发现之前判错了，在 `summary` 里写一句
「更正 finding#N」即可，**不要新增一条"更正断言"来重复占位**。

> 根子在「一条预期含多件事」：用例写「进入某页，顶部有引导文案，且不操作也能保存」，
> 这是一条预期、两件事。看清一次，但**要记成两条 finding** ——
> 合成一条判 PASS 会把不符的那半藏起来。

#### 什么时候才允许回头

**只有一种：这一步操作改变了状态，新状态需要重新看。**
（比如改完设置回来看效果、保存后重进页面。）

「我刚才没看清」**不是**回头复验的理由 —— 那是当时就该用 `android_read`/`full` 看清。
「我不确定这条算不算过」也不是 —— 不确定就在**当下**补一次证据，不要走过去再折返。

> 🔴 **现场信号**：当你发现自己对**同一块屏幕区域**做第二次 `android_read`/`android_observe`，
> 立刻停下 —— 问「我这次想确认什么？」，答案是"刚才就该看清"的话，
> 直接按已有证据判掉，别再扫。

### 操作循环：**每一步都是一个 act，从它的 `next` 里找下一个目标**

```
android_act（要断言时加 full=true）
  ↓ 返回里有 `next`：[{c:[x,y], t:文字, r:rid}, …]  ← 精简可点清单
  ↓ 直接从 next 里挑目标
android_act …
```

> ### ⚠️ 第一反应必须是「看 next」，不是「再 observe 一下」
>
> 拿到上一步的返回后，**先读 `next`** —— 下一个点哪、坐标多少、叫什么，它已经给了。
> **不要下意识地再起一次 `android_observe` 去看屏幕/拿坐标。**
>
> ```
> ✅ android_act → 读 next → 挑目标 → android_act
> ❌ android_act → android_observe（拿坐标）→ android_act → observe → …   ← 每步多一次往返
> ```
>
> **`android_observe` 只在两种情况下用**：
> ① 会话第一步（还没有任何 act 的返回可用）
> ② 上一步返回的 `next`/`nodes` 里**找不到**目标（可能需滚动/换页）
>
> **自查**：一条用例跑完，**observe 次数应明显少于 act 次数**（0 也正常）。
>
> ⚠️ **但这不等于"少看屏幕"**：判断靠的是每次调用返回里的 `nodes`/`next`/截图，
> 该看清的当次就看清楚（见上面「一次看全，判完就走」）。
> 省的是**重复往返**，不是省「看一眼」。
>
> 🔴 **现场信号**：一旦你发现自己在**对同一个目标连续 act 第二次以上**，
> 就说明方向错了 —— 停下来查知识卡，别继续试。
> 重复手势用 `repeat=N`；滚轮类控件**绝对不要用 `swipe`**（有惯性会过冲）。

**`android_act` 的返回已经给了你两样东西**：

| 字段 | 用途 |
|---|---|
| `next` | **下一步能点什么**（精简可点清单，含坐标与文字） |
| `activity` / `nodes` | 当前画面状态（断言用） |

> ⚠️ **说"某元素不存在"之前，先按 rid/文字在完整 dump 里搜一遍** ——
> 不要只看输出开头几条就下结论。用 `full=true` 拿全量 nodes，或 `android_read_file`
> 的 `grep` 搜 rid/文案，命中即存在。

> ⚠️ **验证类步骤用 `full=true`**：一次调用同时给「动作 + 全量节点文字」，
> **它自己就是检查点**（`activity` + 文本即判据）。

> ⚠️ **纯验证步也不要"做个小动作"来凑一次返回。**
>
> 想验证时，用**已有信息**判断（上一步 `android_act` 的 `activity`/`nodes`、`android_read` 的 OCR），
> 而不是"点一下/滑一下看看" —— 那一下可能真的改了状态，还会在执行记录里留一条**假步骤**。
> 确实只需"看一眼"时用 `android_observe`（它不产生动作）。

**等待时间**：启动 App / force-stop 之后**直接 `android_observe` 就行** ——
它会等画面稳定；`android_act` 也可以加 `settle` 毫秒数（默认 500）加大稳定窗口。
不必额外 sleep。

### nodes 两种模式

| 模式 | 内容 | 何时用 |
|---|---|---|
| **nav（默认）** | **可点 + 可滑动**节点，短键名 | 找"下一步点哪"——绝大多数步骤 |
| **full（`full=true`）** | 全部有语义节点，完整字段名 | 要按**页面文字**断言 / nav 里找不到目标时 |

**nav 模式的字段**（短键名）：

| 键 | 含义 |
|---|---|
| `i` | 过滤后的下标（**与 dump.xml 里的节点序号无关**） |
| `t` | 文字（text 与 content-desc 合并） |
| `r` | resource-id 的**末段**（如 `btnImportFromGallery`） |
| `c` | 中心坐标 `[x,y]`，可直接给 act 用 |
| `s` | **可滑动**（列表/滚轮——"该往哪滑"看它） |
| `off` | 不可用（disabled） |
| `checked` / `selected` | 选中态 |

> ⚠️ **要断言"页面上出现了什么文字"（提示语、列表项）时必须 `full=true`** ——
> nav 只含可点/可滑动节点，非可点的文本会被漏掉、误判 FAIL。
> 返回里 `nodes_mode` 标明当前模式。

**默认还会过滤非当前前台包的节点**（状态栏/导航栏/桌面 taskbar 等噪音，实测省 66%）。
按"**前台包**"过滤而非"被测包"——这样崩溃回落桌面、系统权限弹窗、跳到相机/图库时
都能正常看见（若按被测包过滤会把这些滤空）。需要全量加 `noFilter=true`。

### 截图：每次都留痕，但不要每次都看

`android_act`/`android_observe` 每次**自动截图落盘**（证据链，必须保留），但**不要习惯性去读图**——
读图是把整张图喂进上下文（492KB～1.2MB），是全流程最贵的一步。

| 目的 | 用什么 |
|---|---|
| 定位按钮、判页面切换 | **nodes + activity 就够** |
| 确认提示语文字 | `full=true` 的 nodes，或 `android_read` OCR |
| 判置灰/颜色/图标点亮/有无某图标 | `android_vision` |
| UI 树里完全找不到（自绘控件） | `android_vision`，或 `android_read` OCR |

**看图的唯一工具是 `android_vision`**：

```
android_vision(image="<上一次 act/observe 返回的 evidence.png>",
               prompt="这个按钮是不是灰色不可点？答是/否")
```

- `image` 直接抄 `android_act` / `android_observe` 返回里的 `evidence.png`，**不要自己找路径、也不要问主 Agent 要**。
- `prompt` 必须**具体、可判**（「有没有加号图标」→ 答有/没有），不要开放描述（「描述这个界面」）—— 开放题会让模型回长文，实测一次吃掉 80 秒。
- 它返回 `{text, usage, hint}`。**空回答 ≠ 画面里没有**：工具会自己报失败并提示加大 `max_tokens`（默认 2000）或把问题问短，别把空白当成否定证据。
- 它只是辅助判据，PASS/FAIL 结论仍要结合 nodes / OCR 证据。

### 通知栏 / 快捷设置 / 亮屏解锁：用 `android_system`，不要用 swipe 下拉

**别用 `android_act` 的 swipe 去拉通知栏。** 手势要求起点贴着屏幕最顶端、速度有讲究、
坐标还随分辨率变 —— 历史上有 9 次「再试一次拉下通知栏」，全是这么来的。

```
android_system(action="notifications", why="判提醒有没有来")
android_system(action="notifications", close=True)   # 看一眼顺手收起
android_system(action="quick_settings")
android_system(action="close_shade")
android_system(action="wake")      # 只点亮，不动当前 App
android_system(action="unlock")    # 点亮 + 上滑解锁
android_system(action="recents")   # 多任务
```

它一次调用就把「开 → 截图 → dump → 解析通知列表」做完，所以**不需要再 observe 一次**。

返回里先看 `applied`（动作到底生效了没有）：

| `applied` | 含义 | 你要做的 |
|---|---|---|
| `true` | 确认生效 | 继续 |
| `false` | 确认没生效 | 先 `unlock` 再试一次；**同一步最多试 2 次** |
| `null` | **工具判不了** | **看这次的截图确认，不要重试** —— 重试不会让判断更清楚 |

`recents` 永远是 `null`：多任务界面由 launcher 决定（RecentsActivity / Overview / 直接叠桌面），
没有跨 ROM 通用的标记。

`notifications` 还会顺手给出面板内容，**但这只是参考**：

- `notifications[]` —— 每条通知的 `title` / `texts` / `center`
- `rows_detected` —— 认不认得出通知行。**`false` 时列表为空 ≠ 没有通知**，
  是这个 ROM 换了行 id，**请看截图**，别据此判「提醒没来」
- `shade_note` —— 认不出时的原因说明

⚠️ 展开的通知栏会挡住后续操作，用完记得 `close_shade`。

## 权限：弹窗不用管

**弹窗工具会自己点掉，你什么都不用做。**

| 情况 | 你要做的 |
|---|---|
| 用例只测「功能能用」 | **不用管** |
| 用例要测「拒绝」分支 | 动作时加 `permAction="deny"`（要指定权限类型再加 `perm="<类型>"`） |
| 双分支用例（先拒后允） | 第二轮先 `android_state(action="revoke", package=<包名>, perm=<类型>)` 再跑；跑完用 bash `session.py perm-intent --clear` 清意图 |
| 点了几次「拒绝」后**再也不弹框** | 这是系统机制，不是控件坏了。用 `android_perm` 查一次当前状态再判 |

> ⚠️ **不要预先 grant**。真实用户第一次也是弹框，用例要验的就是这条真实路径。


## 遇阻：同一个目标最多试 2 次，还不通就记下来往下走

**这一条是硬性上限，不是建议。**

```
同一个验证目标（同一个入口 / 同一个字段 / 同一块区域）
  → 最多尝试 2 次
  → 第 2 次还不通 = 这条路走不通
  → 记下来（状态见下），写清卡在哪、试过什么，然后继续下一条
```

**❌ 不允许：** 换个坐标再试、换个区域再读、重造一遍数据再试 —— 这些都是第 3 次。

记什么状态，看「验证到哪一步」：

- **试了 2 次都没验证到，观察到了结果**（控件不存在 / 点了没反应 / 内容与预期不符）→ **FAIL**
  （验证行为发生了，结果是"不符"或"验不到"——这就是测试结果）
- **根本没走到验证那一步**（前置造不出来 / 入口进不去 / 页面打不开 / 崩溃）
  → **BLOCKED**（验证没发生，这条预期没有结果）

一句话：**验证过但没通过 = FAIL；连验证的机会都没有 = BLOCKED。**

```powershell
# 卡住时这么做（status 按上面三行选；bash 跑，唯一允许用 bash 的就是 session.py）
& "<toolkit>\.venv\Scripts\python.exe" "<toolkit>\tools\session.py" finding `
  --status FAIL --event-id <最后一次证据> `
  --expect "<这条预期>" --actual "无法验证：<卡在哪>；已尝试 2 次（<试过什么>）"
```

**为什么记下来继续走而不是停下来等：**

```
停下等人会把整批卡死。记成 FAIL/BLOCKED，这批继续跑完，最后由人在报告里统一看卡在哪 —— 效率高得多。
```

> ⚠️ **实测代价**：一条用例为了验「结束进程后提醒能不能到」，
> 连着建了 6 个事件（A~F），前 5 次都白做 —— 40 分钟。
> 如果第 2 次就记下来走人，能省 30 多分钟。

> 例外：用户主动中断（自己喊停、或者关了窗口）。这种情况直接 `finish` 收尾，
> 在 summary 里写明「用户手动停止：…」，**原地保留现场**（不清理、不还原）。
> 但这不是你的决策 —— 是用户做的。

## Session 判定规则（结论只在 finish 时写）

`running` 是**中间态**，不是结论；结论只有四种：

| 情形 | 结论 |
|---|---|
| 全部预期都验到且符合 | **PASS** |
| **验证发生了但没通过**：预期不符 / 预期验不到（试了 2 次、控件不存在、点了没反应） | **FAIL** |
| **验证没发生**：预置条件造不出来 / 入口进不去 / 页面打不开 / 被测或关联包崩溃(ANR) / 用户手动终止 | **BLOCKED** |
| 工具层/环境异常导致会话未完成执行（断连等） | **ERROR** |

"部分符合"也是 FAIL —— 在 actual 里写清哪条符合、哪条不符即可。

**分界线就一条：验证这一步到底发生没有。**
- 发生了、结果不符或验不到 → **FAIL**（控件不存在、点了没反应都是观察结果，写清实际什么样）
- 没发生（被预置、崩溃、进不去挡在门外）→ **BLOCKED**

`finish` 会校验断言与证据的一致性，不符合就拒绝提交（会话保留，改完可以再提交）。
**已提交的会话不能重复 finish。**

> 工具只检查「已记录断言之间是否自相矛盾、证据引用了没有」，
> **不保证用例的所有预期都被覆盖** —— 逐条实际验证仍是你的事。

**冒烟 / 探针会话别用 `finish` 收尾，直接 `abandon`。** `finish` 写进去就是结论，
而 `abandon` **不覆盖已提交的结论**（`session.py` 会回你「会话 #N 已是结论态，
abandon 不覆盖已写的结论」）—— 所以先 finish 再想作废，来不及了，通过率永久多一条
假记录。跑完自检、装完机验证这类「不是用例」的会话，正确做法是趁它还是 `running`：

```bash
& "<toolkit>\.venv\Scripts\python.exe" "<toolkit>\tools\session.py" abandon `
    --id N --reason "作废：装机冒烟，不是用例"
```

### ⚠️ 用例写法：「字段（如…）」「（最多N）」这类括号**是要验的规格**

用例常这么写：

```
<某字段>（如 1～20，最多 24）
<某字段>（共 10 种）
<某字段>（第 x～x 项）
```

**括号里写的是这个字段的取值范围和上限 —— 那是规格，要验。**

```
① 选项全列出来（chip / 列表）
   → 打开弹层，数一遍最大到几

② 滚轮选择器（只显示当前值的小窗口）
   → 拨到边界（一直拨到不能继续 / 回绕），然后取消退出不改值
```

**实际范围 ≠ 用例写的范围 → 照实判 FAIL**，actual 写清实际看到的范围就够了。

> 别为了让数字对上，跑去改别的字段造条件 —— 那测的就不是这个字段了。
> 这种情况通常是**用例本身需要修正**（比如两个字段有关联但用例没写），
> 你按实际报 FAIL，就是给用例作者提供了修正依据。

### ⚠️ 用例里的预期，**一条没验证到就不能判 PASS**

用例的每一条预期都必须**实际验到**（有 dump/OCR/截图证据）。
"步骤执行了但没看结果"、"入口当时没找到所以跳过" —— 这些都**不算验证到**：

| 情况 | 不能判 | 应判 |
|---|---|---|
| 试了但没验到（入口找不到试了 2 次 / 步骤做了没看结果） | ❌ PASS | **FAIL**（如实写"预期X未验证到"） |
| 根本没走到验证（预置造不出来 / 入口进不去 / 崩溃） | ❌ PASS | **BLOCKED** |
| 用例本身的步骤与实际界面不符（如描述的入口不存在） | ❌ 默默跳过 | **FAIL**，并在报告写明差异 |

**"没验到"和"验到了且通过"是两回事** —— 前者一律不算通过。

### ⚠️ 判「弹窗 / 页面」：看截图，一眼的事

**弹窗** = 一块卡片浮在当前页上，四周看得到原页面、背景变暗。
**整页** = 铺满屏幕，没有被"盖了一层"的感觉。

> activity 名带 `Activity`、dump 里没有 `Dialog` 字样 —— **都不代表不是弹窗**。
> 别拿这些去反驳用例。

## 知识卡：只读，写不了

知识卡（`assets/knowledge/<包名>.md`）和路径卡（`assets/knowledge/paths/<包名>.md`）
**都不由你写**：

| | 谁写 | 你怎么用 |
|---|---|---|
| 知识卡 | **人**（用户手工维护） | `android_read_file(card="<包名>")` 读 |
| 路径卡 | AI 自动采集（`session.py paths` / `paths-apply`） | 同上，`card` 一次搜两张 |

**没有任何工具能让你改知识卡** —— 不用找，也不用试。

### 发现卡里写的和实际不符，怎么办

**写进 `--summary`，让主 Agent 报给用户。** 这是唯一出口。

```
finish --status FAIL --summary "……
另有一条与知识卡不符：卡里写「<引一句卡里的原文>」，
实际<你看到的现象>。
建议改成「<怎么改>」（可选）"
```

写清三件事，用户才好判断要不要改卡：

```
① 卡里原来是怎么说的（引一句原文）
② 实际是什么样（你观察到的现象）
③ 建议怎么改（可选，但很有用）
```

### 什么情况该报

```
✅ 卡里写的和实际不符（照卡做导致走错）
✅ 卡里没提，但这一步让你卡了很久

❌ 正常走通的流程（卡里说了，也照着走通了）
❌ 用例特定的数据（"测试A1"、"第9周"）
❌ 坐标 / 像素 / bounds（换机型就废）
❌ 「会话473 实测」这种（会话号对下次没用）
```

**别把 summary 写成流水账** —— summary 主要写这段用例的结论和现场状态，
卡不符只占末尾一两句，不要挤掉主结论。
