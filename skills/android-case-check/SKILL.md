# 用例够不够格跑

**单条派发前：10 秒，心算，不写脚本、不读文件、不调研、不查设备。**
**批量预筛：用户明确要求筛查整批时才读用例目录，只读，结论只在对话里。**

两种场景用**同一套判定口径**（下面的 1 → 6），别搞两套标准。

## 这个 skill 是干什么的

以前 case 写得模糊，靠执行的人临场把守：自己补全前提、自己决定什么算「正常」。
AI 执行没有这层默契，同一条模糊用例每次补得不一样，结论就飘。
**准入的作用是在派发前把描述问题挑出来**：描述模糊、预期不明确、需要拆分、
不适合自动化 —— 让用例写到「机器照着走就能判」再跑。
设备状态、服务可用性、运行时故障不是准入该预判的，交给执行侧如实记。

**职责边界**：准入只管到「派不派、提醒什么、不合格时怎么说」。
怎么派、执行侧记什么、跑完怎么回看记录 —— 由主 Agent 与执行侧各自负责，这张卡不写。

## 判断方法

先在脑子里过两个问题：

### ① 有步骤吗 —— 知道要做什么吗

能不能按顺序说出「先做什么、再做什么」。

```
✅ 「点右上角更多 → 选那个入口 → 点里面的第一项」
✅ 「走A-走B」
❌ 「测一下那个新功能」      → 做什么？不知道
```

### ② 有预期吗 —— 做完该看到什么，说得出来吗

**这是关键。** 每条预期要能落成一句「看到 X 就算过」。

```
✅ 「点「导入」→ 预期：进入选图页」
   → 能不能看到：前台切到选图页
   → 反证：没反应 / 弹别的

✅ 「点「完成」→ 预期：保存成功并回到列表页」
   → 能不能看到：页面变了
   → 反证：停在原地 / 报错

❌ 「界面显示正常」   → 什么算不正常？
❌ 「功能可用」       → 可用是什么样？
```

**更细一点的预期要好，但不是必须**：

```
好  「A 页面有「添加课程」标题，B 页面表单有 5 个字段」
可以「进入 A 页面，点 B 弹窗，弹窗里能改名称和颜色」
```

**说得出「什么算 FAIL」就够格，不必写到控件的粒度。**

## 准入判定：两层六类，固定顺序

| 顺序 | 层 | 类别 | 合格（放行） | 不合格（拦） |
|---|---|---|---|---|
| 1 | 基础准入 | **可执行**：有步骤吗 | 能按顺序说出「先做什么、再做什么」 | 只有目标 / 功能名，一个动作都说不出来 |
| 2 | 基础准入 | **可判定**：有预期吗 | 每条预期能写成「看到 X 就算过」，且说得出反证；涉及多项时列得出清单 | 没给预期；只写「正常 / 可用 / 良好」；或「所有 / 每一项」没列字段清单 |
| 3 | 基础准入 | **本机可验**：工具层够得着吗 | 结论落在屏幕可见的内容上（页面、文字、弹窗、跳转） | 结论落在声音 / 连接 / 硬件 / 成像 / 性能上；或要第二台设备、真实网络账号 |
| 4 | 语义筛查 | **描述模糊** | 步骤、前提、指代、条件能定出唯一走法 | 读不出唯一走法：主观词、口语指代、多分支混写；条件写「左右 / 按规定 / 国家规定的…」。**前提漏写但读得懂 → 不是这里，转隐含依赖提醒** |
| 5 | 语义筛查 | **需拆分** | 一条用例只有一条执行路径、一个终态 | 两个互斥前置、两个独立终态、一条断言捆绑多个要分别取证的独立事实 |
| 6 | 语义筛查 | **不适合自动化** | 过程依赖的东西本机可造、且在前提里写清了 | 写具体了、工具层仍做不到的（六类清单见下）→ 拦；**描述没写清 → 归类别 4，不归这里**；隐含依赖 → 只提醒 |

**按 1 → 6 短路，命中即停，只报命中的那一类。**
**六类全过才派发；任一类命中 = 硬拦，不派、不占设备、不产生执行记录。**
**唯一例外：隐含依赖只记一条提醒，不算命中、不参与短路、不停下等确认，其余都过就照常派发。**

一句话：1 + 2 = 能不能变成「点几下 + 看一眼」；3 + 6 = 看不见、造不出的东西不许猜；
4 + 5 = 这段话是不是只描述了**一条**能走通的路。

## 各类怎么判（拦 / 提醒 / 放行）

### ⛔ 类别 1 · 说不出步骤

```
「测一下那个新功能」「把这块弄好」   ← 只有目标，没有动作
→ 不派，问："先点哪个、再点哪个？"
```

**只有"一个动作都说不出来"才拦**；步骤糙、没分点、没写清入口，都不算。

### ⛔ 类别 2 · 没有预期

```
「跑一下 168」  ← 但对话里从来没给过预期
→ 不派，问用户："这条要验什么？做完该看到什么？"
```

### ⛔ 类别 2 · 预期说不出反证

```
❌ 「界面正常」「功能可用」「体验良好」
→ 不派，问："「正常」具体指看到什么？"
```

### ⛔ 类别 2 · 预期是个没边界的集合

**「所有」「每一项」「一一对比」「显示无误」「全部一致」后面没跟清单 → 拦。**

```
❌ 「修改某条目中的所有选项」「每一项信息与修改保持一致，显示无误」
   → 「所有 / 每一项」是哪些项？没列出来，就说不出「看到 X 就算过」的 X，
     也说不出反证。执行者只能自己补全清单，每次补得不一样 →
     同一条用例一会儿 PASS 一会儿 FAIL
→ 不派，问："要改哪几项、各改成什么、在哪个页面核对哪个值？逐项列出来"

✅ 已列清单就不拦：「把标题改成 X、开始时间改成 Y、提醒改成 Z，
   详情页逐项核对这 3 项」—— 集合有边界，能判
✅ 单一事实也不拦：「列表里的条目全部删除 → 列表为空」，一眼可判
```

**判据只有一条：能不能把要核对的项一条条列出来。** 列不出就是判不了，
不是「写得糙」。别拿「预期只有一句话」的反例把它放行 ——
反例说的是字少，这里拦的是集合没边界。

### ⛔ 类别 3 · 超出工具层能力（只能看屏幕，管不了硬件）

**工具层能做的只有：看屏幕、点按、输入、滑动、读文字。**

预期落在下面这些上的，**不派**，直接告诉用户「这条现在跑不了」：

```
❌ 声音   响铃 / 提示音 / 震动有没有响
❌ 连接   蓝牙、WiFi、蜂窝、NFC 的配对与连接
❌ 硬件   充电、电量、温度；光线、距离等传感器读数
❌ 成像   摄像头拍出来的画质（能进相机界面，判不了成什么样）
❌ 性能   帧率、内存、启动耗时
```

**例外：横竖屏不拦。** 虽然物理上转不了设备，但可以用命令模拟：

```
adb shell settings put system accelerometer_rotation 0   # 关掉自动旋转
adb shell settings put system user_rotation 1             # 横屏（0 为竖屏）
```

用例步骤里出现「切换到横屏」「横屏模式下打开」这类，子 Agent 用上面的命令做就行，
「横屏下显示正常」这类预期照样可判（看屏幕就是了）。不拦，放行。

### ⛔ 类别 3 · 本机造不出来

```
❌ 需要另一台设备做对端（蓝牙配对、跨设备同步）
❌ 需要真实网络账号（登录态、云端数据）
❌ 需要特定硬件（NFC、指纹模组）

✅ 「已有 XX」不算 —— 子 Agent 会现场做
✅ 需要清数据、重启 App 不算
```

### ⛔ 类别 4 · 描述模糊

**读不懂才拦**：类别 2 管预期（说不出反证 / 集合没边界），类别 4 管步骤、前提、指代、条件。
同一个词写在哪决定归哪类：「界面正常」写在**预期**里 → 类别 2；写在**步骤**里 → 类别 4。

```
❌ 「打开那个页面，按之前那样操作」      → 哪个页面？之前是哪样？
❌ 「界面正常 / 体验良好」写在步骤里     → 动作都没说清
❌ 一句里混了「有 X 走 A、没有 X 走 B」 → 到底走哪条？
❌ 「前 X 天左右」「根据国家规定 / 放票规定」「等一会儿」
   → 到底哪天、按哪条规则、等多久？
→ 不派，问："这条到底走哪条路？前提是什么？"
```

**前提漏写 ≠ 描述模糊**：前提段写了别的前置、步骤却依赖另一件没写的事，
或用例根本没写前提段 —— 只要还读得出唯一走法，就**不是类别 4**，
转类别 6 的隐含依赖：只提醒、照常派发。读不懂才归这里。

**模糊时间与条件属于描述模糊，不是「不适合自动化」**：
「距离某节日前 30 天左右」「根据某规定提醒」这类写法，
人能靠经验补全，机器不能 —— 请把具体日期 / 年份、具体规则、
以及「看到什么算过」写进用例。
写具体之后若仍需要工具层做不到的事，再按类别 6 判；**别拿类别 6 替描述模糊背锅**。

### ⛔ 类别 5 · 需拆分

**阈值：只有「一条用例塞了两条路」才拦。** 命中任一条：

```
❌ 两个互斥前置：「无 X / 有 X」，预期分别验空态和 X 存在时的行为
❌ 两个独立终态：一步之后既可能停 A 页也可能停 B 页，两条预期各管一个
❌ 一条断言捆绑多个要分别取证的独立事实（每件事都要单独看一眼才判得了）
→ 不派，给拆分建议：按前置 / 终态拆成 N 条，每条单一前置、单一终态
```

**和类别 2 的分工**：连「有哪些项」都列不出 → 类别 2（集合没边界）；
列得出清单、但要分别走不同路径 → 才是类别 5。

**典型**（脱敏）：

```
前提：无 X / 有 X
预期 1：若无 X，当前页面为空页面
预期 2：选一个 X 后进入编辑页
→ 拆成「无 X 验空态」「有 X 验选择」两条。
  本机造不出「无 X」的那一支，单独成条后再按类别 6 判 —— 别把整条说成跑不了
```

**互斥前置 ≠ 顺序两步**（别把能依次做完的用例拆开）：

```
❌ 前置段写「无 X / 有 X」→ 两个状态不可能同时成立 → 命中 5
✅ 步骤 1「把某开关设成 A，验预期 1」、步骤 2「再设成 B，验预期 2」
   → 编号列着、能依次做完、预期各自对应 → 一条用例跑得完，放行
```

**判据：一次执行能不能把两条路都走完。** 走得完就不拆。

**同一终态下的多个事实不拦**（见下节），别把写得细当成要拆。

### ⛔ 类别 6 · 不适合自动化（硬拦项）

类别 3 管「预期本身落在工具够不着的东西上」，类别 6 管「**写清楚了、工具层仍做不到**」。

**写具体了仍做不到的，拦：**

```
❌ 需人工或物理介入（插线、按实体键、人工审核）
❌ 跨应用不可达入口（要跳到本机没有的第三方应用）
❌ 依赖外部账号登录态 / 真实网络账号
```

**与类别 3 重叠的按短路先报 3**（要第二台设备、要读硬件 / 传感器值、要听声音），
这里不重复判、也不重复报。

**描述没写清的一律先归类别 4，不归这里：**

```
❌ 「前 X 天左右」「根据某规定」「国家规定的…」「等一会儿」
   → 不是不适合自动化，是描述模糊，按类别 4 要求写具体
```

**判据：把措辞改具体之后，这条还跑不了吗？**
改具体就能跑 → 类别 4（要求明确表述）；改具体仍要做工具层做不到的事 → 类别 6。

**静态预判不了的，不拦**（运行时才发生，交给执行侧如实记 BLOCKED）：

```
✅ 崩溃 / ANR / 断连 / 记录通道异常 / 用户手动终止
✅ 服务当时恰好不可用（措辞里看不出来）
```

**横竖屏例外照旧不拦**（命令能模拟，见上面类别 3）。

### 本方案的能力边界：六类不适合自动化

工具层只有**看屏幕 / 点按 / 输入 / 滑动 / 读文字**（见类别 3），
一条 ADB 通道同时负责观察和写记录（`act` / `observe` / `finding` / `finish`）。
**证据不可稳定观测、动作做不到、或动作会打断这条通道** —— 写清楚了也不适合自动化。
类别 3 管「结论落在不可观测的东西上」，这里管「过程做不到 / 会破坏通道」。

| # | 用例文本里出现 | 本方案为什么跑不了 |
|---|---|---|
| 1 | 音质、色彩观感、触感、动画自然度、流畅 / 卡顿感、是否顺滑 | 屏幕文字里没有可判反证；A/VLM 初筛也给不出稳定 Oracle |
| 2 | 插拔 SIM/SD/USB、充电、翻转、指纹、手写笔、实际拍照成像、传感器读数 | 没有机械臂 / 治具 / 专业仪器 |
| 3 | 蓝牙耳机、投屏、外设互联、手机与 PC 互联、换新机、需配合机收发 | 依赖第二台设备 / 外设 / 多端状态同步 |
| 4 | ADB 断连、重启、关机、恢复出厂、触发重启的配置、低电模式与 USB 冲突 | 观察与记录通道被测试动作打断，拿不到完整记录 |
| 5 | 低电 / 满电 / 满内存、弱网 / 无服务 / 屏蔽箱、长期运行、特定账号或 VPN | 条件构造时间长，或构造过程破坏自动化运行条件 |
| 6 | 三方应用升级、在线内容变化、广告弹窗、上传下载进度、动态轮播 / 视频页 | `observe → 决策 → act` 之间页面会漂移，锚点与取证不可复现 |

**第 7 类「用例质量与 Oracle 不明确」不归这里**（Oracle = 判定依据）：
步骤缺失、预期缺失、描述笼统、只写「检查某某菜单」、校验范围矛盾、
用例过长、结果无法验证 —— 那是类别 1 / 2 / 4 / 5 的活，
按描述类要求写具体，别拿工具能力当借口。

**边界：**

```
✅ 只是没声明素材 / 服务来源 → 隐含依赖，只提醒
✅ 明写要测上表这些对象 → 类别 6 硬拦
✅ 崩溃 / 断连 / 服务当时不可用 → 运行时才发生，不预判
✅ 横竖屏、日期时间等命令能模拟的状态 → 不拦
```

**「无控件 ID」不算**：定位走屏幕文字 / desc / 结构，不依赖 rid；
只有结论要读底层状态（电量数值、传感器读数）才算不可观测，归类别 3。

### ⚠️ 类别 6 · 隐含依赖（只提醒，不拦）

**这两类是提醒，不是命中：**

```
⚠️ 隐含本机资源：措辞里有「固定素材 / 选择已有… / 已有的某条目」，
   但前提段没声明这份素材从哪来
⚠️ 隐含外部服务：措辞里有「解析 / 导入 / 同步 / 云端 / 服务端返回」，
   但前提段没声明服务可用
```

**不算隐含依赖（别误伤）：**

```
✅ 验证目标不依赖它：措辞里的导入 / 解析只是「到起点的路」，
   且步骤里另有可替代路径；预期验的是后续动作（弹框、删除、取消）
✅ 步骤里已写明怎么造出该状态，且预期不要求该服务本身成功
```

**判据：把这份依赖抽掉，用例的预期还验不验得成？** 验得成连提醒都不给。
仍要提醒的例子：预期本身写「导入成功后新建…」「解析流程正常完成」→
抽掉就验不成，提醒一句，但**照常派发**。

**同类用例写了「网络 / 数据可用」、本条没写却走同一流程 → 是漏写前提的信号。**

**这类前提漏写不算类别 4**：用例仍读得懂，只是少写了依赖；
派发照常、提醒一句，别按描述模糊硬拦。

**提醒口径**：只说「这条可能依赖 X，执行时留意」，
**不说「设备上没有 X」「没有网络」，不去查，也不要求用户确认**：

```
❌ 不查设备、不查网络、不 ping、不看 WIFI 状态
❌ 网络层通不代表解析服务可用 —— 实测 WIFI 已连、公网能通，
   解析照样报「需要连接网络」。查了也预判不了，别拿它当放行依据
❌ 不停下等回复、不给三选项、不把提醒写成拦截
```

提醒写进派发 `prompt` 的第 5 项，回给用户的话里一句话带过；
用例照常派给 android-executor，产生正常的执行记录。

## 不拦反例（别把糙用例误判成不合格）

**下面这些照旧放行**，不是「不许跑」的理由：

```
❌ 步骤写得糙、没分点
❌ 预期只有一句话
❌ 同一终态下一条预期含两件事（如「进入 A 页，标题是 B」）—— 一件事，不用拆
❌ 步骤里编号写「先设成 A 验预期 1，再设成 B 验预期 2」—— 顺序两步，不是互斥前置
❌ 步骤数和预期数略有出入
❌ 不知道这功能在哪、怎么点
❌ 步骤里的导入 / 解析只是到起点的路，另有可替代路径，预期验的是后续动作
❌ 不确定能不能做成
❌ 前提和步骤看起来有点矛盾，但仍能定出唯一走法（子 Agent 现场处理）
```

**对照类别 4**：前提漏写、没写前提段、前提段写了别的前置 —— 只要还读得出
唯一走法，就不是描述模糊，按隐含依赖只提醒。

**对照类别 2**：同一终态下一条预期含两件事 → 放行；但写成「所有 / 每一项」
却没列字段清单 → 命中类别 2（集合没边界，不是写得细）。

**对照类别 5**：一条预期含两件事，若是**同一终态下的两个事实** → 放行；
若是编号列着、能依次做完的两个步骤 → 也放行（见「走得完就不拆」）；
只有前置段互斥、或一步之后到不了另一终态，才命中需拆分。
分不清且**项能列出来**才放行。

**对照类别 6**：用例明写了「需要联网 / 数据可用」，那只是描述前置，不拦；
「前提漏写、步骤却依赖」→ **只记提醒、不拦**（隐含依赖不算命中）；
条件写「左右 / 按规定 / 国家规定的…」→ 归类别 4 描述模糊；
只有写具体了、工具层仍做不到的（人工介入、跨应用入口、外部账号）才归类别 6 硬拦。

## 用例从哪来

**用户贴的优先级最高** —— 他刚说的就是最新的；没贴才去看用例库。

用例库是 `<target>/assets/cases/<包名>/` 下人写的 `*.md`（前提 / 步骤 / 预期）。
批量预筛只读这些 md；跑过之后沉淀的 `_steps.yaml` 只存机械跳转，
**不是筛查依据**（它的文件头自己写着「前置条件、造数据、判定都不在这里」）。

```
用户：「跑 176。这是用例：步骤 1... 2... 预期 1... 2...」
→ 就用这段

用户：「跑 176」（没贴，但文件里有）
→ 读用例库里那条 md

用户：「跑 176」（文件里也没有）
→ 问："176 的步骤和预期是什么？"
```

---

## 批量预筛（只读，不落盘）

**只有用户明确说「筛查整批 / 哪些用例会卡」时才做**，不是派发前的默认动作。

```
1. 列出 `<包名>` 用例库目录下所有 `*.md`
2. 只读每份 md 的「前提 / 预置条件 / 步骤 / 预期」，用上面 1 → 6 同一套口径逐条过
3. `_steps.yaml` 不是筛查依据 —— 它只存上次实测的机械跳转，
   文件头自己写着「前置条件、造数据、判定都不在这里」
4. 同类用例里其他条写了「网络 / 数据可用」而本条漏写 → 前提漏写的信号
5. 对话里只给清单：可跑 N 条（其中附提醒 K 条）/ 待改 M 条；
   附提醒的给「编号 + 缺哪份依赖 + 提醒文案」，不计入待改、仍可跑；
   待改的逐条给「编号 + 命中类别 + 原文证据 + 补齐建议」
```

**不做：**

```
❌ 不写报告文件、不给用例打标、不改用例 / 知识卡 / 界面
❌ 不建 session、不查运行库、不查设备、不查网络
❌ 不把全文塞回对话，只给结论行
```

**批量筛查 ≠ 批量派发**：清单是给人看的，用户点名哪几条才逐条走派发流程；
派发时对那一条按**最新原文**重新判一次（他可能刚改过）。

> 筛查只看人写的 md；执行时怎么读落点不归这张卡管。

## 派发

过关就派给 `android-executor`。**`prompt` 里放：**

```
1. 用例原文（原样贴，一个字都不改）
2. 设备 serial：<serial>
3. 被测包名
4. 工具层路径：<target>
5. 你的提醒（如果有）：只写与执行有关的客观事实，
   比如"用例未声明所需素材来源，执行时若造不出前置状态就如实记 BLOCKED"
```

**`prompt` 里不放：**

```
❌ 你拆好的步骤
❌ "先做 A 再做 B" 的方法指导
❌ 历史跑过几次
❌ 你猜的技术方案
```

原文改了，执行时记的预期就对不上用户的原话了。

## 拦截结果：固定输出三件事

拦下之后，回给用户的话必须包含：

| 要素 | 内容 |
|---|---|
| ① **命中哪一类** | 1 → 6 里的哪一类，写类别名 |
| ② **证据** | 引用用户原话的那一段，一个字都不要改 |
| ③ **补齐动作** | 一句能照抄的追问 + 一个具体到能判的例子；需拆分给拆分建议 |

模板：

```
❌ 不派发：<命中哪一类>

你给的是：
  「点右上角更多 → 选那个入口 → 点里面的第一项」

这段只有步骤没有预期 —— 做完这串该看到什么？
比如「进入选图页」这样的。你说清这个，我就能派。
```

**类别 2 / 4 / 5 / 6 的补齐动作怎么给：**

| 命中 | 说什么 |
|---|---|
| 2 预期没边界的集合 | 请逐项列出要改的字段、改动值和核对位置；**不替用户列清单** |
| 4 描述模糊 | 指出哪句读不出唯一走法，请补清前提 / 指代 |
| 5 需拆分 | 给按前置 / 终态拆成 N 条的建议；**不替用户决定怎么拆** |
| 6 硬拦项 | 说清哪一项造不出 / 到不了，请补清或改用例 |

**隐含依赖不走这一节**（只提醒，照常派发）：

```
⚠️ 提醒：<缺哪份依赖>
用例里「<原话片段>」没在前提声明 <X> 的来源 / 服务可用性。
这条照常派发；执行时若造不出前置状态，就如实记 BLOCKED，不要说成功能有问题。
```

不给选项、不等回复、不写「不派发」。

**拦下就是拦下，这些附带动作一律不做：**

```
❌ 不派发（不给 android-executor，不占设备）
❌ 不编预期填进去 —— 编出来的预期是假的，跑出假 PASS 比报"判不了"更糟
❌ 不建 session、不写 test.db、不产生 run_history —— 被拦的用例没有执行记录
❌ 不改用户的用例文件 —— 补内容是用户的事
❌ 不查设备、不查网络、不替用户确认资源在不在
❌ 不说成"用例失败 / 功能有问题" —— 是这段描述判不了，不是被测 App 有缺陷
❌ 不"先跑跑看" —— 没有预期跑出来的结论没人能信
```

**同时命中多类**：按 1 → 6 顺序**只报前一项**。补齐一项再看下一项，
一次抛多个问题用户不知道怎么答。**隐含依赖不算命中**，只另外附一句提醒，
既不影响短路，也不改变「其余都过就派发」的结论。

## 改完再进来：重入闭环

用户补了一句 / 改了文件之后，**从头再判一次**（单条仍心算）：

```
用户补了内容
   ↓
按最新说法重新过 1 → 6（不继承上次"已拦 / 已放行"的结论）
   ↓
   ├── 六类全过 → 立刻派发（提醒照旧带着）
   └── 还有命中 → 只报那一类，回到上面的模板
```

**重入时按这几条处理：**

| 情况 | 怎么做 |
|---|---|
| 用户在对话里补了预期 / 前提 | 以**这段为准**，覆盖先前版本；不回头读文件 |
| 用户说「我改了文件」 | 这时才读 `assets/cases/<包名>/...`（单条筛查里唯一允许读文件的场景；批量预筛见专门那节） |
| 用户按类别 5 拆成了几条 | **每条单独重判**，一条不过不拖累其他条 |
| 隐含依赖的提醒 | **不需要用户回复**；若他主动补了前置说明，按最新原文重判一次并去掉该提醒 |
| 用户只补了一半 | 只判补齐那部分；仍不合格就继续报，不降级放行 |
| 补的预期仍落在类别 3 / 6 硬拦项 | 直说「这条现在跑不了」；不许凑一个"屏幕上能看"的替代预期来过关 |
| 同一条被拦 ≥2 次仍没补齐 | 停下给三个选项：① 补内容 ② 换写法 ③ 先不跑。**不要自己替他选** |
| 用户不补、改问别的 | 这条停在拦截态，不自行推进；他再提「跑 176」就再判一次 |

**重入成功后派发**：`prompt` 里贴**用户最新那段原文**（不是文件旧版），
并加一句"这是修订后版本，第 N 条预期是新增的" —— 子 Agent 据此逐条记 finding。
拦截期间没有产生任何记录，所以这次派发就是这条用例的**第一次**执行。
