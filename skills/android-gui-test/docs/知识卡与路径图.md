# 知识卡与路径图

> 需要时读。**只在要查卡、写卡的时候看**。
> 里面是：两类资产的分工 · 路径图怎么用 · 知识卡怎么写 · 视觉通道。

## 两类资产，分工明确

| 资产 | 位置 | 记什么 | 谁维护 |
|---|---|---|---|
| **知识卡** | `assets/knowledge/<包名>.md` | **坑、行为规律、控件特征**（人类会记住的经验） | 人 / AI 精炼 |
| **路径图** | `assets/knowledge/paths/<包名>.md` | **「我在哪 → 认什么锚点 → 点了去哪」**（机器该记的结构） | 执行中自动采集 + 人工校正 |

`assets/knowledge/_system.md` 是跨 App 的**系统界面**兜底卡，前台包名不在任何 App 卡时读它。
`assets/knowledge/_template.md` 是新建卡的模板。

> **为什么要分开**：知识卡只留精炼经验，避免无限膨胀；路径记结构，量大且易变，
> 交给自动采集。混在一起会让卡又长又难检索。

## 路径图：一张**有穷的节点图**

**不记步骤序列、不记坐标**，只记三件事：

```
节点（落脚点，我在哪）──[锚点（我认得出什么）]──→ 节点（去哪）
```

- **节点**：页面 / 菜单 / 弹窗都算，**不区分 Activity 还是 Fragment**
  （App 内部怎么组织与操作者无关）
- **锚点**：屏幕上**认得出的东西**，用**三要素**描述（见下）
- **边**：从本节点出发，点某个锚点会到哪个节点

### 为什么是"图"而不是"一条线"

**路径是有穷的** —— App 的落脚点就那么多（本 App 约 13 个），可穷举。而现实里：

- **同一对起止点常有多条路**：进「课程表基本信息编辑页」既能从空态页
  「手动创建」（1 步），也能从周视图绕「课程表设置 → 点课表行」（3 步）
- **一个节点有多个出边**：周视图既能「导入课程表」，也能「课程表设置」

所以画成**节点 + 出边表**，而不是线性链路。

### 节点命名：`页面名-形态`

同一个 activity 可能有多种形态，**名字分开了才检索得到**：

```
课程表页-空态      认出: 「还未添加课程表」
课程表页-周视图    认出: 顶栏 desc「导入课程表」
                    ↑ 两者 activity 相同（TimetableActivity），靠锚点区分
```

### 怎么用（执行前先定位）

```
1. 认自己在哪 → 看 activity + **屏幕上有什么锚点**，对照节点索引
2. 检索       → grep 卡里 `## <节点名>` 那一节
3. 找出边     → 表里「→ 去向」就是要去的节点名
4. 点过去     → 按锚点走定位降级链
```

> ⚠️ 卡里的 `nodes` 字段就是**节点索引**（供第 1 步用），
> 不必整卡读 —— 认准节点名后只 grep 那一节。

### 定位降级链：rid → desc → text → 现场坐标

按稳定性**依次试**，命中即用：

| 顺位 | 线索 | 稳定性 | 说明 |
|---|---|---|---|
| 1 | `rid`（resource-id） | 最高 | App 小改版/换设备基本不变 |
| 2 | `desc`（content-desc） | 高 | 图标类控件的语义名 |
| 3 | `text` | 中 | 改文案才失效 |
| 4 | 现场坐标 | — | **不进卡**，每步现场派生 |

**都不中才算失配**（失配再现场探索并更新卡）。

> ✅ **实测对比**（TB522FU / 9.0.0.110 与 TB323FU / 9.0.0.83）：
> 两台设备的 rid / desc / text **完全一致**，只有坐标不同
> → 换设备时**只需现场重新派生坐标**，锚点表照用。

**锚点表格式**（四列；`—` = 实测该项为空，不是"没查"）：

```markdown
| 锚点（认得出就行） | rid | desc | text | 去向 |
|---|---|---|---|---|
| 右上角「更多」三个点图标 | `iv_more` | — | — | 菜单 |
| 顶栏「导入课程表」 | `action_curriculum_table_import` | 导入课程表 | — | 导入方式弹层 |
| 菜单项「课程表」 | `item_title` | — | 课程表 | 课程表页 |
```

> ⚠️ **共用 rid 必须靠 text 区分**：四个菜单项 rid 都是 `item_title`；
> 所有缩略图 rid 都是 `icon_thumbnail`。
>
> ⚠️ **图标类锚点常 desc/text 全空**（如 `iv_more`、`action_add_all_event`）
> → 只有 rid 一条线索，rid 变了就得现场重认。

> **同一 activity 多形态**：不靠 activity 判断，靠**屏幕上有什么锚点**判断。
> 例：课程表页空课表时有「还未添加课程表」，有课表时顶栏有「导入课程表」。

**为什么这个模型耐用**：它记的是「**要进课程表就去首页右上角找更多**」——
人类就是这么记的，App 小改版也不影响；而步骤序列一改就废。

> ⚠️ **自动采集只覆盖"页面级跳转"**（点击前后 activity 变了才算一条边）。
> **弹层/弹窗的锚点采集不到** —— 而它们恰恰最容易错
> （`android:id/button1` 在多处复用、菜单项共用 `item_title` 要按文字分、
> 时间弹层是 Canvas 自绘根本没有节点）。别以为多跑几轮路径图就自动全了。

### 同 rid 多态：路径图必须显式标注

**一个 rid 可能对应多个不同含义的控件** —— 光凭 rid 不知道点的是什么。
这种锚点必须在路径图里**显式标注**，否则就是埋雷：

| 类型 | 例子 | 怎么判 |
|---|---|---|
| **文案随场景变** | `android:id/button1` = 删除 / 完成 / 确定 | **必须看 text** |
| **同 rid 双态** | `action_schedule` = 编辑（普通）/ 取消（多选态） | 看 text |
| **多个同类共用** | `item_title`（4 个菜单项）、`checkbox_select`（每行）、`iv_arrow`（每小节） | 按 text；无文字的**按行序** |
| **完全无文字** | `icon_thumbnail`（照片缩略图） | 只能看图按位置选 |

**规则**：

- 这类锚点在**锚点行就地标注** `⚠️多态`，并在路径图**开篇单独一节**汇总（便于一进来就看到）
- `button1` 最危险 —— 它出现在**所有系统弹框**里，点错就是"确认了不该确认的事"
- **无文字的多态锚点**（`checkbox_select`/`icon_thumbnail`）**点完必须回读状态确认**
  （如勾选的 `checked`），**不能假设点中了**

> 真实教训：某次勾选 `checkbox_select` 点了 3 次才成功（前两次点空），
> 导致后续步骤白跑一遍。**点完回读状态**本可以立刻发现。

### 自动整理：机器出草稿，人只做确认

**人工整理太费劲**，所以边是**自动整理成草稿**、**人确认后**才写入：

```
用例跑完（finish）→ 自动采集 → storage/pending_paths.md（待确认草稿）
                                   ↓ 人看一眼
        & "<toolkit>\.venv\Scripts\python.exe" "<toolkit>\tools\session.py" paths-apply [--only 1,3]
                                   ↓
                     写入路径图「## 自动采集的边」
```

**草稿长这样**（已经归成**节点名**，不是裸 activity）：

```markdown
1. **菜单（弹层）** --[text=课程表]--> **课程表页-空态**
2. **课程表页-空态** --[rid=btnCreateManually]--> **课程表基本信息编辑页**
```

**怎么归到节点名的**：

1. 路径图每个节点带一行机器可读的 **`识别键`**：
   ```markdown
   ## 课程表页-空态
   - **activity**: `.timetable.display.TimetableActivity`
   - **识别键**: `text=还未添加课程表` · `rid=btnCreateManually`
   ```
2. 每次 `act` 落库时**顺带存一份屏幕身份签名**（页面上出现过的 `kind=value` 短串）
3. 整理时用签名去匹配各节点的识别键，**命中最多者**即该节点

> ⚠️ 识别键必须**实测填写**（从 dump 抄），不能猜 —— 它是自动归属的唯一依据。
>
> 一个都不命中时**返回空**（宁可归不出，也不乱归）。

**为什么写入"自动采集的边"而不直接写进各节点**：
人工整理的节点表带 desc/text 与 ⚠️ 提示，质量更高；自动边混进去反而降质。
人看过草稿后，可自行把高频边**手抄进对应节点**。

## 知识卡：写卡规范

### 第一原则：设备无关

我们会在**不同机型**上跑。所以卡里：

| ✗ 不写 | ✓ 要写 |
|---|---|
| 坐标、bounds、行距、列 x、屏幕尺寸 | resource-id、content-desc、文案 |
| "第 N 个箭头"、"点右下角" | 行为规律、坑、判定依据 |

**理由**：数值型实测值换个机型/方向就失效，**留着就是误导**。
需要标定时写"**怎么标定**"，不写标定结果。

> 真实教训：卡里记着 `TB323FU / 3040×1904`，实际设备是 `TB522FU / 2560×3840`，
> 所有坐标类内容一次性作废。

### 第二原则：标题 = 检索键

AI 拿到的索引就是各卡的 `##` 标题。标题要能被**交互类型词**搜到：

```
✓  ## 弹窗-首次启动三连    ## 时间选择器-双滚轮    ## 坑-清数据会清掉备份
✗  ## 首次启动的三个弹框（实测 2026-09-11）        ← 带日期
✗  ## 一些踩坑记录                                  ← 叙事式
```

标题里**不要带**日期、用例号、构建号。

### 第三原则：只写"会让人做错或重探"的

- 一条经验一行结论 + 一行依据；过程叙事不进卡
- **过时条目直接删**，让体积收敛
- **"入口在哪"写进路径图**，知识卡只留坑与行为规律

## 查卡

- **路径图**：先看自己落在哪个落脚点 → 找锚点 → 点它
- **知识卡**：按交互类型词检索，**只读命中小节**

> `session.py start` / 首个 `android_observe` 会返回 **`knowledge_hint`**：知识卡路径 + 小节索引。

## 沉淀四问（写进卡之前过一遍，全过才留）

1. **换设备 / 换方向还成立吗？** 不成立就不要写
2. **下次会来搜这个词吗？** 搜不到的写了白写；把词补进标题
3. **不写会做错或重探吗？** 常识/显然推论不进卡
4. **是"结构"还是"经验"？** 结构（入口、rid、连接）→ 路径图；经验（坑、规律）→ 知识卡

# 视觉通道（android_vision）

> SKILL.md 的附录。**只在需要工具级视觉断言时读**。

## 定位

**对话内执行时，优先用 `android_vision` 工具**——它直接看截图的像素，判颜色/图标/置灰这些 OCR 拿不到的东西。
`vision.py` 是同一能力在**无对话场景**（批量回放、CI 脚本）下的入口，走 bash。

```powershell
& "<toolkit>\.venv\Scripts\python.exe" "<toolkit>\tools\vision.py" --image <png> --prompt "按钮是置灰的吗？回答并给依据"
```

配置在 Web 测试台「视觉模型」页维护，Key 只存 `storage/vision.json`（不入库）。

## 什么时候才需要视觉判断

UI 树（nodes）能表达的，**一律不要用视觉**：

| 目标 | 用什么 |
|---|---|
| 界面是否打开 / 进入了哪个页面 | `activity` 字段 |
| 某个控件是否存在、文字是什么 | `full=true` 的 nodes |
| toast / Canvas 自绘文字 | `android_read`（OCR） |
| **置灰 / 颜色 / 图标点亮 / 视觉样式** | 才需要看图或 vision |

> 视觉模型又贵又慢，且偶发调用失败会把"可见即达成"的目标误判成未达成。

## 结论口径

视觉输出是**辅助判据**，PASS/FAIL 结论仍需结合 dump / OCR 证据。

## 测试连接

Web 测试台「视觉模型」页有「测试连接」按钮，会用当前配置发一次真实请求
（一张 64×64 的小图，服务端要求宽高都大于 10），验证鉴权与模型可用性，并显示耗时与错误类型提示。
