关键决定 DESIGN CHOICE
04

为什么 AI 不直接 bash 跑 python

这是整套机制里最重要的一次转向 —— 早期就在 bash 里跑，天天翻车。

旧 bash 拼命令行

python tools/act.py tap --x 1782 --y 210 --via "rid=iv_more"
  • PowerShell 的引号、& 前缀、% 转义，每个会话都要白跑一轮
  • 中文路径与参数经 shell 编码，变成乱码再报「文件不存在」
  • 空字符串被吞掉 —— 想清空输入框，参数直接消失
  • cwd 不对就找不到脚本，还会在错的地方造出一个假库
  • 顺序全靠 AI 记；漏一步就证据不齐

今 原生工具 + stdin JSON

android_act(action="tap", x=1782, y=210, via="rid=iv_more")
  • 参数走 stdin 的 JSON，不经 shell 解析 → 引号、中文、空串原样到达
  • 工作目录固定指向工具层，产物落点不会漂
  • 每次调用就是一次取证：截图 + dump + meta 自动落盘
  • 参数有 schema 校验，传错名字立刻报错，不会静默走偏
  • 顺序由工具保证，AI 只需要决定「点哪」

角色 AGENTS
06

两个 Agent，一个管调度，一个管执行

主 Agent · android-tester

判断 → 派发 → 汇总

用户用自然语言说用例，它先判断这条能不能跑，再交给执行 Agent，最后汇总成一张表。

· 一次只派一个执行 Agent（串行，避免抢设备）
· 派完就结束回合，等系统通知，不 sleep 轮询
· 派发前先列目录核对文件名，不凭编号猜
执行子 Agent · android-executor

看 → 动 → 判 → 记

拿着一条用例上台，逐步操作并判定；卡住就记 BLOCKED 往下走，不阻塞整批。

· 只做用例要求的事，没写的一律不动
· 一次看全就判，判完不回头复查
· 同一目标最多试 2 次，不通就 BLOCKED

两段 persona 加上两份 SKILL.md 就是全部「作业指导书」—— 一个告诉 AI 怎么用工具，一个告诉 AI 什么算通过。

06

判定收尾

逐条 finding
session.py finish

android_act(action="tap", x=…, y=…, via="rid=iv_more", why="用例步骤3：打开菜单", expect="rid=item_title")

三个字段是硬要求：via 你是凭什么点这儿，why 对应用例哪一步，expect 期望落到哪 —— 工具自己拿这三样去核对落点，对不上当场告诉你。

session.py finding --status FAIL --expect "显示倒数模块" --actual "月视图空白" --event-id 10234

每条断言必须挂一个真实存在的事件 id，工具会回到库里核对这条事件属于本会话、证据文件真的在盘上。编不出来就写不进去。

纪律 ENFORCEMENT
08

纪律不写在提示词里，写在代码里

提示词会被遗忘、被折叠、被绕开。硬约束只有写在数据库那一层才算数。

① 断言必须挂真证据

db.py · add_finding
actual 不能为空；PASS / FAIL 必须有 expect 且至少挂一个事件；事件要属于本会话，证据文件要真的在盘上。

② 汇总必须和明细对得上

db.py · _check_summary_counts
summary 里写「8 PASS / 4 FAIL」，库里是 9 / 3 —— 直接拒绝收尾。

③ 知识卡不许写死东西

session.py · _KB_VIOLATIONS
8 条正则拦截：坐标、像素值、会话号、「应判 PASS/FAIL」这类判定权 —— 一律写不进去。

④ 判定口径只有四档

db.py · STATUSES
PASS / FAIL / BLOCKED / ERROR。没有 WARN，没有「待确认」—— 不符合就是 FAIL。

PASS验过且符合 FAIL验过但不符合 BLOCKED连验证的机会都没有（最多试 2 次） ERROR工具层异常
证据 EVIDENCE
09

每一步都留得下证据，事后能回放

storage/ ├── test.db 会话 / 事件 / 断言 / 判定 └── run_history/ └── 3f9c…/ ├── evidence/ │ ├── step01/ │ │ ├── shot.png 截图 │ │ ├── dump.xml 控件树 │ │ └── meta.json activity / 动作 / 耗时 │ ├── step02/ … │ └── step57_perm/ … ├── calls/ 每次工具调用的入参出参 └── timing/ 分阶段耗时

一次动作 = 一个证据目录

点完之后工具自己等画面稳定、截图、存控件树；AI 不需要记得「去存证据」，也就不会漏。

落点自动核对

传了 expect，工具就跑一遍断言，把 matched / missed 一起返回，点错了当场知道。

权限弹窗单独成步

点掉的每个系统权限框都记一步、留一张图，但截图不多拍一次 —— 复用本轮已有的那份。

沉淀 COMPOUNDING
10

跑得越多，下次问 AI 越少

两条沉淀线，都不靠人手工维护。

沉淀线 A

知识卡 · 人确认过的经验

「提醒触发时间 = 开始时间 − 提醒偏移」「进空课表只有空占位、没有加号图标」—— 只记确认过的事实和操作经验，不记坐标、不记会话号、不记结论。

assets/knowledge/<包名>.md
assets/knowledge/paths/<包名>.md

沉淀线 B

steps 路径 · 机器自己导出的路线

收尾时自动把「从哪来 → 点了什么 → 到哪去」导出成一条步骤路径，下次同一个 case 直接接着走，不必重新摸索入口。

assets/cases/<包名>/<用例名>_steps.yaml
start_from · step_count · 每步 via + expect

还有一条被动沉淀：每个会话的耗时、事件数、工具占比都进库， 哪类用例慢、哪一步耗时长，事后可直接查 —— 优化有依据，不靠感觉。

原则 PRINCIPLES
13

这几条是用删除换来的

01

不是共性问题，不改代码

为一条用例的怪现象给工具层打补丁，会让框架长满只服务一个 App 的临时代码。是 Case 的问题就改 Case。

02

判据必须是用户能感知的

判「是不是弹窗」看截图一眼，不靠 activity 名字；判「提醒生没生效」拉通知栏看，不靠读系统 alarm 列表。内部状态不等于用户看到的东西。

03

卡住就记 BLOCKED 往下走

同一个目标最多试 2 次，不通就记录原因并继续。不暂停等人工 —— 一停就卡死整批。

04

改流程前，先列出「记录必须仍然显示什么」

曾经为了少拍一张图，把「每个点掉的弹窗算一步」也一起删了，还报了「测试通过」。验证断言必须覆盖旧约束，不能只测新行为。
