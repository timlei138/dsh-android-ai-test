# 冷启动：起点由工具层负责

**复位是工具层自动做的，不用你操心。** 你只需要知道两条结论：

1. **默认只 force-stop（关进程），不清数据。**
   `pm clear` 只在用例明确要求「首次使用 / 首次授权」时才用 ——
   拿它当默认复位会清掉本用例要用的前置数据。
2. **起点由用例的 `preconditions` 决定**，不要自己另起一套
   （比如自己按 back 回到某个页面当起点）。

## 你会看到的三种"假失败"

这三种现象都**不是你的判断错**，是设备状态的问题。识别出来就能少绕弯路：

### 屏幕睡着 → 一切点击静默失效

症状：你点哪都没反应，屏幕上没有可点的东西，日志里全是"点了没变化"。

真相：设备休眠了，锁屏挡在前面。工具层会尝试唤醒，但如果**连续几轮
屏幕毫无变化、可点项异常地少**，就把它当成"设备可能没醒"来报，
不要硬找控件、不要连续点同一个点。

> 这是最容易误判成"模型不会用"的一类 —— 看起来是你的错，其实是设备没醒。

### 跨包浮层挡在前面

症状：被测 App 已经重启了，但屏幕上还是上一个 App 调起的框
（典型：点「从图库导入」调起的系统选择器仍在前面）。

真相：那个框不属于被测 App 的进程，关掉 App 动不了它。
**回 `home` 再重进 App** 通常能解决。

### 冷启动看起来做了，其实没做

不要相信"应该已经复位了"。**以你眼前这一屏为准**：
如果屏幕上明显不是 App 首页，就按"起点不对"处理（`home` 重进），
而不是假设复位已经成功、从中间某步硬往下走。

## 报错时你只需要做一件事

**看到任何原始报错，原样转述，不要自己分析、不要重试。**

这条不是客套。真实发生过：一个会话把"工具参数校验失败"读成了"环境路径故障"，
于是虚构出一条报错和一整套根因分析 —— **设备一次没碰，报告看起来很专业**。
