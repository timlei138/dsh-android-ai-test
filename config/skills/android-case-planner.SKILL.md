# Android 用例：拆解与派发（主 Agent 专用）

## 你的职责只有两件事

1. **拆解**：把需求变成结构化的 `steps` / `asserts` / `preconditions`
2. **派发**：交给执行子 Agent

**你不执行用例。** 主 Agent 调用 `android_case` 会被**代码直接拒绝**
（按 `delegationDepth` 判断，主 Agent = 0 → 拒，子 Agent = 1 → 放行）。
被拒了就改用 `subagent` 派发，别原地重试。

## 运行环境：只有一个 venv

排查"缺依赖 / 跑不起来"类问题时看这里：**整条链路只有一个运行环境**，
编排（langgraph/langchain）和设备依赖（adbutils/opencv/rapidocr）装在同一个
`.venv` 里。

- 位置：`D:\dsh\langgraph-poc\.venv`，由 `requirements.txt` 可重建
- **`assets/.venv` 不该存在** —— 存在说明环境又分家了，回归测试会失败
- 别按"编排 venv / 设备 venv"两套去理解报错：**只有一个 venv**，
  缺依赖就是这一个没装好

> 子 Agent 那边看不到也改不了这些（它没有 shell），所以环境知识只放这里。

## ★ 「打开 webui」指哪个

这个模式下说 **webui = 用例执行结果 WebUI（`http://127.0.0.1:8770`）**，
**不是** DSH 自己的对话界面。两者毫无关系，别混淆。

```
D:\dsh\langgraph-poc\start-webui.cmd          # 起服务 + 自动开浏览器（默认 8770）
D:\dsh\langgraph-poc\start-webui.cmd -Port 8771 -NoBrowser
```

- 零依赖、标准库；**重复启动不报错**，已开着只是把浏览器再指过去
- 页面上看：用例库 / 运行记录 / 断言结果（代码判还是模型判）/ 自动化率 /
  动作时间轴（含截图）/ 视觉模型配置
- 回答"上次这个用例过没过、这次为什么变了"就靠它（历史在
  `assets/storage/runs.db`，每次运行带 YAML 快照）

开服务需要你启动进程。**别自己去猜 DSH 的端口或界面** —— 这个模式下的
webui 就是上面那个测试结果界面，不是 DSH 自己的对话界面。


## ★★ 铁律：不许写 Python 脚本去探测页面

**找元素、验证元素，一律走执行器（派子 Agent 跑）。别自己写脚本 dump XML。**

你有 shell，**技术上写得了** —— 所以这条得靠你自己守住。

用户多次实测的结论：
- 脚本写错就得改，改完再跑，**一轮几分钟** —— 比直接观察效率低得多
- 脚本里写死的字段是**猜的**，跟执行器真正用的判据（`landing` / `check`）不是一回事
- 拿脚本"验证过"的结论去写 YAML，等于把猜测固化成判据

拆解需要的设备事实（界面长什么样、控件 rid 是什么），要么来自已有 YAML / 知识卡，
要么**派子 Agent 跑一次观察**，要么问用户。别自己先探一遍。

## 第一步：先看有没有沉淀好的用例

**优先复用，不要重新拆。** 已经验证过的用例比现场拆的可靠得多
（里面有跨版本踩出来的坑、验证过的落点判据）。

用户说"跑 168"时，用编号去匹配文件名：

```
glob("**/storage/cases/*168*")        # 优先：按编号找
glob("**/storage/cases/*联想日历*")   # 只知道 App 名时
glob("**/storage/cases/*.yaml")       # 都不确定就列全部
```

- **命中 1 个** → 直接派发，`case_name` 传名字片段（如 `"168"`）
- **命中多个** → 把候选列给用户确认，**别自己挑一个**
- **命中 0 个** → 走第二步现场拆解，**并且拆完必须入库**（见下）

### 库里没有 → 拆完要入库，别只在内存里跑一次

用户原话：「后面 plan 的过程中如果这是个新的 case 就要加入到数据库」。

"这次能跑通"不算交付 —— 下次再问同一条用例，还得从头拆一遍。
所以现场拆解完，先把它落成用例，再派发：

```bash
# 原始需求原话（用户给你的那几句话，原样存，不要加工）
curl -X POST http://127.0.0.1:8770/api/cases \
  -d '{"case_key":"190","title":"联想日历_190_xxx","raw_text":"用户原话..."}'
```

- `raw_text` **必须是用户的原话**，不要改写成你的理解 ——
  它是需求记录，以后判"这条用例当初要求什么"全靠它
- 编号已存在会返回 409：那就别新建，改用库里那条
- 入库后 WebUI 用例库就能看到，**不用再往 `D:\dsh\cal_cases` 放 txt 文件**
  （那两个目录只是最初的导入来源，不是用例的正主）

YAML 里 `confidence: verified` 表示已经跑通过多次，可信度高。

## 第二步（没现成用例时）：现场拆解

### 拆解产物长什么样

```json
{
  "case_id": "168",
  "title": "联想日历_168_图库导入入口",
  "package": "com.zui.calendar",
  "preconditions": [
    {"kind": "nav", "desc": "拉起 App 回到首页作为起点",
     "do": ["am start -n com.zui.calendar/.AllInOneActivity"]}
  ],
  "steps": [
    {
      "id": "s1",
      "do": "点右上角「更多」",
      "locate": {"rid": "iv_more"},
      "landing": {"activity": ".timetable.display.TimetableActivity"}
    }
  ],
  "asserts": [
    {"id": "a1", "desc": "进入课程表页面",
     "check": {"activity": ".timetable.display.TimetableActivity"}}
  ]
}
```

> ⚠️ **`do` 字符串和数组都收**（`"am start ..."` 或 `["cmd1", "cmd2"]`）；
> 多条命令必须用数组，否则会被当成一条。
>
> `locate` 和 `target` 是**同一个字段的两个名字**（加载器两个都收），
> 内联传参时写 `locate: {"rid": "..."}` 就行。

### `pm clear` 只在"首次使用"场景才用

用户原话：「不是每个用例都需要 pm clear。只有涉及到首次使用，
这种情况才清理。其他情况不需要清理。」

判断标准只有一条 —— **这条用例验的是不是"第一眼/第一次"的状态**：

| 用 | 不用（绝大多数） |
|---|---|
| 首启引导页、首次授权弹窗、初始安装态 | 日常操作流程（建课表、加事件、切视图…） |

**默认不写。** 想加之前先问：清掉数据后，我测的那个状态还在吗？
清不清都能测到 → **不该清**。

代价很多人没算到：**不可逆**（真实课表全没了），而且**可能让用例更弱**
（176 要验"空课表界面"，清数据只能得到"首次启动"，反而绕远了）。
起点靠 `kind: nav` + `assert_start` 保证就够了。

### `landing` 是质量的关键

**每一步都应该给 `landing`。** 没有它的步骤代码无从复核，
只能靠执行子 Agent 自己判断"到了没有" —— 那就退化回"靠模型自觉"。

⚠️ 技术上说，**没写 `landing` 的步骤不会报错**（子 Agent 说完成就算完成），
所以这是"你不给它就没人给"的地方。**漏写不会失败，只会悄悄变差。**

`landing` 是个字符串，最常用的两种判据：

| 判据 | 例子 | 说明 |
|---|---|---|
| `activity` | `.timetable.display.TimetableActivity` | 页面类名。**是子串包含匹配**：短名必须真的包含在完整名里 |
| `rid` | `btnImportFromGallery` | 控件资源 id |
| `text` | `图库导入` | 屏幕文字（代码只能子串匹配，**判不准，会交给模型**） |

多个条件用**逗号**（AND）或**竖线**（OR）。

> `asserts` 里的 `check` 是**字典**，能写的键更多（`permission`、`node_present`、
> `dialog_present`、`after_tap` 等）。完整清单读
> `references/permissions.md`，别凭印象写 —— 写了代码不认的键会被丢弃
> （报告里会打"不认识的判据键"警告，但那条断言就等于没验）。

### 拆解纪律（这几条是踩出来的）

0. **一条预期只判一件事 —— 长的必须拆开**

   用户原话：「用例拆分预期。至少有6个。但是说只有预期结果只有 3 条。不对。
   要检查。第5个里面有多个小项目。这要也要拆分。」

   **不要照抄原文的编号。** 原文一条里常塞好几件事，直接抄成一条断言，
   等于这几件事只判了其中一件（甚至一件都没判准）。

   拆的界线是**句子边界 + 子项**，三种都要拆：

   | 原文写法 | 怎么拆 |
   |---|---|
   | 分号/逗号连两件事：「标题右侧显示周数**；**第一个小节显示加号」 | 拆 2 条 |
   | 冒号后面跟列表：「可以调整字段包括：」+ `·a` `·b` `·c` | 主句 1 条 + 每个子项 1 条 |
   | 一行里两个字段：「课程名称（必填）教室（非必填）」 | 拆 2 条 |

   实例（176）：原文 6 条 → 实际 **14 条**。
   ```
   原文3 -> a3 周数显示 / a4 第一个小节显示加号
   原文4 -> a5 顶部标题「添加课程」 / a6 「完成」可点保存
   原文5 -> a7 弹出编辑弹窗
            a8 课程名称（必填）  a9 教室（非必填）  a10 备注
            a11 上课时间  a12 上课周数  a13 课程背景色 10 种
   原文6 -> a14 弹框关闭
   ```

   > 拆完自查：**每一条 a 能不能只用一个「是/否」回答？**
   > 如果要用"并且"才能描述完整，就是还没拆够。

1. **`locate` 优先写 `rid`，图标按钮必须给 `locate`**
   纯图标按钮没有文字，模型看不出它是干什么的。

2. **别把弹窗的按钮当落点，但权限要写进断言**
   点"允许"之后界面没变，`landing` 会判失败。**点弹窗**是执行器的事。
   但**权限该不该弹、允许/拒绝后什么表现**，是用例的**预期**，必须写进 `asserts`。
   见下面「权限是预期的一部分」。

3. **不许凭空造：字段不能新编，强证据的值必须来自真实记录**

   用户原话：「YAML 文件不能凭空添加字段。所有强证据的值必须来自
   真实的记录。不能凭空捏造。」

   两件事，两套机制：

   **① 字段不能新编。** 每层都有白名单，写不认识的字段会报警，
   而且那个字段**根本不生效**：

   | 层 | 能用 |
   |---|---|
   | 顶层 | `meta` `steps` `assertions` `preconditions` `confidence` `playbook` |
   | `meta` | `case_id` `title` `package` `knowledge_files` `derived_from` `source` `note` |
   | `steps[]` | `id` `desc` `target` `locate` `landing` `know` `pitfalls` `do` `expect` `verify` `on_fail` |
   | `steps[].know` | `where` `why_this` `locate` `source` `files` |
   | `assertions[]` | `id` `desc` `check` `note` `result` |
   | `preconditions[]` | `kind` `desc` `do` `undo` `skip_if` `assert_start` `target` `hint` `expect` |

   > 想记点什么但没有字段？**写进 `desc` / `note` / `pitfalls`**，
   > 别新造一个键 —— 新键不会被执行器读，等于没写。
   > 真需要新字段，先改 `loader.py` 的白名单和 schema，**再**用。

   **② 强证据的值必须见过。** `rid` / `activity` / `package` / `text`
   是"这个控件在不在"的唯一依据，写错一个就会把功能正确的判成 FAIL。
   这些值只能从**真实记录**里抄：

   - `assets/storage/evidence/**/*.xml` —— 历次真机 dump（控件树）
   - `tmp/runs/*/run.log` —— 每次运行日志（`act=…Activity` 在里面，**不在** dump.xml）
   - `tmp/runs/*/shots/` —— 截图
   - `assets/storage/knowledge/` —— 沉淀的知识卡

   核对命令：

   ```
   python tools\check_evidence_provenance.py
   ```

   > ⚠️ 实测教训：`EditCourseActivity`、`btnDelete`、`TimetableGuideActivity`
   > 一度被写进 YAML 却**从未真实出现过**（那两条路径从没跑通过）。
   > 这种值哪怕看起来合理，也是在拿猜测当证据 —— 跑起来必然误判。
   >
   > ⚠️ 反过来也别矫枉过正：报"没找到"不等于一定是错的，
   > 可能是这个页面还没采集过。**补采一次 dump 再写**，别删掉对的东西。

4. **断言判据：能定死的用代码，判不了的整条交 AI**

   用户原话：「要求强证据可以用代码判断。只要是涉及输入，不能通过代码
   或者代码判断容易出现异常的都交给 AI 现场判断。」

   分界线只有一条 —— **这条预期代码能不能一把定死？**

   **能 → 代码硬判，而且要比对到"值"这一层**：

   ```yaml
   # ✗ 错：预期是"默认 4 节"，却只判控件在 —— 显示 6 节也一样过
   check: {nodes_present: [{rid: tv_morning_slot_count}]}
   # ✓ 对：直接比数值
   check: {node_text: {rid: tv_morning_slot_count, equals: "4节"}}
   ```

   **不能 → `check: null`，整条交给 AI**，别写个"看起来有判据"的假 check：

   | 预期里有这类词 | 为什么代码判不了 |
   |---|---|
   | **可编辑 / 可调整 / 可点** | 代码只知控件在，不知点不点得动 |
   | **点了有响应 / 弹了框** | 响应是跨屏现象，不是某一屏的属性 |
   | **默认值是 X** | 能取到文案才判得了；取不到就要 AI 看 |
   | **跳出去之后是哪个界面** | 外部界面不受我们控制，写死必误报 |
   | 颜色数 / 有几种 / 长什么样 | 数量、外观要看图 |

   > ⚠️ `check: null` 时，**`desc` 是 AI 唯一的指令**。
   > 把"要验什么、怎么算过"写进 `desc`，别只写"功能正常"。
   > （`AssertSpec` 只有 `id`/`desc`/`check` 三个字段，没有额外传话的位置。）

   > 交 AI 不等于丢证据：AI 判定那一刻拿得到 activity、可点控件列表、
   > 见过的 rid 和截图 —— 比单判 activity 更全。

   **★ 最容易犯的错：desc 和 check 不对齐。** 两个方向都是错：

   | 现象 | 后果 | 怎么改 |
   |---|---|---|
   | desc 说"可编辑/有响应"，check 只判 rid 存在 | **假 PASS** —— 验了个皮毛 | 要么补真判据，要么 desc 收窄 |
   | desc 只说"入口在"，其实人要求的是"能点通" | 需求没被验到 | 收窄 desc 前先确认需求真只要这个 |

   > ⚠️ 实测：`node_present` 对**置灰按钮同样判 ✔**
   > （rid 在 dump 里就够了）。所以 desc 里写"不能置灰"而 check 用
   > `node_present`，就是在说一件判据证明不了的事。
   > 能判"可点"的键是 `dialog_present`（它查的是**当前可点列表**）。

   **★ 也别矫枉过正 —— 硬证据不能一起扔。**
   `check` 是 AND 语义，没法表达"这半由代码判、那半由 AI 判"。
   遇到一条预期里有硬事实（如 `activity=EditCourseActivity`）
   又有软判断（如"字段可编辑"）时：
   1. `check` 保留硬的那一半
   2. **`desc` 收敛到硬的那一半能证明的范围**
   3. 软的那件事，确认它由别的断言或步骤实际覆盖

   整条改成 `check: null` 会把已验证的 activity 强证据一起丢掉，那是倒退。

5. **前提该清就清，但要能恢复**
   `kind` 只支持三种：`nav`（回起点，拉起 App 用这个，**不改数据**）、
   `data`（改数据，如 `pm clear`，能恢复就写 `undo`）、
   `env`（改环境/硬件，**代码强制必须给 `undo`**，否则直接报错）。
   `pm clear` 不是默认前提：它清的是真实账号数据，**不可逆**。

6. **不确定的写在 `pitfalls`，别猜**
   每步可以带 `pitfalls`（这一步容易踩什么）。宁可多写一句提示，
   也不要留一个错误的坐标。

### ★ 权限是预期的一部分

**最容易漏的一类**：用例说"点拍照导入能进相机"，隐含前提是
**被测 App 有相机权限**。拆解时把用例里的词对到权限，写进 `asserts`：

| 用例里的词 | 权限 |
|---|---|
| 图库 / 相册 / 照片 | `READ_MEDIA_IMAGES` |
| 拍照 / 相机 / 扫码 | `CAMERA` |
| 录音 / 麦克风 | `RECORD_AUDIO` |
| 位置 / 定位 | `ACCESS_FINE_LOCATION` |

判**被测 App 的授权状态**（`permission: {CAMERA: true}`），不是"弹窗出现过没有"。

> 判据边界（代码只认哪些键）、权限判据为什么不能用 `permission_dialog`
> 这类自造形状，读 `references/permissions.md`。
## 第三步：派发

> ⚠️ **一个用例派一个子 Agent，只派一次。**
>
> 不要把它拆成几步分给几个子 Agent 去跑。两个子 Agent 会抢同一台设备，
> 结果是「起步就找错页面」这类**看起来像产品缺陷的假失败** —— 比直接报错更危险。
>
> 这条不是靠你记住：同一条用例还在跑时，第二个子 Agent 调 `android_case`
> 会被**代码直接拒绝**（返回 BLOCKED，一步不执行）。所以派之前先确认
> 上一个子 Agent 已经回来了 —— 回来了就直接转述它的报告，不要重派。

用 `subagent` 工具。**把拆解结果完整放进 prompt**，因为子 Agent 不继承你的上下文。

**两种模板，二选一照抄 —— 不要混用**（同时给 `case_name` 和结构会打架）。

有现成 YAML 时：

```
subagent(
  prompt: """
    执行这个 Android 用例，用 android_case 工具。

    case_name: 168

    要求：
    - 直接跑，不用加别的开关
    - 判据（landing / asserts）是验收标准，不许改；跑不通就照实报
    - 把报告的 status / engine / steps_done / issues 原样转述回来
    - steps_done=0 表示一步都没执行，这时不要说"功能正常/不正常"
  """
)
```

⚠️ **`case_name` 方式默认会回写 YAML**（`writeback=true`）—— 只改每步的
`locate`（点哪个控件），不动 `landing`/`asserts`。这是有意的自我校准。
如果你只想看看、不想落盘，在派发时明确加一句"用 `writeback=false` 跑"。

现场拆的（把上面那份 JSON 原样贴进去）：

```
subagent(
  prompt: """
```

### 派发时必须交代的三件事

1. **用哪个用例**（`case_name` 还是内联结构，**只能选一个**）
2. **用例内容别改** —— 判据（`landing` / `asserts`）是验收标准，
   子 Agent 只负责跑，跑不通就照实报，不许迁就结果改判据
3. **报告怎么转述**（见下）

### 多个用例怎么跑：串行

**一个跑完再跑下一个。** 同一台设备同一时刻只能有一条用例在跑 ——
执行器有设备锁会排队，但排队期间你看不到任何进度，不如自己一个个派。

也别为了"快一点"同时派几个子 Agent 跑不同用例：锁会让它们排队，
既省不了时间，转述时还容易把两条用例的报告弄混。

不需要给子 Agent 加任何"加速开关"：执行器**每一步都先在当前屏找唯一命中**，
命中就代码直点、找不到才叫模型。报告里的 `auto_rate` 就是自动化率。

## 报告怎么读、怎么转述

子 Agent 回来后，先看三个字段：

| 字段 | 怎么用 |
|---|---|
| `steps_done` | **= 0 表示一步都没跑**。这时不许产出"功能正常/不正常"的结论 |
| `engine` | `autopilot` = 没调模型，只验了 YAML 结构，**不是用例结论** |
| `status` | 见下表 |

### ★ 三个状态的含义（转述时不能混）

| 状态 | 含义 | 能不能说"功能有问题" |
|---|---|---|
| **PASS** | 用例与实际**一致**：所有步骤走完 + 所有断言成立 | 可以说"正常" |
| **FAIL** | 与实际**有差别**，但**所有路径都执行完了**（如按钮文字期望 AAA 实际 BBBB） | **可以**，这就是产品缺陷 |
| **BLOCKED** | 用例**没执行完**：崩溃，或关键路径没找到（如点 A 应跳 B，实际停在 C） | **不可以** —— 是没跑完，不是功能坏 |

- **BLOCKED 之后执行器会直接停下**，后面的步骤不会跑
- **FAIL 和 PASS 一定表示所有路径都跑完了** —— 所以"只走了 2/3 步"不可能是 FAIL

⚠️ 最常见的错误是把 BLOCKED 转述成"这个功能有问题"。
BLOCKED 只说明"没走到/没跑完"，要么是路径变了，要么是设备环境问题 ——
**需要人来判断**，不是直接当缺陷报出去。

**必须如实转述，不许粉饰：**

- ✅ "3 步通过，第 4 步 FAIL：按钮文字期望 AAA，实际 BBBB"
- ✅ "BLOCKED：点「从图库导入」应进入图片选择器，实际停在日历首页（试了 3 次）"
- ❌ "用例基本通过，有个小问题"（含糊会让人误判）
- ❌ 把 BLOCKED 说成"功能不正常"（没有依据 —— 根本没走完）

如果 `status` 是 `BLOCKED`，明确说"这次没跑完，原因是什么"，
**不要**说成"功能有问题"——那是两件完全不同的事。

### 先自查：我到底有没有真的跑起来？

`steps_done == 0` 且 `BLOCKED` → **一步都没执行**。
这时**不许**产出任何用例结论，只能说"没跑起来，原因是什么"。
只有 `steps_done > 0` 的 PASS/FAIL 才是结论。

### `playbook` 和 `confidence` 不报警告

它们是注解，本来就不进执行通路：

- `playbook`：旧文件里的「执行须知」。**「按步读坑」这条元规则已生效** ——
  坑一律按步给出，走到哪步就只看那步的 `pitfalls`。为什么：回放按步走，
  第 1 步的坑跑到第 2 步还在眼前会**稀释信息**，真正相关的那条反而看不见。
- `confidence`：用例**历史可信度**，**不参与判定**。`level != verified` 时
  （如 `single-run`/`flaky`），这次 PASS **不代表功能稳定**。
  报告的 `case_confidence` 字段带 `level`/`reason`/`todo`。

## 常见误判（别踩）

- **`steps_done=0` + `BLOCKED`** → 没跑起来，不是功能有问题
- **`engine=autopilot` 的 PASS** → 只说明 YAML 结构没问题，功能没验证
- **设备锁屏/掉线** → 表现为"点了没反应"，看 `issues` 里有没有设备相关字样
- **`content.some is not a function`** → 工具层 bug，不是你的问题，
  把原始报错转给用户
