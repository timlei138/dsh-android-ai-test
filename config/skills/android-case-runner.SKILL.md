# Android 用例执行器（执行子 Agent 专用）

> **这份技能卡是给"执行子 Agent"看的。**
> 如果你是被派来跑用例的，继续往下读。
>
> **如果你是要拆解/派发任务的主 Agent —— 你用错技能卡了，
> 去读 `android-case-planner`。** 你没有 `android_case` 工具，
> 这份文档里所有命令你都执行不了（硬调会被代码拒绝）。

## 这个技能解决什么

早先的执行方式是"把纪律写在提示词里，指望模型遵守"。实测会漏：
模型会连点同一个无效坐标 9 次、会把权限框当成目标页面、
会在两个页面之间来回弹 58 轮烧掉 6 分钟。

**现在把纪律挪进代码。** 你只负责把收到的用例跑完并如实报告；
执行器负责：

| 执行器代码负责 | 说明 |
|---|---|
| 动作节奏 | `act → 读 next → act`，不在每步后浪费 6 秒观察 |
| 强证据直点 | 目标在当前屏**唯一命中**就代码直接点，不问模型 |
| 落点判定 | 声明完成时，代码用 `landing` 判据**复核**一次 |
| 结论闸门 | `activity=` 类预期由代码核对"本次是否真的到达过" |
| 坐标合法性 | 坐标必须来自当前响应，编造的会被拒绝 |
| 死循环 | 同点连点、**交替循环**都会被识别并终止 |
| 运行时权限 | 工具层自动点"允许"（抢 6 秒窗口）并记账 |
| 前提/恢复 | 按 `preconditions` 执行，跑完按 `undo` 还原 |
| 知识卡注入 | 第一步给全文，**后续每步按该步内容自动检索片段** |
| YAML 回写 | 跑完把**代码实际点过的路径**写回 YAML（见下） |

## ★ 你的定位：一个普通的测试人员

**不要把自己当"照着脚本执行的机器"，也不要当"要用 rid 精确编程的工程师"。**

你是一个懂基础操作的测试员：
- 知道**返回键**（back）能退回上一层 —— 卡在某个陌生页面时，按它就是
- 知道**Home 键**（home）能回桌面 —— 迷路了就从桌面重新进 App
- 知道**看屏幕上有什么**、点看起来对的控件
- 知道**翻知识卡**找这个 App 有什么坑

对应到 `android_case` 的返回（`StepAction`）：
- 点屏幕控件 → 给 `next_x` / `next_y`
- **按返回键 → `key="back"`**
- **回桌面 → `key="home"`**

⚠️ 这几个系统动作是**你纠正错误的主要手段**，别只会在屏幕上找图标。

### YAML 是参考，不是命令

用例 YAML 里写的 `target: rid=xxx` 是**上一次怎么走的记录**，
不是"你必须点这个 rid"，更不是"找不到就无解"。

版本不同、设备不同、界面微调，YAML 都会对不上。**这是常态，不是异常。**

正确的反应顺序：
1. 代码先按 YAML 的 `target` 在当前屏找 —— **唯一命中就直接点，不花你的 token**
2. 对不上 → 代码把**处境**交给你（这步本来干什么、现在在哪个界面、卡在哪）
3. **你自己想办法**：看屏幕上有没有更合适的入口、要不要先按 back 退出当前页、
   要不要回 Home 重新进 App、要不要翻知识卡
4. 走通了 → 代码会把**它实际点过的**路径回写进 YAML，下次就准了

⚠️ 但**落点判据（landing）和断言（asserts）不许你改** ——
那是用例的验收标准，属于人的需求，只记录路径、不改标准。

## 你怎么用它

调 `android_case` 工具。**你不需要也不能**用 shell、adb、写文件 ——
你的工具面被限制住了，`android_case` 是唯一能碰设备的口子。

### 情况一：主 Agent 给了 `case_name`（有现成 YAML）

直接跑，**别自己重新拆**：

```
android_case(case_name="168")
```

加载器会自己读步骤、判据、`pm clear` 前提、每步的坑和知识点。
用这种方式时**不要**再填 `steps`/`asserts`/`package`（会和 YAML 打架）。

**只有这种方式会回写 YAML**（因为只有它有一个真实文件在那儿）。
跑完 `yaml_writeback` 会说明改了哪几步。

想先看会改什么、暂不落盘，加 `writeback=false`。

### 情况二：主 Agent 给了内联的用例结构

把 `steps`/`asserts`/`preconditions` 原样传进去：

```
android_case(
  case_id="168", title="...", package="com.zui.calendar",
  steps=[...], asserts=[...], preconditions=[...]
)
```

**不要改主 Agent 给的判据。** 如果某个判据明显跑不通，
照实跑、照实报 —— 改判据是"迁就结果"，会让报告失去意义。

### 完整参数表

| 参数 | 说明 |
|---|---|
| `case_name` | 用现成 YAML（推荐）。**与下面四个互斥** |
| `case_id` / `title` / `package` | 内联模式的基本信息 |
| `steps` / `asserts` / `preconditions` | 内联模式的用例内容 |
| `knowledge_files` | 额外知识卡（YAML 里也可写） |
| `serial` | 指定设备；不填则用唯一在线设备 |
| `perm_action` | `grant`（默认）/ `deny`，只测"拒绝分支"才填 deny |
| `writeback` | 是否回写 YAML，默认 `true` |
| `answer` | `model`（默认）/ `autopilot`，见下 |

不需要"纯代码模式"这类开关 —— **每一步都先由代码在当前屏找唯一命中**，
找到就直点、找不到才叫模型。报告里的 `auto_rate` 就是自动化率。

#### `answer` —— 谁来做判断（默认 `model`）

```
android_case(case_name="168")                        # 默认就是真模型
android_case(case_name="168", answer="autopilot")    # 只自测 YAML 时
```

| 值 | 含义 |
|---|---|
| `model`（**默认**） | 真模型：`decide`/`assert` 交给 LLM。这是"用例过不过"的唯一真实答案 |
| `autopilot` | 规则应答器：按 `target`/`landing` 走，**完全不调用 LLM**。只验「YAML 写对没有」，不产生用例结论 |

**默认是 `model`，跑用例不用传。** 理由：忘了传 → 真模型（正确结果）；
而不是忘了传 → 假成绩（危险）。`autopilot` 改成"要显式声明才用"。

> ⚠️ **绝对不要拿 autopilot 的结果当用例结论。**
> 两者的报告长得一模一样（都有轮次/`decide`/PASS），但 autopilot 根本没接模型。

> ⚠️ YAML 里有些字段执行器还没实现。这些会**明确打印成 "未采纳"** 警告，
> 不会静默丢掉。看到警告不等于失败，但意味着那条信息这次没生效。

### ★ 强证据直点：代码什么时候替你动手

每一步，代码先看**当前这一屏**：

- `target` 的 `rid=` / `xpath=` / `text=` 在**当前屏唯一命中** → **代码直接点**，不问你
- 命中 0 个，或命中 **2 个以上**（分不清要点哪个）→ **交给你**判断

> ⚠️ 唯一性是**硬门槛**。0 个或多个都绝不"取第一个凑合"——
> 取第一个正是"点错地方"的最大来源。

**这是按屏判断，不是一次性放弃**：某一屏没命中交给你，你走过去之后，
下一屏代码照样会重新尝试直点。

### ★ 每一步先问代码：落点到了吗？

**进入一步时，代码先做一次判断**：YAML 写的 `landing` 现在满足了没？

- **满足了** → 这一步直接算完成，进下一步，**不调用模型**
- 没满足 → 按 `target` 找控件去点
- 点不着 → 才交给你（模型）

为什么这很重要：上一步点完，屏幕可能**已经**是下一步的界面了。
老做法是照样问一次模型"这步完成了吗" —— 白花一次调用。

⚠️ **但代码绝不"猜"完成**：某一步要是 YAML 里没写 `landing`，
代码不会凭空判它完成（那会让整步被跳过、用例凭空 PASS），而是交给你判断。
**"没有判据"不等于"已经完成"**，这条对代码和你都一样。

#### ★ 判据分工：确定的给代码，有异议的给 AI

| 判据 | 谁判 | 为什么 |
|---|---|---|
| `activity=` | **代码** | 跳到哪个页面，唯一确定 |
| `rid=` | **代码** | 控件在不在，唯一确定 |
| `package=` | **代码** | 前台包名，唯一确定（**相等**匹配） |
| `text=` / `desc=` | AI | 代码只能子串匹配，**判得出但判不准** |
| `dialog_present` / `input_text` | AI | 同上，还可能是别的页面的同名内容 |
| 没写判据 | AI | 代码无从判断，绝不猜"完成" |

混合判据（如 `activity=.A,text=课程表`）**整体交 AI** ——
代码无法确认 `text` 那半成不成立，合出来的结论就不可信。

为什么这么分：**"判得出但判不准"比"判不了"更危险**，
它带着代码的权威感，会让人以为验过了。

**XML 看不见的东西，走另外两条路**：
- 文字（XML 里没有）→ **OCR**
- 颜色 / 背景 / 布局 → **视觉模型**

#### 临时弹窗：是干扰，不是判据

用例关心"点了这个按钮跳到哪"，不关心中途蹦出个什么框。

- `activity` 判据满足了就走，**不管中间出现过什么弹窗**
- 判据不满足了才让 AI 看屏幕 —— 那时它才会发现"哦，被弹窗挡住了"
- 点掉弹窗要申报 `is_dialog=true`，**不算连点**（否则反复弹的框会被当成死循环误杀）
- 但"弹窗豁免"有**上限**（每屏 4 次），不会让人靠点弹窗无限刷下去

## 冷启动：起点固定

**规则：除非用例明确要求清数据，否则一律冷启动复位。**

YAML 的步骤是按「从 App 首页出发」写的。如果起点取决于"上次停在哪个界面"，
步骤顺序就没法直接用，只能靠人去迁就设备现在在哪。冷启动把这个从根上消掉。

> ⚠️ **只 `force-stop`（关进程），不清数据。**
> `pm clear` 是**用例明确要求**时才做的事（「首次使用」「测首次授权」）。
> 拿 `pm clear` 当默认复位＝拿大锤砸一切，会清掉本用例要用的前置数据。

这里踩过**三个真机 bug**（都已修，回归测试见 `test_coldstart.py` / `test_wake_guard.py`）：

**bug1：`adbutils.app_stop/app_start` 静默失效。**
实测 `app_stop('com.zui.calendar')` 后 `pidof` 仍返回原 pid，
`app_start()` 返回 `None` 且进程没被拉起 —— **但代码不报错**，
还照样打印"已冷启动复位"。**这是最坏的一类 bug：骗过了日志。**
⇒ 改用 `am force-stop` + `monkey`，并**回读 `mCurrentFocus` 校验**。

**bug2：杀掉 App 后，它拉起的系统浮层还留在前台。**
实测：日历点「从图库导入」调起 PhotoPicker
（`PhotoPickerGetContentActivity`，包名 `com.android.providers.media.module`），
此时杀掉日历 —— **这个框不属于日历进程**，`force-stop` 日历动不了它，它一直在前台挡着。
⇒ 冷启动必须**先清掉这类跨包浮层，再拉起被测 App**。

**bug3：屏幕睡着时，一切点击都静默失效。**
实测：跑 168 得到 `18 轮 / steps 1/4 / BLOCKED`，模型**连续 3 次点 `(0,0)`**。
日志里全是模型的错，但真相是设备休眠了：`mWakefulness=Dozing`、
`mCurrentFocus=NotificationShade`（锁屏遮挡）。屏幕上根本没有可点控件。

> ⚠️ **又是一类"骗过了日志"的故障** —— 症状看起来像"模型不会用"，其实是"设备没醒"。

⇒ 冷启动**第一步**先 `KEYCODE_WAKEUP` + `wm dismiss-keyguard`，
再 force-stop / 拉起 App。**只在需要时发**，不要每次强行点亮用户的屏幕。

#### ★ 资产必须自包含

**设备依赖和数据都在 `assets/` 里，不在任何 `.agents` 技能目录里。**

2026-10 删掉旧技能目录时，结果不是"少了个技能"，而是
**设备 venv（adbutils/opencv/rapidocr）跟着没了** —— 它原本只存在于被删的目录。
于是 `runner_python()` 掉到兜底、返回**工作区根 `.venv`**（编排用的、没有 adbutils），
`run.py` 报「缺依赖：先建环境」，整条执行链断掉（`status=BLOCKED steps=0`）。

> ⚠️ 这是**静默崩坏**：没有 ImportError 指向真因，只有一句"缺依赖"。

现状（已修，回归测试 `test_assets_selfcontained.py`）：

```
D:\dsh\langgraph-poc\.venv          → 编排（langgraph/langchain）
D:\dsh\langgraph-poc\assets\.venv   → 设备操作（adbutils/opencv/rapidocr）
assets\requirements.txt             → 能重建设备 venv
```

**两个 venv 不能合并、不能互换。**

#### 报 `content.some is not a function` = 工具的 bug，不是你的问题

只在测试模式炸。看到就把原始报错转给用户，**不要**自己分析、不要重试。

#### ★ 看到 `WinError 267` / `skill_root` 才读这节

> **判据：报错原文里没出现 `267` 或 `skill_root`，就不要往这想。**
>
> 曾经有会话其实失败在**工具 schema 校验**（`steps_done=0`，压根没进 execute），
> 但它读到了这节，就断定"是 skill_root 的已知故障"，
> 进而虚构出一条报错和一整套根因分析 —— **设备一次没碰，报告看起来很专业**。

真遇到时：`skill_root` 指向了**不存在的目录**。
注意**空串表现完全不同**——`Path("")` 就是 `Path(".")`，不报 267，表现为「找不到 `run.py`」。

**别手写资产路径**，一律 `from assets_path import skill_root`。

### 情况三：用例还没沉淀成 YAML（主 Agent 现场拆的）

主 Agent 会直接把拆好的结构给你。原样传进去：

```
android_case(
  case_id="168", title="联想日历_图库导入入口", package="com.zui.calendar",
  steps=[
    {id="s1", desc="点右上角「更多」，菜单选「课程表」",
     landing="activity=TimetableActivity"},
    {id="s2", desc="点「从图库导入课程表」",
     landing="activity=PhotoPickerGetContentActivity"},
  ],
  asserts=[
    {id="a1", desc="可打开课程表页面", check="activity=.timetable.display.TimetableActivity"},
    {id="a2", desc="图库导入入口可点击", check="node_present=rid=btnImportFromGallery"},
  ])
```

## 跑的时候你能看到什么

执行器会**实时上报进度**，你不用干等。报告里有：

| 字段 | 用途 |
|---|---|
| `progress` | 逐条动作轨迹（时间、点哪、到了哪个界面） |
| `stalled_at` | 卡在哪 —— 空串表示没卡 |
| `elapsed_s` | 总耗时 |
| `steps_done` | 走完了几步（放弃的步**不算**） |
| `auto_rate` | 自动化率：**这一步是代码直点的，还是叫了你** |
| `case_confidence` | 用例历史可信度，**不参与判定** |

## 最重要的一件事：landing 要写准

`landing` 写不准，用例就会判错 —— 这是**唯一**需要你仔细想的地方。
它必须是**可验证的机器判据**，不是"应该到了图库页"这种描述。

| 判据 | 写法 | 说明 |
|---|---|---|
| activity | `activity=TimetableActivity` | 允许短名（`.Foo` 命中 `a.b.Foo`） |
| 控件存在 | `rid=btnImportFromGallery` | 按资源 id 精确匹配 |
| 文本 | `text=课程表` | 子串匹配 |

多个条件：**逗号 = AND**，**竖线 = OR**。
例：`activity=Foo,rid=bar` 要两者都成立；`rid=a|rid=b` 命中其一即可。

★ **落点必须是稳定终态**，不能是流程中途一闪而过的东西。
写成中途状态 = 用例会在"路过"那里就被判完成。

### 断言用 YAML 的结构化判据（判得比模型准）

跑 YAML 用例时，`check` 是**结构化字典**，会被**代码直接判定**，
判不了才交回模型。已实现：

| 判据 | 形状 | 说明 |
|---|---|---|
| `activity` | `{activity: ".Foo"}` | 本次**到达过**（不是"当前在哪"） |
| `activity_changed_to` | 同上 | 同义 |
| `node_present` | `{node_present: {rid: x}}` | 过程中出现过即算 |
| `node_absent` | `{node_absent: {rid: x}}` | 从没出现过 |
| `node_text` | `{node_text: {rid: x, equals: "课程表"}}` | 该控件的文案 |
| `dialog_present` | `{dialog_present: {rid: button1}}` | 弹框出现 |
| `package` | `{package: "com.x"}` | 当前前台包名 |
| `after_tap` | `{after_tap: {dialog_present: {...}}}` | 嵌套子判据 |

多个键 = **AND**。注解字段（`note`/`measured`/`desc`）不参与判定。

> **不认识的判据键会被明确标出来**（"⚠️ 不认识的判据键 xxx（未实现，未参与判定）"），
> 不会静默忽略 —— 静默忽略会让用例"看着跑了其实没验"。

### 踩过的坑：别把弹窗的按钮当落点

写 landing 时**只写那个页面独有的、稳定的标识**。反面教材：

```
s2 落点 = rid=button1        ← 错的
```

`button1` 是 **App 自绘说明页**上的「同意」按钮（包名还是被测 App）。
把权限框弹出来当成了"到达图库入口"，于是照片权限从没被授予，用例误判。

**正确写法**：`activity=PhotoPickerGetContentActivity` —— 那是唯一真正的落点。

判据：**这个 rid 只有目标页面才有吗？** 如果它在弹窗、遮罩、通用按钮上也会出现，
就不能用它当落点。

### 更隐蔽的坑：`activity=` 短名必须真的包含在完整名里

```
落点写 activity=TimetableActivity
实际到的是 .timetable.widget.TimetableGuideActivity   ← 不含 "TimetableActivity"
```

匹配规则是**子串包含**。`TimetableGuideActivity` 里没有 `TimetableActivity`
这个连续子串，所以**永远匹配不上** —— 流程会在原地来回弹到死循环（实测 58 轮）。

写 `activity=` 落点前，先确认目标 activity 的**真实全名**。
多个可能的落点用竖线：`activity=TimetableActivity|activity=TimetableGuideActivity`。

### 图标按钮的 target 要选对

「更多」「返回」「加号」这类按钮**没有文字**，模型光看 `rid=iv_more` 认不出它是「更多」，
会去点列表里第一个带文字的东西（实测点了日期栏，然后卡死）。

所以 `target` 要给得让代码能唯一命中：

```yaml
target: rid=iv_more
landing: activity=.timetable.display.TimetableActivity
```

`target` 支持 `rid=` / `xpath=` / `text=` / `desc=` / `key=`。
**推荐 `xpath=`** —— 它能表达"右上角那个"这种结构关系，比单个 rid 更不容易撞车。

> ⚠️ **绝不存坐标**。坐标换个分辨率就废，而且看起来"很精确"，最容易被误信。
> 要定位就用 xpath 这种**结构路径**，同一个控件不会因为分辨率变化而找错。

**菜单项通常没有 rid**（`rid=None`），这时必须按文字定位：`target: text=课程表`。

## 权限：分两类，各管各的

> 最容易判错的一节。判错一次，一条本来 PASS 的用例会被判成 FAIL。

### 判归属只看**包名**，不看文案

| 弹窗 | 包名 | 怎么处理 |
|---|---|---|
| **系统权限弹窗** | 固定 `com.android.permissioncontroller`（GMS 为 `com.google.…`） | 工具层自动点 + 记账，不用你管 |
| **App 自己的弹窗** | **就是被测 App 的包名** | **流程的一部分**，顺手点掉就行 |

⚠️ 不要用弹窗文案去猜归属。文案会骗人 —— 相机 App 弹的
「相机正在尝试使用相机」里也有"相机"二字。**包名是唯一确定的。**

### App 自己的弹窗：不必特别在意

「请确保图片清晰、完整」「课程表上新了」「需要使用以下权限」这类，
**都是 App 功能的一部分**，跟页面上的普通按钮没区别：

- 它出现了就点掉，**按顺序走完即可**
- **只要不影响主流程，就不用特意管它**

### 真正要验的：被测 App 的权限有没有给

用例预期「允许后能打开相机」，验的是**被测 App 拿到了权限**，
不是"屏幕上弹过什么框"。所以断言用**授权状态**判：

```yaml
check:
  permission: {CAMERA: true}         # 日历已被授予相机权限
  package: "com.zui.camera"          # 允许后确实打开了相机
```

`permission` 判的是 `dumpsys` 里的**授权结果**，跟弹窗长什么样、弹没弹过无关。

**相机 App 自己的权限，与本用例无关。** 用户原话：

> 点击拍照导入按钮后，日历需要相机权限。同意了才能打开相机。
> **只要打开就行了**。哪怕打开后相机 APP 权限，那不是我们这个 case 关心的。

### ★ 两类权限，处理方式不同

| 类别 | 举例 | 处理 |
|---|---|---|
| **内容型** | 相机、照片、存储、位置、通讯录、麦克风 | **同意了才能继续下一步** —— 没确认授予就停下报错 |
| **普通型** | 通知、日历、设备信息 | 不给可能只影响某个功能，不阻断流程 |

> ⚠️ 关键：**"判不了"绝不等于"已授予"。**
> 读不到授权状态时必须报未确认，不能默认放过 —— 那会让用例带着没给的权限往下跑。

### 双分支（允许 + 拒绝）：分两轮跑

一个用例往往要验"允许后能用"和"拒绝后有提示"两条：

1. **先拒绝、后允许** —— 拒绝会改变弹窗形态（多出「不再询问」），
   让"允许"落在确定的第二形态上。
2. **第二轮必须先撤销权限** —— 权限已授予时系统**不会再弹窗**，
   不撤销就直接走不通（表现像"没弹框"，其实是根本不弹）。
3. **第二轮记得清掉 deny 意图**（`perm_action` 重置）。

### 工具层怎么处理

系统权限框约 **6 秒**不点会自动消失，所以**工具层自动响应**（默认点「允许」），
并在报告里记账。你不需要手动点，但**需要核实**：

| 字段 | 含义 |
|---|---|
| `granted_permissions` | **被测 App 当前被授予了哪些权限**（断言用这个判） |
| `runtime_permissions` | 点了哪些按钮（含坐标、事件 id） |
| `runtime_permission_prompts` | 弹窗文案（**仅供留痕，不作判据**） |
| `unmatched` | 框在，但没有能安全点的按钮 → **交回给你判断** |

⚠️ **「选择照片」「前往设置」「拒绝并不再询问」工具层故意不点**：
- 「拒绝并不再询问」会设 don't-ask-again，后续"授予"分支**永远不再弹框**
- 「选择照片」是部分授权，语义和"全部允许"不同，该由用例决定
- 「前往设置」会跳出被测 App

> ⚠️ **权限点击只记账，不写进 YAML。**
> 那是平台标准流程，没有信息价值，写进去只会把用例文件弄脏。

## 前提条件：该清就清，但要能恢复

会改设备状态的操作写进 `preconditions`，并**在 `undo` 里给出恢复方式**：

```
preconditions=[
  {kind="data", desc="确保没有旧课程表，首次使用才出现入口",
   do=["pm clear com.zui.calendar"], undo=[]},
  {kind="data", desc="拉起 App 回到首页作为起点",
   do=["am start -n com.zui.calendar/.AllInOneActivity"], undo=[]}
]
```

- `kind="data"` —— 改数据（清应用、改设置），**能恢复就必须写 `undo`**
- `kind="env"` —— 改环境/硬件（飞行模式、屏幕方向），跑完按 `undo` 还原

**默认不是清数据**：只在用例确实需要"首次使用"状态时才 `pm clear`。
测试账号的数据可以放心清，但**真实账号的数据不能清** —— 先确认。

## 报告怎么读

### ★ 三个状态的含义（转述时不能混）

| 状态 | 含义 |
|---|---|
| **PASS** | 用例与实际**一致**：所有步骤走完 + 所有断言成立 |
| **FAIL** | 与实际**有差别**，但**所有路径都执行完了**（如按钮文字期望 AAA 实际 BBBB） |
| **BLOCKED** | 用例**没执行完**：崩溃，或关键路径没找到（如点 A 应跳 B，实际停在 C） |

两条铁律：
- **BLOCKED 之后不会再执行下面的步骤** —— 执行器会直接收尾
- **FAIL 和 PASS 一定表示所有路径都跑完了** —— 所以"只走了 2/3 步"不可能是 FAIL，只会是 BLOCKED

落点不符最多试 **3 次**，仍不符就 BLOCKED 并停下。报告里的 `issues` 会写明
期望什么、实际停在哪一页。

工具返回结构化结论，重点看：

- `status` —— 见上表
- `issues` —— 逐条问题。**`判定纠正` 开头的是代码推翻了模型判断**，值得细看
- `steps_done` / `coverage_ok` —— 走完了几步、预期是否全部验过
- 运行时权限那段 —— 见上，不可逆，必须如实转述
- `restored` —— 恢复了什么
- `yaml_writeback` —— **YAML 被改了哪几步**（见下）
- `action_trace` —— 每步**实际**点/按了什么

⚠️ **BLOCKED 不是"功能有问题"，也不是"环境有问题"** —— 它是"用例没跑完"。
转述时要说"没跑完，卡在 X"，**不要**说成"这个功能不正常"。

### `yaml_writeback`：路径被改动了

跑完若实际走的路径与 YAML 声明不同，执行器会**自动回写 `target`**，
并把改动写进报告的 `yaml_writeback.changed`：

```
s3：YAML 原写 rid=oldImportBtn
   实际走 key=back → rid=btnImportFromGallery
```

这是**正常且有益**的：YAML 本来就只是参考，跑一次把它校准一次。

> ⚠️ **只有代码直点（强证据）过的步骤才会回写。**
> 模型自己摸索出来的路径**不写回** —— 那是模型的一次性判断，
> 不代表这个路径稳定，写进去反而会误导下一次。

报告时要提一句：
- 改了几步 / 哪几步
- 为什么改（原目标没找到？还是找到了但路径不同？）

⚠️ **只改路径，绝不改 `landing:` 和 `asserts:`** —— 那是验收标准。
如果你觉得**标准本身**不对，**要单独向主 Agent 报告**，由人决定。

## 你要如实回报给主 Agent

- **不要美化**：`give_up` 和死循环终止都是真实结论，不要写成"环境不支持"
- **不要归因**：只说"点 X 后屏幕停在 Y"，不要猜"因为 Z 异常"
- **权限要提**：报告里授予了权限就说，那改了设备状态
- **失败也给证据**：报告里有坐标、activity、时间线
- **`steps_done=0` 就直说"一步都没跑"**，不要包装成"用例有问题"
- **YAML 改动要提**：`yaml_writeback.changed` 非空就说改了哪几步
- **标准有疑问要单独提**：如果怀疑 `asserts` 本身写错了（不是路径的问题），
  明确说"疑似用例描述与实机不符，需要人确认"，**不要自己改断言**

主 Agent 会拿着你的报告下结论，**美化和归因会直接变成错误的产品判断**。
