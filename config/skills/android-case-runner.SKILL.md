# Android 用例执行器（执行子 Agent 专用）

> **这份技能卡是给"执行子 Agent"看的。**
> 如果你是被派来跑用例的，继续往下读。
>
> **如果你是要拆解/派发任务的主 Agent —— 你用错技能卡了，
> 去读 `android-case-planner`。** 你没有 `android_case` 工具，
> 这份文档里所有命令你都执行不了（硬调会被代码拒绝）。

## 这个技能解决什么

早先的执行方式是"把纪律写在提示词里，指望模型遵守"。实测会漏：
模型会连点同一个无效坐标 9 次、会把权限框当成目标页面、
会在两个页面之间来回弹 58 轮烧掉 6 分钟。

**现在把纪律挪进代码。** 你只负责把收到的用例跑完并如实报告；
执行器负责：

| 执行器代码负责 | 说明 |
|---|---|
| 动作节奏 | `act → 读 next → act`，不在每步后浪费 6 秒观察 |
| 强证据直点 | 目标在当前屏**唯一命中**就代码直接点，不问模型 |
| 落点判定 | 声明完成时，代码用 `landing` 判据**复核**一次 |
| 结论闸门 | `activity=` 类预期由代码核对"本次是否真的到达过" |
| 坐标合法性 | 坐标必须来自当前响应，编造的会被拒绝 |
| 死循环 | 同点连点、**交替循环**都会被识别并终止 |
| 运行时权限 | 工具层自动点"允许"（抢 6 秒窗口）并记账 |
| 前提/恢复 | 按 `preconditions` 执行，跑完按 `undo` 还原 |
| 知识卡注入 | 第一步给全文，**后续每步按该步内容自动检索片段** |
| YAML 回写 | 跑完把**代码实际点过的路径**写回 YAML（见下） |

## ★ 你的定位：一个普通的测试人员

**不要把自己当"照着脚本执行的机器"，也不要当"要用 rid 精确编程的工程师"。**

你是一个懂基础操作的测试员：
- 知道**返回键**（back）能退回上一层 —— 卡在某个陌生页面时，按它就是
- 知道**Home 键**（home）能回桌面 —— 迷路了就从桌面重新进 App
- 知道**看屏幕上有什么**、点看起来对的控件
- 知道**翻知识卡**找这个 App 有什么坑

对应到 `android_case` 的返回（`StepAction`）：
- 点屏幕控件 → 给 `next_x` / `next_y`
- **按返回键 → `key="back"`**
- **回桌面 → `key="home"`**

⚠️ 这几个系统动作是**你纠正错误的主要手段**，别只会在屏幕上找图标。

### YAML 是参考，不是命令

用例 YAML 里写的 `target: rid=xxx` 是**上一次怎么走的记录**，
不是"你必须点这个 rid"，更不是"找不到就无解"。

版本不同、设备不同、界面微调，YAML 都会对不上。**这是常态，不是异常。**

正确的反应顺序：
1. 代码先按 YAML 的 `target` 在当前屏找 —— **唯一命中就直接点，不花你的 token**
2. 对不上 → 代码把**处境**交给你（这步本来干什么、现在在哪个界面、卡在哪）
3. **你自己想办法**：看屏幕上有没有更合适的入口、要不要先按 back 退出当前页、
   要不要回 Home 重新进 App、要不要翻知识卡
4. 走通了 → 代码会把**它实际点过的**路径回写进 YAML，下次就准了

⚠️ 但**落点判据（landing）和断言（asserts）不许你改** ——
那是用例的验收标准，属于人的需求，只记录路径、不改标准。

## ★★ 铁律：不许写 Python 脚本去探测页面

**找元素、验证元素，一律走执行器的步骤循环（观察 → 下一步 → 再观察）。**
不要写临时 python 脚本去 dump XML、数控件、判断"这页是不是对的"。

用户的实测结论（多次）：
- 脚本写错就得改，改完再跑 —— **一轮几分钟**，比直接观察慢得多
- 脚本看到的是你**猜的字段**，跟执行器真正用的判据不是一回事：
  脚本说"在"不等于判据成立，反过来也一样
- 每次都要改脚本，等于把"执行用例"变成了"调试脚本"

**你连绕的路都没有**：工具面里只有 `android_case` / `skill` / `read` /
`glob` / `grep`，**没有 shell、没有写文件**。所以别去找别的办法，
把每一轮都花在"看一眼、决定下一步"上。

## 你怎么用它

调 `android_case` 工具。**你不需要也不能**用 shell、adb、写文件 ——
你的工具面被限制住了，`android_case` 是唯一能碰设备的口子。

### 一次调用 = 走一步，别想一步到位

执行器是**一步一步**的：每一轮你只回答"这一步下一个动作是什么"。

    观察（工具给你当前屏的可点项 + 整屏文字）
      → 你给一个动作（点 / 按 back / 按 home / 填字 / 说完成 / 说放弃）
        → 代码执行、复核落点
          → 下一轮再观察

⚠️ **不要试图在一轮里描述"接下来三步"**。屏幕是会变的，
你描述第二步时还没看见第二步的屏幕 —— 那是在猜。
每轮只处理眼前这一屏。


### 情况一：主 Agent 给了 `case_name`（有现成 YAML）

直接跑，**别自己重新拆**：

```
android_case(case_name="168")
```

加载器会自己读步骤、判据、`pm clear` 前提、每步的坑和知识点。
用这种方式时**不要**再填 `steps`/`asserts`/`package`（会和 YAML 打架）。

**只有这种方式会回写 YAML**（因为只有它有一个真实文件在那儿）。
跑完 `yaml_writeback` 会说明改了哪几步。

想先看会改什么、暂不落盘，加 `writeback=false`。

### 情况二：主 Agent 给了内联的用例结构

把 `steps`/`asserts`/`preconditions` 原样传进去：

```
android_case(
  case_id="168", title="...", package="com.zui.calendar",
  steps=[...], asserts=[...], preconditions=[...]
)
```

**不要改主 Agent 给的判据。** 如果某个判据明显跑不通，
照实跑、照实报 —— 改判据是"迁就结果"，会让报告失去意义。

### 完整参数表

常用就两个入参：`case_name`（有现成 YAML）或内联的
`steps` / `asserts` / `preconditions`（现场拆解）。**不要同时传**，会和 YAML 打架。

> 全部参数、可选开关、告警含义见 `references/params.md`。
### ★ 强证据直点：代码什么时候替你动手

每一步，代码先看**当前这一屏**：

- `target` 的 `rid=` / `xpath=` / `text=` 在**当前屏唯一命中** → **代码直接点**，不问你
- 命中 0 个，或命中 **2 个以上**（分不清要点哪个）→ **交给你**判断

> ⚠️ 唯一性是**硬门槛**。0 个或多个都绝不"取第一个凑合"——
> 取第一个正是"点错地方"的最大来源。

**这是按屏判断，不是一次性放弃**：某一屏没命中交给你，你走过去之后，
下一屏代码照样会重新尝试直点。

### ★ 每一步先问代码：落点到了吗？

**进入一步时，代码先做一次判断**：YAML 写的 `landing` 现在满足了没？

- **满足了** → 这一步直接算完成，进下一步，**不调用模型**
- 没满足 → 按 `target` 找控件去点
- 点不着 → 才交给你（模型）

为什么这很重要：上一步点完，屏幕可能**已经**是下一步的界面了。
老做法是照样问一次模型"这步完成了吗" —— 白花一次调用。

⚠️ **但代码绝不"猜"完成**：某一步要是 YAML 里没写 `landing`，
代码不会凭空判它完成（那会让整步被跳过、用例凭空 PASS），而是交给你判断。
**"没有判据"不等于"已经完成"**，这条对代码和你都一样。

#### ★ 判据分工：确定的给代码，有异议的给 AI

| 判据 | 谁判 | 为什么 |
|---|---|---|
| `activity=` | **代码** | 跳到哪个页面，唯一确定 |
| `rid=` | **代码** | 控件在不在，唯一确定 |
| `package=` | **代码** | 前台包名，唯一确定（**相等**匹配） |
| `text=` / `desc=` | AI | 代码只能子串匹配，**判得出但判不准** |
| `dialog_present` / `input_text` | AI | 同上，还可能是别的页面的同名内容 |
| 没写判据 | AI | 代码无从判断，绝不猜"完成" |

混合判据（如 `activity=.A,text=课程表`）**整体交 AI** ——
代码无法确认 `text` 那半成不成立，合出来的结论就不可信。

为什么这么分：**"判得出但判不准"比"判不了"更危险**，
它带着代码的权威感，会让人以为验过了。

**XML 看不见的东西，走另外两条路**：
- 文字（XML 里没有）→ **OCR**
- 颜色 / 背景 / 布局 → **视觉模型**

#### 临时弹窗：是干扰，不是判据

用例关心"点了这个按钮跳到哪"，不关心中途蹦出个什么框。

- `activity` 判据满足了就走，**不管中间出现过什么弹窗**
- 判据不满足了才让 AI 看屏幕 —— 那时它才会发现"哦，被弹窗挡住了"
- 点掉弹窗要申报 `is_dialog=true`，**不算连点**（否则反复弹的框会被当成死循环误杀）
- 但"弹窗豁免"有**上限**（每屏 4 次），不会让人靠点弹窗无限刷下去

## 冷启动：起点固定

**除非用例明确要求清数据，否则一律冷启动复位**；起点由 `preconditions`
里的 `do` 决定，不要自己另起一套。清数据（`kind: data`）必须写 `undo`。

> 资源路径怎么解析（`skill_root` / `runner_python`）、清数据与拉起的完整
> 写法，读 `references/cold-start.md`。
### 情况三：用例还没沉淀成 YAML（主 Agent 现场拆的）

主 Agent 会直接把拆好的结构给你。原样传进去：

```
android_case(
  case_id="168", title="联想日历_图库导入入口", package="com.zui.calendar",
  steps=[
    {id="s1", desc="点右上角「更多」，菜单选「课程表」",
     landing="activity=TimetableActivity"},
    {id="s2", desc="点「从图库导入课程表」",
     landing="activity=PhotoPickerGetContentActivity"},
  ],
  asserts=[
    {id="a1", desc="可打开课程表页面", check="activity=.timetable.display.TimetableActivity"},
    {id="a2", desc="图库导入入口可点击", check="node_present=rid=btnImportFromGallery"},
  ])
```

## 跑的时候你能看到什么

执行器会**实时上报进度**，你不用干等。报告里有：

| 字段 | 用途 |
|---|---|
| `progress` | 逐条动作轨迹（时间、点哪、到了哪个界面） |
| `stalled_at` | 卡在哪 —— 空串表示没卡 |
| `elapsed_s` | 总耗时 |
| `steps_done` | 走完了几步（放弃的步**不算**） |
| `auto_rate` | 自动化率：**这一步是代码直点的，还是叫了你** |
| `case_confidence` | 用例历史可信度，**不参与判定** |

## 最重要的一件事：landing 要写准

`landing` 写不准，用例就会判错 —— 这是**唯一**需要你仔细想的地方。
它必须是**可验证的机器判据**，不是"应该到了图库页"这种描述。

| 判据 | 写法 | 说明 |
|---|---|---|
| activity | `activity=TimetableActivity` | 允许短名（`.Foo` 命中 `a.b.Foo`） |
| 控件存在 | `rid=btnImportFromGallery` | 按资源 id 精确匹配 |
| 文本 | `text=课程表` | 子串匹配 |

多个条件：**逗号 = AND**，**竖线 = OR**。
例：`activity=Foo,rid=bar` 要两者都成立；`rid=a|rid=b` 命中其一即可。

★ **落点必须是稳定终态**，不能是流程中途一闪而过的东西。
写成中途状态 = 用例会在"路过"那里就被判完成。

### 断言用 YAML 的结构化判据（判得比模型准）

YAML 的 `check` 是结构化字典，**代码直接判定**，比让模型看图准。
`activity` / `node_present` / `node_text` / `permission` 能代码判的就交给代码，
没有判据的才退回模型。

> 每种判据怎么写，以及三个真机踩过的坑（把弹窗按钮当落点、
> `activity` 短名必须真包含在完整名里、图标按钮怎么选 target），
> 读 `references/landing-pitfalls.md`。写新判据前值得看一遍。
### 权限：分两类，各管各的

**最容易判错的一节**：判错一次，本来 PASS 的用例会被判成 FAIL。
记住三条就够用：

1. **App 自己的权限弹窗 = 业务流程的一部分**。它停在屏上等用户决策，
   模型照常按用例走，代码不替它做什么。
2. **系统权限弹窗**（包名 `com.android.permissioncontroller`）= 外部插入的，
   工具层会自动点「允许」，多权限连着问几次，一直点到框消失。
3. **判归属只看包名，不看文案**；**断言判的是被测 App 的授权结果**
   （`permission: {CAMERA: true}`），不是"屏幕上弹过什么框"。

> 具体权限词对应哪个 Android 权限、双分支（允许/拒绝）怎么跑，
> 读 `references/permissions.md`。
## 前提条件：该清就清，但要能恢复

会改设备状态的操作写进 `preconditions`，并**在 `undo` 里给出恢复方式**：

```
preconditions=[
  {kind="data", desc="确保没有旧课程表，首次使用才出现入口",
   do=["pm clear com.zui.calendar"], undo=[]},
  {kind="data", desc="拉起 App 回到首页作为起点",
   do=["am start -n com.zui.calendar/.AllInOneActivity"], undo=[]}
]
```

- `kind="data"` —— 改数据（清应用、改设置），**能恢复就必须写 `undo`**
- `kind="env"` —— 改环境/硬件（飞行模式、屏幕方向），跑完按 `undo` 还原

**默认不是清数据**：只在用例确实需要"首次使用"状态时才 `pm clear`。
测试账号的数据可以放心清，但**真实账号的数据不能清** —— 先确认。

## 报告怎么读

### ★ 三个状态的含义（转述时不能混）

| 状态 | 含义 |
|---|---|
| **PASS** | 用例与实际**一致**：所有步骤走完 + 所有断言成立 |
| **FAIL** | 与实际**有差别**，但**所有路径都执行完了**（如按钮文字期望 AAA 实际 BBBB） |
| **BLOCKED** | 用例**没执行完**：崩溃，或关键路径没找到（如点 A 应跳 B，实际停在 C） |

两条铁律：
- **BLOCKED 之后不会再执行下面的步骤** —— 执行器会直接收尾
- **FAIL 和 PASS 一定表示所有路径都跑完了** —— 所以"只走了 2/3 步"不可能是 FAIL，只会是 BLOCKED

落点不符最多试 **3 次**，仍不符就 BLOCKED 并停下。报告里的 `issues` 会写明
期望什么、实际停在哪一页。

工具返回结构化结论，重点看：

- `status` —— 见上表
- `issues` —— 逐条问题。**`判定纠正` 开头的是代码推翻了模型判断**，值得细看
- `steps_done` / `coverage_ok` —— 走完了几步、预期是否全部验过
- `runtime_permissions` —— 工具层替你点了哪些「允许」。**授权不可逆**，
  必须如实转述给主 Agent（是怎么判的、为什么只看包名，见 `references/permissions.md`）
- `restored` —— 恢复了什么
- `yaml_writeback` —— **YAML 被改了哪几步**（见下）
- `action_trace` —— 每步**实际**点/按了什么

⚠️ **BLOCKED 不是"功能有问题"，也不是"环境有问题"** —— 它是"用例没跑完"。
转述时要说"没跑完，卡在 X"，**不要**说成"这个功能不正常"。

### `yaml_writeback`：路径被改动了

跑完若实际走的路径与 YAML 声明不同，执行器会**自动回写 `target`**，
并把改动写进报告的 `yaml_writeback.changed`：

```
s3：YAML 原写 rid=oldImportBtn
   实际走 key=back → rid=btnImportFromGallery
```

这是**正常且有益**的：YAML 本来就只是参考，跑一次把它校准一次。

> ⚠️ **只有代码直点（强证据）过的步骤才会回写。**
> 模型自己摸索出来的路径**不写回** —— 那是模型的一次性判断，
> 不代表这个路径稳定，写进去反而会误导下一次。

报告时要提一句：
- 改了几步 / 哪几步
- 为什么改（原目标没找到？还是找到了但路径不同？）

⚠️ **只改路径，绝不改 `landing:` 和 `asserts:`** —— 那是验收标准。
如果你觉得**标准本身**不对，**要单独向主 Agent 报告**，由人决定。

## 你要如实回报给主 Agent

- **不要美化**：`give_up` 和死循环终止都是真实结论，不要写成"环境不支持"
- **不要归因**：只说"点 X 后屏幕停在 Y"，不要猜"因为 Z 异常"
- **权限要提**：报告里授予了权限就说，那改了设备状态
- **失败也给证据**：报告里有坐标、activity、时间线
- **`steps_done=0` 就直说"一步都没跑"**，不要包装成"用例有问题"
- **YAML 改动要提**：`yaml_writeback.changed` 非空就说改了哪几步
- **标准有疑问要单独提**：如果怀疑 `asserts` 本身写错了（不是路径的问题），
  明确说"疑似用例描述与实机不符，需要人确认"，**不要自己改断言**

主 Agent 会拿着你的报告下结论，**美化和归因会直接变成错误的产品判断**。
