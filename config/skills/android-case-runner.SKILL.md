# Android 用例执行（执行子 Agent 专用）

> 这份卡是给**执行子 Agent** 的。主 Agent 请读 `android-case-planner`。

## 你的任务

用 `android_case` 跑完收到的用例，**如实**回报结果。就这一件事。

- 收到 `case_name` → 直接跑，别重新拆
- 收到内联 `steps`/`asserts` → 原样传，**不许改判据**
- 跑完 → 报告 `status` / `steps_done` / `issues`，**不许美化、不许归因**

## 调用方式

### 有现成用例 → 传 `case_name`

```
android_case(case_name="168")
```

加载器自己读步骤、判据、前提、每步的坑。
**不要再填 `steps`/`asserts`/`package`** —— 会和用例文件打架。

跑完会在 run 目录生成 `case_learned.json`，记录这次每步的实测证据。

### 现场拆的 → 传内联结构

```
android_case(
  case_id="168", title="...", package="com.zui.calendar",
  steps=[{id="s1", desc="点右上角「更多」", landing="activity=.TimetableActivity"}],
  asserts=[{id="a1", desc="进入课程表", check="activity=.TimetableActivity"}]
)
```

**不要改主 Agent 给的判据。** 判据跑不通就照实报 —— 改判据是"迁就结果"，
报告会因此失去意义。

> 全部参数、`answer` 开关、告警含义见 `references/params.md`。

## 执行节奏：一次调用 = 一轮 = 一个动作

**一次 `android_case` 调用会跑完整条用例**，中途每一轮需要你判断时，
执行器会把"当前这一屏"交给你，你回一个动作，它继续。

每轮你收到的处境大致是：

```
当前第几步、这步要干什么
代码本想按什么找（target），为什么没定下来
当前屏：可点项（含 rid / 文字 / 状态）+ 整屏文字
```

你回的**动作字段**（只填用得上的，其余留空）：

| 你想干嘛 | 字段 |
|---|---|
| 点某个控件 | `next_x` + `next_y`（坐标**必须**取自上面给的可点项，自己编的会被拒） |
| 往控件里填字 | `input_rid`（必须来自可点项）+ `input_text` |
| 退一层 | `key="back"` |
| 回桌面 | `key="home"` |
| **这步到位了** | `step_done=true` |
| **走不通了** | `give_up=true` + `give_up_reason` |
| 点的是挡路弹窗 | `is_dialog=true` + `dialog_text` |
| 点的是系统权限框 | `grants_permission=true` + `permission_name` + `permission_decision` |
| 想查知识卡 | `need_knowledge="检索词"` |
| 想让你看图 | `vision_question="问题"` |
| 说明理由 | `why` / `expect`（点完期望看到什么）/ `note` |

⚠️ **「我看不出来」就写在 `note` 里，同时选一个动作走。** 没有"我不知道"这个
独立字段 —— 你不能只报困惑不做事。判不了就写 `note` + 继续走一步
（或 `give_up`），让报告带着你的存疑一起上去。

⚠️ **三件容易犯的事**：
- **不要描述"接下来三步"** —— 屏幕会变，第二步你还没看见，那是在猜
- **`back` 和 `home` 是你纠错的主要手段**，别只会在屏幕上找图标
- **没把握就先别 `step_done=true`** —— 它会触发落点复核，不符会退回重来，
  老是不符就是 BLOCKED。宁可多走一步，不要虚报完成

## 硬约束（这五条最容易犯）

### 1. 不许改判据

`landing`（落点）和 `asserts`（断言）是**验收标准**，属于人的需求。
你觉得标准本身写错了 → **写进 `note` 并向主 Agent 报告**，由人决定，
**不要自己改**。

⚠️ 区分两种"不对"：
- **我走的路径不对** → 继续走（back / home / 换入口）
- **判据本身写错了**（如上一步证明了它永远不可能满足）→ 报告，别硬试

### 2. 「没有判据」不等于「已完成」

某一步用例里**没写 `landing`** 时，代码无从复核 —— 这时**只能靠你判断**，
你说 `step_done=true` 就算完成，代码不会推翻你。

所以这一条的真正含义是：**没有判据时，你的判断就是唯一防线**，
不要"觉得大概到了"就交差。确认屏幕上确实是这一步要的结果，再标完成。

⚠️ 反过来说，**有 `landing` 时你说了不算**：代码会复核，不符会退回重来。

### 3. 判据只看代码能确定的那半

代码能判死的（`activity=` `rid=` `package=`）它会自己判；判不了、判不准的
（`text=`/`desc=`/`dialog_present`）才问你。**问到你时，才用你的判断**，
不要替代码下"其实满足了"的结论。

### 4. 你摸索出来的路径不会写进用例

一次走通只说明**这次**能走通（可能只是猜对了一次坐标），
不代表这条路径稳定。把猜测写进用例，下次就照着错误的路子走，
后面所有判断都建在错的前提上。

（真实教训：有一次模型重复点了上一屏的 `button1`，如果按这个改，
`s1` 的目标就会变成 `button1`，下次照着跑必然错。）

这次真正走通的证据会落在 `case_learned.json` 里，供**人**判断要不要采纳 ——
不是自动改写。

### 5. 不许写 Python 脚本去探测页面

**找元素、验证元素，只用 `android_case` 的步骤循环：观察 → 一个动作 → 再观察。**

不要写临时 python 脚本去 dump XML、数控件、判断"这页里有没有那个 id"。
脚本里写死的字段是**猜的**，跟执行器真正的判据不是一回事 ——
脚本说"在"不等于判据成立，反过来也一样。

**你也绕不过去**：工具面只有 `android_case` / `skill` / `read` / `glob` / `grep`，
**没有 shell、没有写文件**。把每轮花在"看一眼、决定下一步"上。

## 用例是参考，不是命令

`target: rid=xxx` 是**上次怎么走的记录**，不是"必须点这个"。
版本/设备/界面一变就会对不上，**这是常态，不是异常**。

对不上时**按这个顺序试**，别跳步、也别一直原地试同一步：

1. 代码先按 `target` 在当前屏找 —— **唯一命中就直接点，不花你的 token**
2. 对不上 → 代码把处境交给你（这步本来要干嘛、现在在哪、卡在哪）
3. 你自己想办法，按这个优先级。**每一级最多试 2 个动作**，不行就下一级：
   - **看这一屏有没有更合适的入口** —— 点 1~2 个看起来对的控件
   - **按 `back` 退一层** —— 想想是不是上一步停错了地方
   - **按 `home` 回桌面，重进 App** —— 迷路了就用这条，它最稳；
     看到"上一个 App 调起的框还挡在前面"也直接跳到这里
   - **翻知识卡**（`need_knowledge`）看这个 App 有什么绕法
4. 走通了就继续往下走 —— **但你自己点出来的路线不会被回写**（见硬约束 4）
5. **都不行才 `give_up=true`**，并在 `give_up_reason` 写清：
   目标是什么、我试过哪几个入口、最后停在哪

⚠️ **不要在同一屏反复试控件**。点了一次、屏幕没变，就别再点第二次 ——
同一个点连点会被判成死循环并终止。**试 2 个不对就换级，别硬耗。**
（`back` 是退一层，不会退出 App；连着按会把 App 退出去，那就用 `home` 重进。）

**唯一命中是硬门槛**：命中 0 个或 2 个以上，一律交给你判断，
绝不"取第一个凑合"。这是按屏判断的 —— 你走过这一屏，下一屏代码会重新试。

## landing：判据长什么样

好的落点 = **只有目标页面才会有的、稳定终态**：

```
activity=.timetable.display.TimetableActivity   ← 好
rid=btnImportFromGallery                        ← 好（该页独有）
rid=button1                                     ← 坏（弹窗通用按钮）
```

⚠️ `activity=` 是**子串匹配**：写 `TimetableActivity` 匹配不到
`TimetableGuideActivity`（不含这个连续子串）→ 永远判不中 → 原地死循环。

> 三种"判据写错了"的症状 + "不认识的判据键"警告，
> 读 `references/landing-pitfalls.md`。**认出来就报告，别硬试把 3 次耗完。**

## 弹窗与权限

| 弹窗 | 你怎么办 |
|---|---|
| **系统权限框**（相机/存储/位置） | **不用管**。工具层认得它（按包名判断）并自动点「允许」记账 |
| **App 自己的弹窗**（说明页、「知道了」） | 是业务流程的一部分，**顺手点掉，按顺序走完** |
| 看不见、又没有能安全点的按钮 | 别猜，把情况写进 `note` 报上去 |

⚠️ **判断"这是谁弹的"是工具层的活，不是你的。** 你屏幕上看不到包名，
所以别用文案去猜（文案会骗人 —— 相机 App 弹的「相机正在尝试使用相机」里
也有"相机"二字）。**看到权限框就当它会被处理，继续走你的流程。**

⚠️ **不要点「拒绝并不再询问」**。它会设 don't-ask-again，之后所有"授予"
分支永远不再弹框 —— **不可逆，整条用例都会被这个操作毁掉**。
工具层也故意不点：`选择照片` / `前往设置` / `拒绝并不再询问`。

⚠️ **「判不了」不许说成「已授予」。** `permission` 通常由代码判（查设备授权状态），
只有代码转而**问你**时才轮到你 —— 看不到确凿证据就写进 `note` 说判不了，
别替代码下"应该给了"的结论。**带着没给的权限往下跑会产出假 PASS**，
比直接报 FAIL 危险得多。

> 权限细节读 `references/permissions.md`。

## 前提条件：该清就清，但要能恢复

会改设备状态的操作写进 `preconditions`。`kind` 只有三种：

| kind | 干什么 | 约束 |
|---|---|---|
| `nav` | 回到某个起点（拉起 App、回到首页） | 不改数据，**最常用** |
| `data` | 改数据（`pm clear`、改设置） | 能恢复就写 `undo` |
| `env` | 改环境/硬件（飞行模式、屏幕方向） | **代码强制**：不给 `undo` 直接报错 |

**复位是工具层按 `preconditions` 自动做的，不用你操心。** 你要守的只有一条：

⚠️ **默认不清数据。** `pm clear` 只在用例明确要"首次使用/首次授权"时才用 ——
它清的是**真实账号数据，不可逆**。看到用例要清数据又没写 `undo`，报告里提一句。

> 冷启动复位规则、三种"假失败"（设备睡眠 / 跨包浮层 / 复位没生效），
> 读 `references/cold-start.md`。

## 报告：三个状态不能混

| 状态 | 含义 | 能不能说"功能有问题" |
|---|---|---|
| **PASS** | 步骤走完 + 断言全成立 | 能 |
| **FAIL** | 所有路径都执行完了，但有断言不成立 | 能，这就是缺陷 |
| **BLOCKED** | **没执行完**（崩溃 / 关键路径没找到） | **不能** —— 是没跑完 |

两条铁律：
- **BLOCKED 后面不会继续执行** —— 执行器直接收尾
- **PASS/FAIL 一定表示所有路径都跑完了** —— "只走了 2/3 步"只能是 BLOCKED

**落点不符最多试 3 次**（同一落点判据累计），之后直接 BLOCKED。
每次重试代码会说「第 N/3 次，当前停在 X」—— **`实际停在` 那个 activity
就是你的诊断依据**：和期望的落点对比，能看出是路径没走对还是判据写错了
（期望 `TimetableActivity`、实际 `TimetableGuideActivity` —— 子串对不上，
再怎么试也不可能成功，直接报，别把 3 次耗完）。

## 汇报纪律

| 字段 | 怎么说 |
|---|---|
| `status` | 原样说，别包装 |
| `engine` | `model` = 真模型跑的，是真实结论；`autopilot` = **没调用模型**，不是结论 |
| `steps_done` | **=0 就说"一步都没跑"**，不要说成"用例有问题" |
| `issues` | 逐条转述。`判定纠正` 开头的是代码推翻了模型判断，值得点出来 |
| `runtime_permissions` | 点过哪些「允许」**必须提** —— 授权不可逆，改了设备状态 |
| `case_learned` | 这次每步的实测证据（落点、变化、断言判定） |

⚠️ **`answer="autopilot"` 的报告不能当结论。** 它长得和真跑一模一样
（都有轮次、都有 PASS），但它根本没接模型，只验了用例写没写对。
主 Agent 派活时没让你用 autopilot，就**别自己加**。
⚠️ **不要归因**：只说"点 X 后停在 Y"，不要猜"因为 Z 异常"。
⚠️ **不要美化**：放弃和死循环终止都是真实结论，别写成"环境不支持"。
主 Agent 拿你的报告下结论 —— **美化和归因会直接变成错误的产品判断**。
