# 执行机制设计

> 本文是**架构约定**，不是现状描述。代码按本文对齐；与本文不符的地方就是要改的地方。

---

## 一、总体职责

```
主 Agent                          子 Agent
────────                          ────────
拆解用例 case                    执行单个 case
  ↓                                ↓
读取/生成用例 YAML       ──→      解析 YAML，拿到每一步的信息
把卡片 + YAML 交给子 Agent         操作真机，判定结果
收结论、汇总                      回报结论
```

**边界（不可破）**

| | 主 Agent | 子 Agent |
|---|---|---|
| 拆解用例 | ✅ 它的活 | ❌ 不拆 |
| 操作设备 | ❌ **绝不碰** | ✅ **只有它能碰** |
| 给资料 | ✅ 给路径 | 自己按需查 |

设备实例只在子 Agent 里创建。主 Agent 在 `run_case()` 之外，**拿不到任何 Device 对象**。

**执行必须在子 Agent 的 LangGraph Node 里进行** —— 不是子 Agent 外面套一个循环，
而是每个阶段本身就是图里的一个节点。这样断点续跑、流式推送、状态流转才成立。

---

## 二、主 Agent 交给子 Agent 的东西

三样，**全是路径，不是内容**：

```
① 用例 YAML 路径        （有的话）
② 路径卡路径            （导航路径图：从 A 页面到 B 页面怎么走）
③ 知识卡路径列表        （每个 App 一份：有什么坑、控件长什么样）
```

为什么要给路径而不是内容：

- 卡片很大（日历知识卡 34552 字符），塞进上下文不现实
- 给了内容模型就被动接收；给了路径它才能**按需查**

**子 Agent 需要细节时自己查。**

### 2.1 知识卡的给法

| 阶段 | 给什么 | 大小 |
|---|---|---|
| 第一步 | 卡片**目录**（有哪些章节、各多少行） | 约 2400 字符（压缩 93%） |
| 需要细节时 | 模型说"查 X"，代码按章节名或关键词取 | 一次一节 |

模型看到目录才知道"有这些可查"，然后自己决定查什么。

## 三、YAML 是**一级参考文件**，不是执行剧本

### 3.0 没有回放机制

**代码不会照着 YAML 一步步把动作重放一遍。**

为什么去掉：YAML 里最"像剧本"的东西是坐标和动作序列，而这两样恰恰最不可靠 ——
换一台设备、换一个分辨率、换一次布局，坐标全废，`[121,1086]` 可能在完全
不相干的控件上。照着重放的结果不是"快"，而是"静默点错地方"。

去掉回放反而更简单：只有一条路 —— **每一步都看当前屏幕决定**。
有 YAML 时它提供的是**"上次是怎么走的"这一层参考信息**，不是指令。

这带来一个直接后果：**`locate_seq`（按顺序一步步重放）这个字段本身就不要了。**
它是回放的载体 —— "第 1 个点这个、第 2 个点那个" 的剧本式写法。
现在只保留 `target`（这一步要点的东西），怎么找到它由当前屏决定。

### 3.1 YAML 里存什么、不存什么

**禁止存坐标。** 坐标是这一刻这一屏的产物，写进文件就是过期数据。

**但每一步的意图必须写清楚、写具体。** `desc` 不是标题，是**给子 Agent 的指令说明**——
它要让人（和模型）一眼知道"这一步到底做什么动作、点哪里"。

```yaml
steps:
  - id: s1
    # ✅ 具体的动作 + 位置 + 预期
    desc: 点右上角「更多」按钮，在弹出的菜单里选「课程表」
    landing: activity=TimetableActivity
    target: xpath=//*[@resource-id="…:id/iv_more"]
    pitfalls:
      - "iv_more 没有 text/desc，只能按 rid 定位"
      - "点完会先弹权限框，不是直接进课程表"

  - id: s2
    # ✅ 说清点哪里、点完看到什么
    desc: 在课程表空状态页点「从图库导入」，进入系统图片选择器
    landing: xpath=//*[@resource-id="…:id/btnImportFromPhoto"]
    target: xpath=//*[@resource-id="…:id/btnImportFromGallery"]

  - id: s3
    # ❌ 太笼统 —— 没说点哪、点到什么程度算完
    desc: 打开课程表

  - id: s4
    do: [{tap: [2697, 371]}]
    # ❌ 存坐标 —— 换设备即失效
```

**`desc` 该怎么写**

| | 不好 | 好 |
|---|---|---|
| 信息量 | `打开课程表` | `点右上角「更多」按钮，菜单选「课程表」` |
| 有无位置 | `导入` | `在空状态页点「从图库导入」` |
| 有无预期 | `处理弹窗` | `点掉 App 内提示框，进入系统图片选择器` |

三个要素：**做什么动作 + 在哪个位置/控件 + 做完应该看到什么**。

现有用例里 `联想日历_168.yaml` 的 desc 就是这个水准，可以作为样板：

```yaml
- id: s1
  desc: 点右上角「更多」，菜单选「课程表」
- id: s3
  desc: 点掉 App 内提示框，进入系统图片选择器
```

加载 YAML 时**遇到坐标字段直接报错**，不给它悄悄生效的机会。

### 3.2 带坐标的旧 YAML：直接删除，重新生成

不兼容、不迁移、不猜测 —— **删掉，用新机制重新跑一遍生成新的。**

理由：旧 YAML 里的坐标不只是"一个过期数字"，它代表整份文件的思路是
"按位置重放"。这种文件即使把坐标剔掉，`locate_seq` 的顺序剧本、
按坐标推断出来的落点判据都还带着旧假设。逐字段修补比重写更容易出错，
而重跑一遍本来只要几分钟。

**删除是程序自动执行的**，在加载时发现即处理：

```
加载 case YAML
   ↓
扫到坐标字段 / locate_seq（旧机制）
   ↓
删掉这个文件（或整份旧格式），并记日志说明删了哪个、为什么
   ↓
按"首次执行"处理 —— 跑完生成新 YAML
```

⚠️ 删除前把原文件内容写进日志，出问题还能翻。
（项目没有 git，删了就是真没了。）

**当前状态**：现有 2 个 YAML（`联想日历_168.yaml`、`_test_invalid.yaml`）
已扫过，**都不含坐标**。但 168 用的是 `locate_seq`，属于旧机制，
需要在新代码里重新生成。

### 3.3 YAML 提供什么价值

| 内容 | 怎么用 |
|---|---|
| `landing`（落点判据） | **强证据**：代码直判，不经过 LLM |
| `target`（目标控件） | **强证据**：xpath 唯一命中就直接点，不经过 LLM |
| `desc`（这步做什么） | **提示文本**给模型，决定走不通时靠它理解意图 |
| `pitfalls`（每一步的坑） | **提示文本**给模型 |

前两样是硬的，代码直接用。后两样是软的，只影响模型怎么想 ——
但 `desc` 写得具体与否，直接决定模型在代码走不通时能不能救回来。

### 3.4 坑要按步给

`pitfalls` 只给**本步**的。跑到第 2 步时第 1 步的坑还在眼前，信息被稀释，
真正相关的那条反而看不见。

### 3.5 YAML 首次生成

**第一次跑完（此前没有 YAML）→ 生成 YAML。**

写入的是：这步做什么（`desc`）、落点判据（`landing`）、
目标控件（`xpath`/`rid`）、踩到的坑（`pitfalls`）。**不写坐标。**

⚠️ `desc` 必须由**执行过程**生成，不能事后让模型凭空总结：

- 实际点了哪个控件（从 trace 里拿 rid/文字）
- 点完之后看到了什么（landing 的实际值）
- 中途踩到了什么意外（弹窗、加载慢、权限框）

拼出来的 desc 才是具体的，例如：

```
desc: 点右上角「更多」（iv_more），菜单选「课程表」，落到 TimetableActivity
```

而不是模型事后回忆写的 `desc: 打开课程表` —— 那种描述生成出来也没用，
下次跑遇到问题，凭它什么都判断不了。

## 四、强证据：代码直接判、直接点，不经过 LLM

这是本文最核心的机制。

### 4.1 什么算强证据

**能唯一定位的事实**，没有解释空间：

| 类型 | 例子 | 为什么是强证据 |
|---|---|---|
| **页面跳转** | `activity=TimetableActivity` | 设备报上来的字符串 |
| **唯一 view** | `xpath=//*[@resource-id="…:id/iv_more"]` | 只有这一个节点 |
| **特有弹窗** | `xpath=//*[@text="允许" and @resource-id="…:permission_allow"]` | 组合条件唯一命中 |
| **文字** | `text=课程表` | dump 里的文字 |

### 4.2 必须用组合 XPath，不能只靠单一属性

**实测踩到的真问题**：设置页里有 4 个节点完全一样 ——

```
rid=''  desc=''  text=''  b=[121,1086][2919,1303]
rid=''  desc=''  text=''  b=[121,1303][2919,1520]
rid=''  desc=''  text=''  b=[121,1520][2919,1737]
rid=''  desc=''  text=''  b=[121,1737][2919,1849]
```

只按 `rid=` 定位，或者只按 `text=` 定位，**根本分不出是哪个**。
点错一个，整条用例就废了。

所以判据要写成组合条件：

```xpath
//*[@resource-id="com.zui.calendar:id/iv_more" and @clickable="true"]
//*[@text="课程表" and @class="android.widget.TextView"]
//*[@resource-id="…:id/list"]//*[@text="全部课程表"]
```

甚至加上层级（父节点约束）：

```xpath
//*[@resource-id="…:id/menu"]//*[@text="课程表"]
```

### 4.3 命中数校验

一条 XPath 命中几个节点，决定了它能不能当强证据：

| 命中 | 处理 |
|---|---|
| **1 个** | ✅ 强证据，直接用 |
| **0 个** | ❌ 判据不成立 → 交 LLM 判断/修复 |
| **>1 个** | ⚠️ **不算强证据** → 交 LLM 判断，或要求 YAML 补充条件 |

> "命中 >1 时不能直接判" 这条必须由代码守住 —— 这是唯一能防止"点错元素"的关卡。

### 4.4 强证据直达的三种情况

**情况 A：验证点判定（判"到没到"）**

```
判据：xpath=//*[@resource-id="…:id/btnImportFromPhoto"]   （命中 1 个）
实际：屏幕上有这个节点
→ 代码直接判"满足"，不问模型。
```

**情况 B：动作跳转确认（判"点对了没"）**

```
点了"更多" → 期望出现菜单项"课程表"
代码判定：xpath=//*[@text="课程表"] 命中 1 个？
  是 → 直接进下一步
  否 → 交模型看怎么办
```

**情况 C：直接点（不问模型"点哪"）**

这是去掉回放后**唯一**的代码直点路径 —— 依据不是"上次点过这里"，
而是"这一步的目标在**当前屏**上有唯一确定的位置"：

```
YAML 里 turn: target=xpath=//*[@resource-id="…:id/iv_more"]
当前屏 XPath 命中：1 个 → 取它的坐标直接点，不问模型
                  0 个 → 目标不在，交模型
                 >1 个 → 不唯一，交模型
```

关键区别：**它不认"上次点了哪"，只认"现在能不能唯一确定"**。
所以换设备、换分辨率都不影响 —— 命中唯一这件事和像素无关。

### 4.5 什么交给 LLM

**判不了的，能判但结果不成立的，以及不唯一/找不到的。**

| 情况 | 交谁 |
|---|---|
| 强证据命中唯一 → 成立 | 代码，**不经过 LLM** |
| 强证据命中唯一 → 目标有唯一位置 | 代码**直接点**，不经过 LLM |
| 强证据命中唯一 → 不成立 | **LLM**（要不要修、怎么修） |
| 强证据命中 0 或多 | **LLM** |
| 颜色/布局/视觉外观 | **视觉模型** |
| XML 看不到文字 | **OCR** |

**"判不了"绝不等于"已完成"** —— 没有可靠判据时不能默认跳过这一步。

### 4.6 回退给模型是**按屏**的，不是永久的

代码在某一屏上认不出目标，只说明**这一屏**认不出。
屏幕一变（换 activity、换包名、可点控件集合变了），必须**重新给代码一次机会**。

真机踩到的坑（168，80 轮全是模型、代码直点 0 次）：

先是代码判不出 → 交给模型 → 状态里记下"本步已交给模型" →
之后每一轮都读到这个标记 → **再也不回代码**。
强证据直点这一整套机制，实际一次都没跑起来。

所以"已交给模型"这个标记必须绑定到**当屏**：
同一屏上不跟模型抢（免得来回拉锯），换屏就重新判定。

同理，轮次计数只在**换步**时归零。放在"每次进入步骤"都归零的话，
依赖它的判断（"落点已满足就跳过本步只在刚进来时做一次"）会永远成立 ——
用例写成"从 A 到 A"时，一步没走却报 PASS。

### 4.7 系统权限框：代码自动处置，只记账不进 YAML

**这一类弹窗不是被测对象的业务，是 Android 平台的标准流程。**

系统权限框有一个硬约束：**约 6 秒没人点就自动消失**。
而"该同意还是该拒绝"要读用例语义（慢）。决策慢、窗口短 ——
所以必须在**动作返回的那一刻**就地处置，不能等下一轮：

```
点击/按键 → 立刻检测权限框（0.8s 窗口）→ 有就按意图点 → 框没了才继续观察
```

没接这一步的后果是真机验证过的：权限框自己消失了，
后续所有点击都落在不存在的框上，整条用例空转到轮次上限。

#### 归谁：只看包名，不看文案

```
com.android.permissioncontroller  ← 系统权限框（固定，跨设备通用）
com.zui.calendar                  ← 被测 App 自己的界面/弹窗
```

曾用"权限名 → 文案特征词"去猜归属，是错的：相机 App 弹的
「相机正在尝试使用相机」里也有"相机"二字，会被当成被测 App 申请。包名唯一确定。

**归属包名要在权限框弹出之前取** —— 取晚了，前台已经是权限框自己，
归属就记错了。多权限申请时同一个框里连点几次，申请方在整条链上不变，
所以框已在前台时沿用上一次记下的。

#### 两类权限的处置不同（关键）

| | 普通运行时权限 | 内容型权限 |
|---|---|---|
| 例子 | 通知、日历读写、设备信息 | 相机、照片视频、麦克风、定位 |
| 不给会怎样 | 某个功能不可用，**流程照走** | **流程根本走不下去** |
| 判定要求 | 记账即可，失败不阻断 | 必须确认**真的授予了** |
| 依据 | 默认同意 | `dumpsys package` 复查授权结果 |

"点过允许按钮" ≠ "授权成功"。内容型权限没真授予，下一步必然进不去 ——
所以这类要拿 dumpsys 的 `granted=true` 当判据，而不是看屏幕上弹过什么。

**判不了 ≠ 已授予。** dumpsys 取不到、权限名对不上，就如实记"未能确认"，
绝不默认成"已授予"。

#### 记录，但不写进 YAML

用户原话：

> 这种权限的我们只点击记录点击了哪些个权限。
> 操作步骤不记录到 yaml 里面。因为都是按照标准走。

道理：系统权限框是平台标准流程，每个 App 都一样 ——「拒绝 / 允许」两个按钮、
rid 固定、位置由系统决定。写进用例 YAML 没有任何信息量，只会：

- 让用例文件变脏，人看不出哪几步才是这个 App 的业务链路
- 把"平台通用行为"冒充成"这个 App 的经验"，误导后来人
- 跨 Android 版本 rid 变了，写死的判据反而失效

但**点过什么必须留下** —— 授权是不可逆的现场变更，审计要查。
所以分两个出口：

```
点过的权限 → report.runtime_permissions / runtime_permission_prompts（留着）
权限框动作 → 永不进入 YAML（writeback / generate 两道都过滤）
```

## 五、单步执行：全部在 LangGraph 节点里

每一步是一个明确的阶段，每个阶段是图里的一个节点：

```
      ┌─────────────────────────────────────────────┐
      │                                             │
      ▼                                             │
 ┌──────────┐                                       │
 │ observe  │  XML+截图落盘，返回可点清单             │
 └────┬─────┘                                       │
      │                                             │
      ▼                                             │
 ┌──────────┐  从落盘 XML 查                         │
 │  judge   │  这一步的落点判据成立吗？                │
 └──┬────┬──┘                                       │
    │    │                                          │
 成立│    │不成立 / 判不了                           │
    │    ▼                                          │
    │ ┌──────────┐                                  │
    │ │  LLM 判  │  或交视觉模型 / OCR                │
    │ └────┬─────┘                                  │
    │      ▼                                        │
    │ ┌────────────────┐                            │
    │ │       act      │  下一步点哪？               │
    │ │                │                            │
    │ │ 先问代码：      │                            │
    │ │ target 的 xpath │                            │
    │ │ 命中唯一？      │                            │
    │ │   是 → 直接点    │ ← 不问模型                  │
    │ │   否 → 问模型    │                            │
    │ └───────┬────────┘                            │
    │         ▼                                     │
    │      点击 ────────────────────────────────────┘
    ▼
 ┌──────────┐
 │  next /  │
 │  done    │
 └──────────┘
```

> **没有"按 YAML 重放"这条分支。**
> 有 YAML 时，YAML 只提供两样东西：落点判据（判"到没到"）、
> 目标控件（判"点哪"）。两者都必须**在当前屏上唯一命中**才生效。

### 5.1 observe 节点：XML 落盘，只给可点控件

**XML 不进上下文。**

一份日历首页 dump 约 34000 字符 ≈ 1.7 万 token，每轮都带、几十轮就是百万 token，
而其中 95% 是布局容器 —— 模型根本用不上。

**做法**：每次观察把三样东西写到磁盘，**只把路径和可点清单**交给上层。

```
storage/evidence/<case>/step01/
    dump.xml     ← 45 KB，全量落盘，不进上下文
    shot.png     ← 355 KB，只在需要视觉判断时才读
    meta.json    ← activity / package / 尺寸 / rotation
```

返回给子 Agent 的东西：

```python
Screen(
    xml_path  = "…/step01/dump.xml",   # 路径，不是内容
    shot_path = "…/step01/shot.png",
    clickable = [                       # 只有可点的，实测 7 个
        {i:0, r:"",       t:"返回",     c:[154, 203]},
        {i:1, r:"button2", t:"卸载",     c:[847, 903]},
        {i:2, r:"button3", t:"强行停止",  c:[2191, 903]},
        …
    ],
)
```

**只取 clickable=true 的**，不要整棵树。一屏通常十几个，模型扫一眼就看完；
整棵树几百个节点，模型反而抓不住重点。

### 5.2 验证时直接查落盘的 XML，不再截图

这是关键优化：**同一个界面的判据，全部从落盘文件查**。

```python
scr.xpath_count('//*[@resource-id="…:id/button2"]')   # → 1，命中唯一
scr.xpath_center('//*[@resource-id="…:id/button2"]')  # → [847, 903]
scr.has_text("卸载")                                   # → True
scr.find_rid("button2")                               # → 可点项
```

好处：

- **不用重新 dump** —— 一次观察的数据能回答该界面上的所有判据
- **不用截图** —— 文字/控件类判据根本不需要图
- **不占上下文** —— 查出来的只是一个数或一个坐标

只有在需要**颜色/布局/视觉外观**判断时才读 `shot.png` 交给视觉模型。

### 5.3 坐标系

`rotation` 会变，宽高跟着换，所以每次现取 `window_size`，绝不缓存。
（实测抓到过：横屏快照 3040x1904，转竖屏后 1904x3040。）

### 5.4 judge 节点

按第四节的规则走。**强证据命中唯一就出结论，直接路由到 next，不调 LLM。**

判据全部从**落盘的 XML** 查，不重新 dump、不截图：

| 判据 | 怎么查 |
|---|---|
| `activity=XxxActivity` | 比 `screen.activity` |
| `xpath=//*[@resource-id="…:id/x"]` | `screen.xpath_count(expr) == 1` |
| `text=课程表` | `screen.has_text("课程表")` |
| 颜色 / 布局 / 外观 | 读 `shot.png` 交视觉模型 |

### 5.5 act 节点：先问代码，再问模型

**决策顺序是固定的 —— 代码先、模型后。**

**第一步：这一步的目标控件，在当前屏上能不能唯一确定？**

```yaml
- id: s1
  target: xpath=//*[@resource-id="…:id/iv_more"]   # 或 rid=iv_more
```

```python
n = screen.xpath_count(target)
  1  → 取坐标直接点，**全程 LLM 零介入**
  0  → 目标不在当前屏，进第二步
 >1  → 不唯一，进第二步
```

这就是"强证据可以直接点，不用问模型"。它成立的前提只有一个：
**当前屏上只有一个节点符合条件**。这和"上次点过这里"无关，
所以换设备、换分辨率都不影响。

**第二步：代码定不了，才问模型**

模型看到的只有可点清单（十几个），不是整棵树：

```json
{
  "step": "s1",
  "desc": "点右上角「更多」按钮，在弹出的菜单里选「课程表」",
  "clickable": [{i:0, r:"iv_more", t:"更多选项", c:[2835,203]}, …],
  "hints": [
    "上次是怎么走的：点 iv_more（iv_more 没有 text/desc，只能按 rid 定位）",
    "点完会先弹权限框，不是直接进课程表"
  ],
  "question": "下一步做什么？"
}
```

模型靠 `desc` 知道**这一步要干嘛**，靠 `clickable` 知道**现在能点啥**，
靠 `hints` 知道**上次踩过什么**。

这就是 desc 必须写具体的原因：代码走不通时，模型只能凭它理解意图。
`desc: 打开课程表` 这种描述，模型看完还是不知道该点哪个。

注意 `hints` 是**提示**，不是命令。模型可以参考，也可以判断它不适用。

模型回一个动作，代码**校验**坐标必须在本次清单里，不合法就打回重选。

## 六、设备操作：直连，不起命令行

**不起 subprocess。**

老实现每个动作都 `subprocess.run([python, run.py, "act", …])` ——
一次点击起一个进程（约 1.5s 冷启动），一轮"观察→点击→观察"就是三个进程。

现在是普通函数调用：

```python
scr = dev.observe()                          # 落盘，返回可点清单
n   = scr.find_rid("iv_more")                # 从清单找，不查 XML
hit = scr.xpath_count('//*[@resource-id="…:id/x"]')   # 从落盘 XML 查
dev.act(n["c"][0], n["c"][1])                # 点完自动再观察一次
```

实测：

| 操作 | 耗时 |
|---|---|
| `observe()`（XML + 截图 + 落盘） | **1.17s** |
| XML 大小 | 45 KB（**不进上下文**） |
| 返回给模型的可点控件 | **7 个** |
| XPath 从落盘文件查 | 即时（只在内存解析一次） |
| OCR 首次（含模型加载） | 13.8s |
| OCR 后续（复用模型） | 7.7s |

好处不只是快：状态直接进 LangGraph state，图的能力（断点续跑、流式推送）不被挡住。

**代价**：老的会话 / 证据台账 / 审计没有了。那些是 subprocess 时代为"跨进程追踪
一次动作"而存在的。现在动作和状态在同一条调用栈上，直接记在 `Screen` 和返回结果里。

## 七、防死循环：按进展停，不按时间停

**绝不设时间上限**。停的条件全是"有没有进展"：

| 条件 | 阈值 |
|---|---|
| 总轮次上限 | 80 |
| 同一目标连续无进展 | 3 次 |
| 两点间来回循环 | 检出即停 |
| 崩溃 | 硬终止，**永不重试** |
| 模型给出非法坐标 | 打回重选，连续 3 次才放弃 |

**唯一可安全重试的情况：`executed=False`**（动作确实没执行）。
动作执行了就不能重放 —— 会点两次。

## 七之二、用例状态：PASS / FAIL / BLOCKED

三个状态的边界是**死的**，不是"看起来差不多就报一个"。

| 状态 | 含义 | 判据 |
|---|---|---|
| **PASS** | 这个 Case 与实际**一致** | 所有步骤走完 + 所有断言都成立 |
| **FAIL** | 与实际**有差别**，但所有路径都**执行完成了** | 步骤全走完、断言全验到，其中有断言不成立 |
| **BLOCKED** | 这个 Case **没执行完** | 崩溃、关键路径没找到、或断言没验全 |

### 两条铁律

1. **报 BLOCKED 就不再执行下面的步骤。**
   既然没执行完，后面的步骤和断言就没有依据。
   路由层强制：状态一旦是 BLOCKED，`route_after_plan` /
   `route_after_strong` 直接去 `finish`，不会再多点一次设备。

2. **报 FAIL 或 PASS，一定表示所有路径都执行完成了。**
   所以"步骤只走了 2/3"永远不可能是 FAIL —— 那是 BLOCKED。

### 典型场景对照

| 现场情况 | 状态 | 为什么 |
|---|---|---|
| 点 A 应跳 B 页，实际停在 C 页（试满 3 次） | **BLOCKED** | 关键路径没找到，用例没执行完 |
| 按钮文字期望 AAA，实际 BBBB | **FAIL** | 路径走完了，结果与预期不符 |
| 3 步走完，5 条断言只验到 3 条 | **BLOCKED** | 验收不完整，不能算 PASS 也不能算 FAIL |
| App 崩溃 | **BLOCKED** | 没执行完 |
| 全部走完且全部成立 | **PASS** | —— |

### 落点不符：最多试 3 次

`LANDING_MAX_TRIES = 3`（含首次）。

- 为什么不是 1 次：页面还在加载时会被误判
- 为什么不是更多：同一动作重复三次都到不了目标页，说明**路径本身不成立**，
  继续试只是烧时间，还会让"关键路径没找到"这个结论变模糊

试满后置 BLOCKED 并记录**实际停在哪一页**，便于人工判断是不是产品缺陷。

### 判断口诀

只问一句：**"这个用例跑完了吗？"**

- 跑完了且全对 → **PASS**
- 跑完了但有不对 → **FAIL**
- **没跑完（任何原因）→ BLOCKED**

崩溃、路径没找到、拿不到屏幕、参数不合法、进程中断 —— 都只是 BLOCKED 的不同成因，
写在 `summary` 里说清楚就够了，不需要多一个状态码。

### 10.1 用例状态（2026-02 定稿）

| 问题 | 结论 |
|---|---|
| 状态有几档 | **只有三档**：PASS / FAIL / BLOCKED |
| PASS 的含义 | 与实际**一致**：所有步骤走完 + 所有断言成立 |
| FAIL 的含义 | 与实际**有差别**，但**所有路径都执行完了**（如文字期望 AAA 实际 BBBB） |
| BLOCKED 的含义 | **没执行完**：崩溃、关键路径没找到、断言没验全 |
| BLOCKED 之后还继续吗 | **不继续**。路由层直接去 `finish`，一步都不再往下走 |
| FAIL/PASS 能表示"没跑完"吗 | **不能**。"3 步只走了 2 步"只能是 BLOCKED，永远不是 FAIL |
| 落点不符算 FAIL 吗 | **不算**。试满 3 次仍不符 → BLOCKED（关键路径没找到） |
| 落点不符试几次 | **3 次**（含首次），常量 `LANDING_MAX_TRIES` |
| 为什么是 3 次 | 1 次太急（页面在加载会误判）；更多没意义（三次都到不了说明路径本身不成立） |
| 崩溃归哪一档 | BLOCKED（"没执行完"） |
| 主 Agent 越权被拒 | BLOCKED（一步都没跑） |
| 参数写错 / JSON 不合法 | BLOCKED（一步都没跑） |
| 僵尸会话被清理 | BLOCKED |
| 判断口诀 | 只问"**这个用例跑完了吗**" —— 跑完且全对 PASS；跑完但有不对 FAIL；**没跑完就是 BLOCKED** |

### 10.2 代码怎么强制这些规则（不靠自觉）

| 规则 | 强制手段 |
|---|---|
| BLOCKED 后不再执行 | `route_after_plan` / `route_after_strong` 开头就判 |
| 落点不符只试 3 次 | `LANDING_MAX_TRIES` 常量 + `plan` 里的计数 |
| 落点不符不判 FAIL | `verdict` 里该分支写 `"BLOCKED"` |
| FAIL/PASS 必须跑完 | `verdict` 的判断顺序：步骤数、断言数都在 FAIL 之前 |
| 状态只有三档 | `db.STATUSES` 全集校验 + 全仓库扫描 |
| 文档与代码不脱节 | `test_case_status_semantics.py`（26 项）、`test_status_runtime.py`（7 项）、`test_no_error_status.py` |
