## 二、BLOCKED / FAIL / PASS 三态（不能混）

| # | 保护 | 原因 |
|---|---|---|
| 7 | **"判不了" ≠ "判失败"** | 模型回 `null` 时记 BLOCKED，不能当 FAIL —— 那是**替产品下结论** |
| 8 | **`passed is None` 必须显式判断** | `bool(None)` = False，会把"没验成"静默算成"功能坏了" |
| 9 | **模型回复无法解析 → UNKNOWN** | 不是 FAIL。报告里写明"模型回复无法解析"，让人能区分执行问题 vs 产品问题 |
| 10 | **落点未达成要算进结论** | 167：3 步落点全不符（steps_done=0），却报 PASS |

## 九、节点合并（15 → 8）

```
旧：prep / start_check / prep_apply / plan / strong_target / observe
    / decide / knowledge / vision / act / check / assert / verdict / learn / finish

新：
  prep     准备（合并 start_check + prep_apply）
  plan     进入一步（合并 observe）
  decide   AI 决定（合并 strong_target + knowledge + vision）
  act      执行
  check    走完了吗
  verify   验本步预期（合并 assert + verdict）
  learn    回写
  finish   结论
```

**⚠️ 合并的限制：**

- `assert` + `verdict` 之所以分开，是因为 interrupt 恢复时节点从头重跑 ——
  **不能在同一个节点里既问又答**。合并时要保留这个两段式，或者用别的方式。
- `prep_apply` 从 `plan` 也要能到达（起点纠正期间会跳过它，而 plan 是每步必经点）。
