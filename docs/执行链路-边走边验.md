# 执行链路：边走边验

> 2026-10-22 定稿。这一版推翻了"走完全部步骤再回头验"的旧链路。
> 与本文不符的代码就是要改的地方。

---

## 一、一句话

**AI 边走边验。一步走完，人正好停在该看的那一屏，就地把它名下的预期验掉。走完直接写 JSON。**

不存在"回头重新验证"这个环节。

---

## 二、为什么改

旧链路：

```
走完所有步骤 → assert 节点回头逐条验 14 条断言
```

问题：**验的时候人早就不在那一屏了。**

实测证据（run 81，PASS 8 / FAIL 6）：

| 断言 | 判定时人在哪 | 该在哪 | 结果 |
|---|---|---|---|
| a2 | 课程表引导页 | 编辑页 | FAIL（判错） |
| a4/a5/a6 | 课程表显示页 | 空课表 | FAIL（判错） |
| a14 | 课程编辑页 | 弹窗已关 | FAIL（判错） |

**这些不是产品坏了，是验错了地方。**

用户原话：

> 「AI走的时候第一轮就边走边验证了。能拿到所有的记录。
>   然后最后根据记录写json。而不是回过头就复验证。」

## 三、执行链路

```
prep        准备（设备、用例、知识卡目录）
  ↓
plan        进入一步：取该步的落点/目标/坑/知识
  ↓
strong_target  代码能不能唯一确定要点的东西？
  ↓            （能就直点，不用问 AI）
decide      AI 决定下一步动作（tap / input / done / …）
  ↓
act         执行动作
  ↓
check       这一步走完了吗？
  ↓
  ├─ 没走完 → 回 decide 继续
  └─ 走完   → verify_step = 本步 id
                ↓
             verify  验这一步名下的预期（人就在这一屏）
                ↓
                ├─ 还有没验的 → 继续验（AI 可以为了看清而点击）
                └─ 验完       → step_index + 1，回 plan 走下一步
  ↓
（所有步骤走完）
  ↓
learn       根据记录写 case_learned.json
  ↓
finish      出结论
```

**关键点：`verify` 发生在 `check` 判定完成之后、`step_index` 推进之前。**

这样人停在正确的画面上，验的就是该验的东西。

## 四、判定规则（做减法后的核心）

### 4.1 这一步"走完了吗"

```
点击 → 观察变化
  ├─ XML 没变（changed=False）   → 界面没动，没推进一步 → 交 AI
  └─ XML 变了
       ├─ Activity 变了          → 到了 ✅（硬证据，代码判）
       └─ Activity 没变          → 变了但不知道是啥 → 交 AI
```

**代码只判能确定的两件事**：

1. Activity 切换
2. 崩溃 / 卡死

其余（Fragment 切换、弹窗、局部更新、Toast、WebView）**全部交 AI**。

因为这几件事在 XML 层面长一个样，代码分不出来。硬要分就得为每种写识别逻辑 —— 那是加复杂度，不是做减法。

### 4.2 预期"成不成立"

**全部交 AI**。代码判据（`check`）已停用。

停用理由（都是真机实测）：

- `a4` 判 `iv_add_hint`「不在」，实际就在
- `a13` 要数色块，判据根本写不出来
- 同 Activity 多 Fragment 时，`activity` 判据完全失效

更糟的是它判错时会**盖过 AI 的结论**（"判定纠正"），错得更理直气壮。

### 4.3 AI 为了看清可以动手

验证 a13「共 10 种颜色」时，色板没展开，AI 看不到。

**AI 自己点开看，看完再判。** 这次点击也是流程的一部分，会被记录。

不需要单独的「补证据」机制 —— AI 在 `decide` 里本来就有 `tap` 能力。

> ⚠️ 曾经实现过一套 `assert_fix` / `need_action` / 补证据，run 79 它把整轮跑崩：
> 关不回去时回退按 `back`，人退到桌面，后面 11 条断言全对着 launcher 判。
> **已经删掉。别再引入。**

## 五、步骤是"大概的"，不是严格清单

用户原话：

> 「测试步骤只是大概的一个步骤。中间可能增加一个引导页。
>   但这个也是流程的一部分。所以第一次走就是要探出这个流程。」

意思是：

```
原始 steps：  大概方向
实际执行：    s1 → [多出引导页] → s2 → s3 → ...
```

**中间多出来的引导页、权限框、弹窗，它们也是流程的一部分，不是错误。**

所以：

- 不因为"实际路径和预期不符"就判 BLOCKED
- `asserts[].step` 写的是**大致归属**，实际验证发生在"走到那一步且停稳"时
- 第一轮的任务是**探出真实路径**，把它记下来

## 六、JSON 格式（精简）

```json
{
  "case_id": "176",
  "title": "手动创建空课程表并添加课程弹窗",
  "package": "com.zui.calendar",
  "steps": [
    {
      "id": "s4",
      "desc": "点击空课表第一个小节，进入课程编辑",
      "landing": "activity=.timetable.course.EditCourseActivity",
      "target": "rid=cv_empty_content",
      "pitfalls": ["..."]
    }
  ],
  "asserts": [
    { "id": "a13", "step": "s4",
      "desc": "弹窗里可以调整课程背景色，共 10 种" }
  ]
}
```

**`pitfalls` 保留**（用户：后面有用）。

**断言字段：`id` / `step` / `desc` / `check`。**
`step` 必填（不填这条断言验不了）；`check` **可写但代码不执行** ——
`evaluate_check` 已停用，写了的判据只会作为线索交给 AI 参考。
上面的例子里特意没写 `check`，让 `desc` 独自承担"要验什么"。

## 七、回写 JSON

跑完把这一轮的经验写进 `case_learned.json`：

```json
{
  "case_id": "176",
  "status": "PASS",
  "usable": true,
  "steps": [ ... 实际走通的步骤 ... ],
  "asserts": [
    {
      "id": "a13",
      "desc": "弹窗里可以调整课程背景色，共 10 种",
      "result": "PASS",
      "verify_steps": [
        {"n": 1, "action": "click", "target": "llCourseColor",
         "why": "要数色块，先点开色板",
         "shot": "shots/step30/shot.png", "xml": "shots/step30/dump.xml"}
      ]
    }
  ],
  "knowledge": [ ... 用到的知识卡 ... ]
}
```

**`verify_steps` 是这份 JSON 最有价值的部分**：为了验证这一个点，实际执行了几步、每步做了什么、证据在哪。

### 7.1 usable 标记

| 结果 | 生成 JSON | usable |
|---|---|---|
| PASS | ✅ | `true` |
| FAIL | ✅ | `true`（路径是对的，只是产品没达标） |
| **BLOCKED** | ✅ 生成 | **`false`** |

**BLOCKED 说明没走完，路径是残缺的。生成是为了排查，但不能当基准用。**

这条同时解决了一个隐患：**AI 第一次判断错了，后面就取不到证据 → BLOCKED → 错误不会被固化进下一次。**

## 八、这一版删掉了什么

做减法，去掉的都是实测证明有害或无效的：

| 删掉的 | 原因 |
|---|---|
| `evaluate_check` 判据 | a4 判错、a13 判不了、多 Fragment 失效，还会盖过 AI |
| `assert_fix` / `need_action` 补证据 | run 79 靠 `back` 回退把整轮跑崩 |
| 回头统一验断言 | 验的时候画面早变了，a2/a4/a5/a6/a14 全判错 |
| `check` 字段 | 判据没了，字段也没意义 |

## 九、验收标准

改完之后要能通过：

1. **a13 判 PASS**，且 `actual` 里说得出色块数量（证明 AI 会为了看清而点开）
2. **a2 / a4 / a5 / a6 / a14 不再因"验错画面"而 FAIL**（要么真有结论，要么诚实说 BLOCKED）

4. **回归 70/70 通过**

## 十、血泪教训（别再犯）

1. **跑崩那一轮的不是 `back` 本身，而是"为了补证据而自动连续 back"。**
   run 79 的实现没有停止条件：关不掉时一路 back 退到桌面，
   后面 11 条断言全对着 launcher 判 —— 这才是报废的原因。
   人手动按一次 back 退一层是正常操作，**可以**；问题在"无人看管地连按"。
2. **代码判据判错比判不了更糟** —— 它会推翻 AI 的正确结论。
3. **一次改太多必然互相冲突。** run 79 是补证据 + bind_step + 回写聚合一起上的结果。
4. **测试全绿不代表真机对。** 74 个测试全过的时候，真机已经崩了。
