## 核心改动：check → verify → plan

```
check（这一步走完了吗）
  ├─ 没走完        → plan（重试，撞轮次闸门）
  ├─ 走完，有预期   → verify（就地验！）──┬─ 还有预期 → verify
  └─ 走完，没预期   → plan（下一步）      └─ 没了     → plan / finish
```

关键点：check 判定完成时**不推进 step_index**，而是设 `verify_step`。
verify 验完这一步所有预期才推进。

⚠️ 没有断言的步骤必须**直接推进**，否则没人清 `verify_step`，流程永远卡死。

## 验证时 AI 可以自己动手

用户原话：「因为是这样。当前信息不足。我需要进一步点击或者其他动作才能判定。」

AI 判定时说「判不了，需要点开 XX 看」，执行器就去点一下，然后**重判同一条**。

这不是独立的"补证据"机制（那套复杂东西已经删了），就是**验证时自己动手看一眼** ——
人类测试员点开色板数颜色，看完点「取消」退回，天经地义。

实现要点：
- 就在 `verify` 内部处理，**不加节点**
- 上限 `ASSERT_AI_RECHECK_MAX` 次，防无限点
- 看完用 AI 给的 `close_with` 按钮文字关回去
- **绝不按 back**（保护 16：run 79 按 back 退到桌面，后面 11 条全判错）

## 回写 JSON（learn 节点）

跑完在 run 目录生成 `case_learned.json`：

```json
{
  "case_id": ..., "title": ..., "package": ...,
  "status": "FAIL",       // 这一轮的真实结论
  "usable": false,        // 能不能直接拿去重跑（BLOCKED/FAIL 都是 false）
  "steps": [
    {"id": "s1", "desc": "...", "locate": "...", "landing": "...",
     "actions": [{"rid": "iv_more"}, {"rid": "item_title"}],
     "pitfalls": ["s1 落点未到，第 2/3 次尝试"]}     // 这一步踩过的坑
  ],
  "asserts": [
    {"id": "a13", "desc": "...", "step": "s4", "result": "PASS",
     "verify_steps": [                                // 为验它做了什么
       {"n": 1,
        "why": "配色面板没展开，看不到色块，无法核对数量",
        "open": "课程背景色",                          // 点开了什么
        "close": "关闭",                               // 怎么关回去
        "shot": ".../shots/step32/shot.png",           // 截图
        "xml":  ".../shots/step32/dump.xml"}],         // XML
     "verify_count": 1,
     "actual": "屏幕中弹出「课程背景色」颜色选择弹窗，含 2 行色块、每行 5 个，共 10 个..."}
  ],
  "knowledge": [...]       // 查过什么知识
}
```

这就是用户要的「为了验证个点我执行了多少步，每一步都记录」：
**为什么点、点什么、怎么关、截图、XML 全在。下次重跑可以照着走。**

### 这一块踩的坑

**1. `learn` 节点从来没被调用**

`route_after_check` 和 `route_after_verify` 在步骤走完时直接返回 `"finish"`，
绕过了 `learn`。表现：跑完 run 目录里根本没有 `case_learned.json`。

修：两个路由都改成返回 `"learn"`（用 `abort` 终止时才直接去 finish）。

**2. 回写的 JSON 是空壳**

`status` 是空的、`verify_count` 全 0。两个原因：

- `build_learned_case` 读 `state["status"]`，但 status 是 **finish** 节点才算的，
  而 learn 跑在 finish **之前** → 读到空字符串。
  修：learn 里按同样口径先算一遍。
- `verify_actions` 我写的是 `{"assert": aid}`，而 `build_learned_case` 按
  `assert_id` 归集 → 对不上，全部丢弃。
  修：键名改成 `assert_id`。

**教训：跨模块传 dict 时，键名必须去对方代码里核对，不能凭印象写。**

## 重写中踩的坑（都是自己踩的）

### 1. plan 只准备上下文、不取画面

第一版把 `plan_node` 写成直接转调旧实现，结果：

```
plan×81 / decide×80 / act×0     ← 80 轮原地空转
```

旧图的 `observe` 节点负责刷新 `last_shot`，我把它合并进 plan 却没有真正实现。
于是 `last_shot` 永远是空的 → `ask_vision` 永远失败 → 模型反复要求看图。

**教训：合并节点不等于删节点，被合并节点的职责必须在新节点里真的实现。**

### 2. 路由判据丢了一半

旧 `route_after_decide` 认 6 种动作形态，我第一版只判了 `op/kind`，全不匹配。

旧注释里已经写了三遍这个教训：
> 176 轮 05~08：模型请求看图 → 路由只认坐标 → 判成"无动作"
> 169：模型要按返回键 → key 没坐标 → 动作静默丢失
> 176：模型正确调用 type_text → 路由只判 next_x → 输入从未发生

**教训：action 里任何一个"能单独构成动作"的字段，路由里必须有分支。**

### 3. AssertVerdict 漏字段

旧 schema 有 `unknown`/`error` 字段（保护 9）。我重写时只留了 `passed/actual/event_id`，
结果"模型回复解析失败"这件事会**静默丢掉**（178 实测过）。

**修正：不重新定义 schema，直接从 nodes.py 导入那一份。**

### 4. 设备接口签名靠猜

写了 `dev.click_text(...)` 和 `dev.click_rid(rid, step=..., why=...)`，
实际都不存在 / 签名不对。

而且 `click_rid` 内部调 `act()` 时**不传 step**，记账会丢 —— 回写 JSON 时就断了
"这次是为验哪条断言点的"。

**修正：先 `inspect.signature` 确认真实签名；自己取坐标再调 `act(step=..., why=...)`。**
