# 开发记录：执行器踩坑清单

> 这里记的都是**真机上实测撞出来的**坑，不是猜测。
> 每条都写了"现象 → 根因 → 怎么改"，因为同样的现象可能有完全不同的根因，
> 只记结论下次还是会踩。

---

## 0. 调试方法：先看这里，能省掉大量时间

### 慢在哪

跑一次完整用例：冷启动 5s + 引导 3s + 权限框 + 走位 30s + 模型每轮 10~20s。
一旦要回头改代码，**这 5~15 分钟全部白等**，而且大头等待跟要验证的那行代码无关。

### 用 `dev_probe.py`，别直接重跑用例

| 想验证什么 | 命令 | 耗时 |
|---|---|---|
| 解析对不对 / do 能不能转成动作 | `python dev_probe.py logic 182` | 2 秒 |
| 把设备摆到目标页 | `python dev_probe.py goto "课程表页-空态"` | 25 秒 |
| 某个控件点了会怎样 | `python dev_probe.py tap --rid btnCreateManually` | 3 秒 |
| 只跑准备阶段 | `python dev_probe.py prep 182` | 30 秒 |

设备状态**可以连续复用**：`goto` 摆好之后，`tap` / `prep` 可以反复跑，
不用每次都冷启动。这一条把迭代周期从分钟级压到秒级。

> `goto` 的目标是**路径图里的节点名**，路线由 `pathmap.path_between` 现算，
> 不在这里写死。想加目标就加节点名，别加"怎么走"。

## ★ 最大的教训：不要重复造工具层的轮子

这条放在最前面，因为它**比其他所有坑加起来都浪费时间**。

调试 182 时我在编排层（`child_agent.py`）写了一整套自己的判定逻辑：
`_on_related_page`（自己认弹窗）、`match_landing`（自己解析 --expect）、
`_PAGE_FEATURE_KEYS`……而 **工具层早就有**，而且做得更好：

| 我重造的 | 工具层已有的 | 差在哪 |
|---|---|---|
| `match_landing` 手写解析 | `checkpoint.parse_expect` + `evaluate` | 手写版用 `endswith`，`EditTimetableActivity` 会误命中 `TimetableActivity` |
| `_on_related_page` 认弹窗 | `checkpoint.detect_transient` | 工具层只认白名单，白名单外交回 AI —— 正是用户要的正确分工 |
| 自己写走位路线 | `pathmap.path_between`（BFS） | 路径图 13 个节点、带识别键，换分辨率不失效 |
| 自己判"落点对不对" | `act --expect` → `checkpoint` | 工具层当场回 `checkpoint.missed`，写明期望什么、实际什么 |

**根因**：我一上来就去读 `child_agent.py`（3500 行），没先读工具层。
`assets/tools/` 下十几个模块，每个文件头的注释都在讲"为什么这么写"，
`checkpoint.py` 里甚至直接记着我踩过的那个 `endswith` 坑。

**规矩**：改判定/走位/弹窗这类逻辑之前，**先 grep 工具层有没有现成的**。
`assets/tools/checkpoint.py`、`pathmap.py`、以及
`knowledge/paths/<pkg>.md`（路径图）是第一站，不是最后一站。

**重构后**：
- `match_landing` → 委托 `checkpoint.evaluate`（补 `package=` 判据、`t=`/`r=` 别名）
- `_pathmap_expect` → 查路径图拿落点，查不到就返回空串（第一轮探路）
- prepare 的每个动作都带 `expect`，用 `checkpoint` 判落点，不再看 `res.ok`
- `dev_probe` 的走位交给 `pathmap.path_between`

## 1. `skip_if` 在错误的页面上求值 → 整条 prepare 被跳过

**现象**：case 182 里"存在一个课程表"这条前提**从来没执行过**，
周视图一直是空态，步骤 1 要的 `cv_empty_content` 永不出现，模型在首页空转 80 轮。

**根因**：`skip_if: {not_on_page: '还未添加课程表'}` 的意思是
"屏上没有这句空态文案 = 课表已经建好了，可以跳过"。
但用例开跑那一刻屏上停在**权限说明框**（冷启动必经），
当然没有"还未添加课程表"这句 —— 于是判成"已满足 → 跳过整条 prepare"。

**判据本身没错，错在"在错误的页面上问它"。**

**改法**：`_on_related_page()` 先判断"当前界面算不算跟这条前提相关"，
不相关就返回 `None`（判不了），路由退化成"照跑"，宁可多准备一次。

⚠️ 判断依据**不能只看 activity**：权限框是叠在 `.AllInOneActivity` 上面的，
activity 看着完全正常。要看**可点元素数量**（弹窗只有三四个）和屏上特征词。

## 2. 只在 prep 阶段收集、没人再执行 → prepare 永远不落地

**现象**：`prep_node` 已经把"要做的 4 个动作"记进了 `prepare_wants`，
但日志里 `prep_apply` **一次都没触发**。

**根因**：`prep_apply` 只挂在 `start_check` 后面，且要求 `start_mismatch` 为空。
可起点纠正期间 mismatch 一直在，模型一旦走到起点就直接进 step 模式，
**再也回不到 `start_check`** —— 于是永远触发不了。

**改法**：把 `prep_apply` 也挂到 `route_after_plan` 上。
`plan` 是"每步开始前"的必经点，放这里才真正保证"先准备、后执行"。

⚠️ 必须同时排除 `start_mismatch`：界面没到位就进 `prep_apply`，
它会立刻 return，路由又把它送回来 → **死循环**。

## 3. `input text` 不支持非 ASCII

**现象**：
```
shell 失败(255)：input text "测试课表"
java.lang.NullPointerException: Attempt to get length of null array
    at com.android.server.input.InputShellCommand.sendText
```
名字没输进去，后面点"保存"被当成空名拒绝，又退回空态页。

**实测对比**（同一台设备）：

| 输入 | 退出码 |
|---|---|
| `HelloWorld` | **0** |
| `测试课表` | **255**（NPE） |

**改法**：非 ASCII 一律换成 ASCII 占位名（`TestTimetable`）。
真要输中文得走 IME 粘贴，是另一个工程量，暂不引入。

**连带修的一处**：原来 `input` 失败只记一条 issue、然后**继续点保存**，
报告还写着"4 步完成"，问题被彻底掩盖。现在输入失败直接中止这条前提。

## 4. `except dc.DecisionError` —— 从来没 import 过 `dc`

**现象**：模型输出格式不对时，报告里只有
```
NameError: name 'dc' is not defined
```
完全看不出真实原因。

**根因**：`subagent.py` 里 `dc.DecisionError` 出现 3 次，但**整个文件没有 import dc**。
平时不暴露，因为只有异常路径才求值到它。

**更糟的是**：`test_assert_robust.py` 断言的是字面串
`"except dc.DecisionError" in src` —— **测试锁着错误写法，替 bug 背书**。
改代码时测试反而报错，差点让我以为是回归。

**改法**：`from decision_channel import DecisionError`，改用 `DecisionError`；
测试改成"必须真的 import 了 + 必须用导入后的名字 + 不许出现未定义引用"。

**教训**：测试断言字符串时，别断言"代码长什么样"，要断言"行为对不对"。

## 5. `AssertVerdict.passed: bool` 太严，模型回 null 就崩

**现象**：
```
ValidationError: Input should be a valid boolean [input_value=None]
During task with name 'assert'
```
整个 assert 节点崩掉，整条用例作废。

**根因**：模型有时回 `"passed": null`，它想说的是"我没看清"。
严格 `bool` 不接受 None。

**改法**：改成 `bool | None`，None 走 unknown 通道。

**连带**：`passed = bool(v.get("passed"))` 会把 None 悄悄变成 False ——
正是文件里注释批评过的"把没验成当成验失败"。改成显式三态判断。

## 6. 可点容器没有文案 → 模型在一堆空壳里瞎选

**现象**：日历「更多」菜单里，模型反复点 `iv_more`，把菜单开了又关、关了又开，
最后被判"连续点同一点无效 → 卡死"。

**根因**：菜单项是 `TextView text="课程表" clickable="false"`，
真正可点的是外面那层 `FrameLayout`，**没有 resource-id、没有 text**。
`next` 只保留可点/可滚元素，于是返回四个 `{'c':[2697,371]}` 这样的空壳，
模型根本分不清哪个是「课程表」。

**改法**：`common.py` 的 `summarize_xml` 里，可点节点自己没有文案时，
**从子节点捞** text / content-desc / resource-id 补上。

改完 `next` 变成 `{'c':[2697,371],'t':'课程表','r':'item_title'}`，
模型一次就选对了。

**注意**：这是修**根因**（看不见名字），不是修症状。
循环守卫本身没动 —— 它是坐标比的，合法的开关菜单本来就跟卡死长得一样。

## 7. 冷启动不止一层弹窗

`pm clear` 之后依次会遇到：

1. 系统权限框（`com.android.permissioncontroller`）
2. App 的「日历需要使用以下权限 / 同意」说明页（**这一个有延迟，
   点完上一个之后才出现，脚本里等 3~4 秒再 dump**）
3. 课程表引导页（`TimetableGuideActivity`，点「我知道了」）

任何一个没处理，后面的控件全都拿不到 —— 表现就是"当前屏找不到 X"。

## 8. 会话细节

* `RealDevice(skill_root=..., serial=...)`，`start_session(title)` 要传 title。
* **不开会话**就 `observe_raw()` 会报
  `Audited device calls require a session; use session start first`。
* 方法名是 `start_session`，不是 `session_start`。
* `run_case_json.py` 从 **stdin** 读 JSON，不是命令行参数：
  `'{"case_name":"182"}' | python run_case_json.py`

## 9. 关于"点两下"的实测结论

`cv_empty_content` 确实需要点两下（YAML 里写的是真的）：

```
第1次 -> activity 仍是 TimetableActivity   （被网格吸收）
第2次 -> activity = EditCourseActivity     ✅
```

但 `btnCreateManually` **只需要一下**：

```
第1次 -> activity = EditTimetableActivity  ✅
```

模型曾把"点两下"的规则套到 `btnCreateManually` 上，连点三次，
被循环守卫判成卡死。**不同控件的点击行为不一样，不能套用。**
